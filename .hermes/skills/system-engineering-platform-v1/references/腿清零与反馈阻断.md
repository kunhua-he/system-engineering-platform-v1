# 腿清零与反馈阻断（处置配方）

只在「反馈已蒸馏完但腿清不掉」或「空登记位」时读。清树的**四种卡点**与入口在 SKILL.md §五。

## 腿清零：把阻断蒸馏成债务

**唯一判据口** = `v1_task` 操作=`记忆边界`。四条口径：① 未审完来源 ② 未判词条目 ③ 债务无有效承接
④ **待核须保留**（判词=待核 且 有补证 或 有 `关联目标`）。

**④ 是唯一会永久卡死腿的口径**：它既不许假审完（帧十五/十六是承重身份证），也不因「有关联」就放行。
所以「几千条反馈蒸馏完 ⇒ 腿还是清不掉」的真身就是它（实测 2078 条）。

**华哥口径**（阻断需要大工程时）：**把诉求蒸馏回债务，然后直接提交腿**：
1. 台账 `未完成.json` 加一条承接条目（`[号, 缺什么, 落点, 验证命令]`；走 `v1_edit` ⇒ 先开腿 + 补认领）；
2. **先把新条目合进主干再改判**（`v1_job` 具名作业 `合主线`）：批量判定的关联校验读的是
   **主干现行台账号**，条目还留在腿里没合 ⇒ 一律「关联未知或已不存在」**整批零写**；
3. `v1_task` 操作=`批量判定` 把那批「待核」改判为**债务**：`关联种类`=`未完成条目`、`关联目标`=**台账号字面**
   （如 `"337"`）。承接有效只认**现行台账号**或**真实开工**，未知即拒 —— **填主题名（如 `新:命名面`）会整批零写**，
   先把「主题名 → 条号」映射算好再提交。分批 100–300 条，实测秒级零失败；
4. `记忆边界` 复核四条归零 ⇒ `单纯释放`。

**四个坑（都实测踩过）**：
- **批量判定的「理由」也过字面禁项闸**：㊵ 零字面十干 —— 十个天干字**无论单独用还是嵌在常用词里**都会拦
  （实测：表示「本人」的那个词、表示「打补」的那个词，都因含天干字而红）⇒ 程序化提交前先做一遍批量替换，
  否则整批零写、白跑一轮。
- **台账正文不许写开工号字面**：`清树门禁.读未完成行` 是**按行** `开工号 in 行` 的纯文本匹配 ⇒
  正文里写 `v1-100642` 就把该腿判成「台账点名 ⇒ 不许清」。写「第 642 号开工」。
- **源码树不许写「台账 NNN」与腿号**（判据 ㊳ 形⑤ = 前缀 + 空白 + 号，`.md` 全算）⇒ 写「台账（条目号见
  `未完成.json`）」、「第 NNN 号腿」。另 ㊵ 零字面十干：注释里表示「本人」的那个词直接红，改「自行」。
  **新写的注释最容易踩**：判据 ㊳ 的修法是「**清出处、留事实**」—— 去掉号、把事实原样留着，别把一个号换成另一个号。
- **`单纯释放` 要求「已合主干」**：空腿（无独有提交）合并会因 `MERGE_HEAD` 缺失而拒 ⇒ 直接
  `单纯释放` 即可（它认「支线已合并到主工作树」）；未合主干的腿必须先把改动改对再合，不能带错合。

## 空登记位：子代理只建登记位、没交报告

**形状**：`读取状态=缺件待核` · `内容指纹=missing` · `报告路径`/`快照路径` 全空 · `提取条数=0`
⇒ 永远审不完 ⇒ 永久卡原腿。

**它与 `反馈帧样本.py` 的缺件夹具完全同形**（无指纹 / 无路径 / 提取 0）⇒ 给「审完」开出口**必然**打红
帧十五 / 帧十六（真实发作过：反馈专项 4 条红、合并被 pre-commit 拒）。既有判据是**故意**
这么设计的（防假审完），**别去改它** —— 改判据前先跑一遍反馈专项确认没打红。

**先按 `提取条数` 分两路，别一律删**（实测：一律删会丢事实）：

| 形状 | 判据 | 处置 |
|---|---|---|
| **真空壳** | `提取条数 = 0`（无指纹 / 无路径 / 未提取任何条目） | 走 `清理执行.删来源行(连接, 来源号表)`（只删 `反馈来源` 行） |
| **原件缺失但事实已承接** | `提取条数 > 0` **且** 逐条已判词 | **别删** —— 走 `v1_task` 操作=`登记报告审完` 解除待核（见下） |

第二路**删了会丢已判词条目、断掉债务溯源链**（实测 7 个来源挂着 29 条已判词条目，其中 10 条债务已关联
台账条目）⇒ 华哥说「少了的就删」时**先核实「内容是不是真少了」**，事实在库里就不该删。

**第二路的操作姿势**：`v1_task` 顶层 `开工ID` = **来源的开工号**（跨开工整批拒）· `操作` = `登记报告审完` ·
`参数` = `{"审完表": [{"来源号": N, "提取条数": N, "判词条数": N, "待核理由": "<沿用库里的原文>"}]}`。
前置条件（`反馈审完.py::规范审完` 的「事实已承接优先」出口）：`待核理由` 非空 · `读取状态` 非未读/已读 ·
`提取条数 > 0` · `已判词集 ≥ 提取条数`。成功回执带 `审完: true` · `待核: false`，库里落
`审完说明` = 「原件不可回读（<原状态>）· 发现事实已完整蒸馏（提取 N 条 · 判词 N 条）」，`待核理由` 原样留痕。
验完再跑一次 `未蒸馏反馈集` 确认该开工号已空。

**第一路（真空壳）的删前必做**：核 `反馈条目` 关联为 0 · 导出全字段留痕 · `sqlite3` 在线 `backup()` 备份
（WAL 下备份与主库字节不同是正常的，那是逻辑一致快照）。诉求（缺正式作废口 · 两种缺件语义在库里不可判别）
落台账，不夹带在腿里硬改。
