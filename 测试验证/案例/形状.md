# 案例与运行回执 · 形状（端到端主门禁）

上级：系统工程平台 V1 ／ 落点：`测试验证/案例/形状.md`
依据：`项目文档/决策记录/2026-09-26_验证面的边界.md` 第五节（③类：demo 案例 + 运行回执）·
`项目文档/设计文档/判据的可信性.md`（最高判据）· `跨语言适配/边界协议/边界协议.md`（只读，未动）

**一句话**：用**真案例跑真链路**——跑不通当场自爆，死在哪一层由**既有错误码的段位**与
**失败是哪一步判出来的**直接给出，**不另造一套断言代码**。

## 一 案例目录形状

```text
测试验证/案例/
├─ 形状.md                      本文件：形状的权威
├─ 运行回执.jsonl               每次运行的读数，**追加**，一行一条 JSON
├─ 装门禁.sh                    把阻断门禁装进 .git/hooks/pre-commit（版本化的那一件）
├─ 跑案例/                      跑案例的程序（crate `v1-case-runner`，见第六节）
├─ <案例名>/                    一个案例一个目录 —— **将来计算器这类例程就放这里**
│   ├─ 案例.json                做什么：步骤链（能力编号 + 按契约行序的实参来源）
│   ├─ 输入.程序文本             我们的程序文本源码（原生格式）。「程序」类案例必有
│   ├─ 输入.容器                 .e 容器字节。容器类案例用它，名字随案例自取
│   └─ 期望.json                期望什么：按步骤**一一对应**（运行结果 或 诊断）
```

**编码一律 UTF-8；换行一律 LF**（`.json` 与 `.md` 都是）。`输入.程序文本` 例外：
它**按字节原样**送进能力，**案例库不替调用方转码**——我们的程序文本规格（`程序文本格式.md` 第二节）
是「写出 LF、读入认 CRLF」，认不认 CRLF 是被测对象的事，不是案例库的事。

### 1.1 `案例.json`

```json
{
  "案例名": "真程序文本",
  "说明": "一段人读的话：这个案例要证明什么、输入是哪来的",
  "步骤": [
    {
      "名": "把真程序文本交给 1101 词法分析",
      "能力编号": 1101,
      "实参": [{ "类型标签": 4, "来源": "程序文本" }]
    }
  ]
}
```

- `步骤` **至少一步**。空步骤链是空集 —— **空集不算通过**（`判据的可信性.md` 第二节）。
- `实参` 的**行序即契约**（`能力契约.参数表` 的排列），个数与每行类型标签必须与契约一致。
  不一致 = **案例自身写坏了 ⇒ 工具错误**（退出码 2，不写回执），不是被测对象的缺陷。
- `实参[].来源` 是**封闭枚举**，四个值：

| `来源` | `值` | 取什么 |
|---|---|---|
| `程序文本` | 无 | 案例目录里的 `输入.程序文本` |
| `文件` | 路径 | 相对路径按**案例目录**解；绝对路径原样用（仓外只读语料走这条） |
| `十六进制` | 十六进制串（可带空白） | 就地写的小输入，免得为几个字节建一个文件 |
| `上一步返回` | 无 | 上一步交回的**字节集**（步骤链，`1105 → 1104` 的往返就用它） |

### 1.2 `期望.json`

```json
{
  "步骤": [
    { "结果": "成功", "产物": { "判据": "逐字节等于文件", "文件": "输入.容器" } },
    { "结果": "失败", "死在哪一层": "内核", "产物": { "判据": "空槽" },
      "错误码": { "码": 1, "名称": "提供者未载入", "可重试": true, "可自愈": true, "需人工": false } }
  ]
}
```

- `步骤` 条数**必须与 `案例.json` 的步骤条数相等**（不等 = 案例写坏了 ⇒ 工具错误）。
- `结果` 只认 `成功` / `失败`。**没有「跳过」这一档**；也没有「大概通过」。
- `产物.判据` 是**封闭枚举**，五个值：`不判` · `空槽` · `错误槽` · `非空字节集` · `逐字节等于文件`。
  `错误槽` 要带一个整数 `码`（例 `{"判据":"错误槽","码":1136}`）——它与 `空槽` 是**两件不同的事**：
  空槽 = 调用没到扩展（「未命中返回空」，宪法第 6 条）；错误槽 = **扩展抛错了**（码在返回槽里）。
  失败时也用它 —— 宪法第 6 条「未命中返回空」就靠 `{"判据":"空槽"}` 来证，
  不写就没人证它（那是 `判据的可信性.md` 说的「空集算通过」）。
- `错误码` 的**五项全部比对**：`码` · `名称` · `可重试` · `可自愈` · `需人工`。
  三项业务判断**猜不出来**（`README.md` 第七节），必须人写进案例里。

## 二 回执形状：`运行回执.jsonl`

**一行一条 JSON，追加，永不改写。** 字段逐个如下（`null` = 该项不适用）：

| 字段 | 类型 | 口径 |
|---|---|---|
| `提交哈希` | 字符串 | `git rev-parse HEAD` 的**完整**值（40 位，不截断）。取不到就**不跑**（工具错误） |
| `工作区是否干净` | 真假 | `git status --porcelain` 除**回执自身**之外是否为空。排除自身是因为每跑一次就追加一行 ⇒ 它自身永远脏，不排除该字段就恒为 `false`、永远没有信息量 |
| `案例名` | 字符串 | `案例.json` 的 `案例名` |
| `结果` | 字符串 | `通过` / `失败` |
| `死在哪一层` | 字符串或 `null` | 失败时必填：`调用方` / `适配器` / `内核` / `扩展`（映射见第三节） |
| `死在哪一步` | 字符串或 `null` | 失败时填层内位置：`装载` / `注册表` / `调度` / `执行` / `空声明根` |
| `错误码` | 对象或 `null` | 失败时必填。六项 + 一个旁路项：`码` · `段位` · `名称` · `可重试` · `可自愈` · `需人工` · `已登记` |
| `耗时微秒` | 整数 | 本案例从开跑到出读数的墙钟微秒（`Instant::elapsed().as_micros()`） |
| `跑的时间` | 字符串 | UTC 的 `YYYY-MM-DDTHH:MM:SSZ`（**不是本地时间**：跨机器比读数时本地时区是噪声） |
| `说明` | 字符串 | 一句话读数：成功时写产物形状，失败时写「第几步 + 为什么」 |
| `步骤` | 数组 | 逐步读数：`名` · `能力编号` · `能力名` · **`调用结果`** · **`符合期望`** · `死在哪一层` · `死在哪一步` · `错误码` · `耗时微秒` · `说明` |

**`调用结果` 与 `符合期望` 是两个字段，不许合成一个**：`调用结果` 是**平台那一侧**的结果
（`成功` / `失败`），`符合期望` 是**这一步有没有对上 `期望.json`**。合成一个字段，
「调 1101 期望它失败」这条案例就会读成「结果=成功」，于是「案例通过」被误读成「能力可用」
—— **那就是假绿**。顶层 `结果` 说的是案例判定（`通过` / `失败`），也不是平台那一侧的结果。

`错误码.已登记` 是**旁路项**（`边界协议.md` 允许新增旁路字段）：这个码**没在任何事实源里登记**
时为 `false`。契约规定「未登记的错误码不许抛出」⇒ 出现 `false` 就是一条缺陷证据。
**取不到登记时不编一个名字**——编名字就是把「未登记」藏起来。

### 2.1 一行真实内容

**不复述读数**——照抄一份到本文件里，下一次跑就与实物不一致（复述必漂移，`README.md` 第八节
已经为这件事吃过一次亏）。要看实物就读 `运行回执.jsonl` 的第一行；要看某个案例最近一次的
读数就用 `tail -n 5`（回执按案例名排序追加，一次运行 5 行）。

## 三 「死在哪一层」怎么定

**层级名只有四个**，就是那条链上的四个：`调用方 → 适配器 → 内核（装载/注册表/调度）→ 扩展`。
**不许自身编层级名。** 定法只看两个既有事实源，**不看人怎么想**：

| 事实源 | 怎么读 | 定出什么 |
|---|---|---|
| **失败是哪一步判出来的** | `适配器::装载` 的 `装载失败` · `适配器::调用能力` 的 `调度错误` · 返回槽是不是错误槽 | **层** + **层内位置** |
| **错误码的段位** | `段位 = 码 / 号段类宽度`（`README.md` 第七节：段位即归属） | 段位 → 层的号段归属 |

段位 → 层（`README.md` 第七节「号段即归属」）：

| 段位 | 归属 | 层名 |
|---|---|---|
| `0` | 内核自有 | **内核** |
| `1–6` | 核心支持库 / 三方封装 | **扩展** |
| `7` · `8` | 模块 · 技能 | **扩展** |
| `9` | 接口面与构建验证 | **接口面**（不在本链的四个名字里，如实另给一名，**不硬塞进「内核」**） |

映射表（`跑案例/src/跑.rs` 是唯一实现处）：

| 观测到 | 层 | 层内位置 | 错误码 |
|---|---|---|---|
| `适配器::装载` 返回 `装载失败::载入(内)` | 由 `内` 的变体名按名查到码，段位 0 ⇒ **内核** | `装载` | 该码（判定六步哪一步不过） |
| `装载失败::空声明根` | **适配器** | `空声明根` | 无（跑案例总是递进 ≥1 份声明 ⇒ **到不了这一格**，如实登记） |
| `调度错误`，且 `能力契约(号)` **有值** | 码 1–5 段位 0 ⇒ **内核** | `调度` | 码 1/2/3/4/5 |
| `调度错误::提供者未载入`，且 `能力契约(号)` **无值** | **内核** | `注册表`（占位项兜底） | 码 1 |
| 转发成功，但返回槽的类型标签 = **错误标签** | 由槽里那个码的段位定（扩展段 ⇒ **扩展**） | `执行` | 槽里的码 |
| 转发成功，返回槽是正常值 | —— | —— | 通过 |
| 案例文件坏了 / 语料读不到 / 接缝被解析到别的声明上 / git 读数取不到 | **不写回执** | —— | **工具错误**，退出码 2 |

**「号不在」与「号在但没实现」分得开**，靠的就是 `能力契约(号)` 有没有值：
- 保留项（1101）：号**在**声明的表里、状态位标了错误项 ⇒ 由**调度**判出；
- 从未声明的号（5003）：号**不在**任何声明的表里 ⇒ 由**注册表**的占位项兜底。

### 3.1 一处缺口：任务书要的「调用留痕」取不到

任务书说死在哪一层要用「错误码的段位 **+ 调用留痕**」。**实测：调用留痕取不到。**
`运行内核/调用留痕`（crate `v1-trace`）**没有被适配器接上** —— 适配器源码里对 `留痕` /
`v1_trace` 的引用数是 **0**，适配器的公开面也没有任何取留痕的口。
⇒ 本件只用**段位**这一个事实源定层，留痕那一半**如实报缺口**，不假装用上了。
（最近的可用读数是适配器账本的 `累计耗时毫秒(号)`；它记的是耗时，定不了层，故未进回执。）

## 四 为什么回执要绑提交哈希

**「回执必须绑提交哈希」是<u>本件自身的规则</u>**（2026-09-27 更正：本条曾写成「照抄
`判据的可信性.md` 第三节」，而该节列的是**假绿的六种来源**，**没有这句话** —— 那是一次
**假引文**，已改）。它要防的是那一节里同一类东西（假绿）：判据报的「通过」说的不是这一次的内容。

具体到本件：回执是**上一次跑**留下的读数。没有提交哈希，一份旧回执与一份新回执长得一模一样，
于是「没跑过」会被当成「跑过了且通过」——**那就是假绿**。绑了哈希之后，门禁能直接判
「这份回执说的是不是**这一个**提交」：`装门禁.sh` 装的钩子在跑之前先比
`git rev-parse HEAD` 与回执里的 `提交哈希`，不一致就当场拒。

### 绑的是「跑那一刻的 HEAD」＝ 提交时是**父**提交

回执的 `提交哈希` 取的是 `git rev-parse HEAD` **在跑案例那一刻**的值（见 §三 字段表）。
钩子跑在**提交之前** ⇒ 那一刻的 `HEAD` 就是**本次提交的父提交**。**回执不可能写自身的
提交哈希**（自指：提交对象还没生成）。所以：

| 读法 | 含义 |
|---|---|
| 回执里哈希 = `X`，且「跑于 pre-commit」 | 那次跑验的是 `X` 的**子**提交**将要**包含的那棵树（工作区） |
| 本次提交只改回执 | 两者内容相同，无事 |
| 本次提交改了代码 | 回执验的仍是**本次要提交的内容**，而哈希写的是父 —— **不是「父提交的代码过了案例」** |

**钩子通过后把回执 `git add` 进本次提交**（第 ④ 步）：证据跟着提交走，提交完 `git status`
不残留这一行（此前不暂存 ⇒ 每次提交后工作区恒脏一行，是**假脏**，会掩盖真的脏）。

## 五 退出码与三类结局

| 结局 | 退出码 | 写回执吗 |
|---|---|---|
| 全部案例通过 | `0` | 写（每条一行） |
| 有案例失败 | `1` | 写（失败那一行带层 + 错误码） |
| **工具错误** | `2` | **不写** |

工具错误 = 案例文件坏了 / 语料读不到 / 接缝 `GetPlatformInfo` 被解析到别的声明上 / git 读数取不到。
**不写回执**的理由：回执的不变量是「失败必有结构化错误码」，而工具错误没有码；
硬写一行没有码的失败就把那个不变量破坏了 —— 后人再也分不清「被测对象坏了」与
「判据的输入坏了」（`判据的可信性.md` 第三节第 5 条：判据的解析器坏了也是假绿来源）。

**装载失败算案例失败（退出码 1），不算工具错误**：被验扩展的声明载不进来是**被测对象的缺陷**
（`README.md`：扩展缺了底座照跑 ⇒ 载入失败 = 该能力不可用），不是尺子坏了。
此时每个案例写一行同样的读数：层 = 内核、层内位置 = 装载、码取自 `载入错误` 的变体名。

## 六 跑案例的程序

`测试验证/案例/跑案例/`，独立 crate（包名 `v1-case-runner`），在根 `Cargo.toml` 的 `members` 里。
**零第三方依赖**：`Cargo.lock` 里除 `v1-*` 外没有任何包。

依赖四条，各有理由：

| 依赖 | 为什么 |
|---|---|
| `v1-adapter` | **装载与调用一律经它的公开面**（`装载` / `调用能力` / `能力清单` / `能力契约`）。本 crate 里**没有** `v1_loader::载入` 的调用点——有第二个就是第二条腿（拓扑判据 3） |
| `v1-contract` | 类型标签与号段类宽度（唯一来源是生成物，不许在这里再写一份数） |
| `v1-loader` | **只为**取 `建表错误` 的变体名（错误码登记按名查）。本 crate 没有 `载入` 调用点 |
| `v1-compiler` | 被验的扩展。只经它的 `GetPlatformInfo` 接缝取声明，**不 import 它的任何实现** |

文件分工（`main.rs` 是入口：只做路由，零实现）：

| 文件 | 做什么 |
|---|---|
| `src/main.rs` | 入口：`std::process::exit(跑::入口())` |
| `src/最小JSON.rs` | 案例文件的读写件（零第三方依赖；**不是平台能力**，是案例目录的载体格式） |
| `src/案例.rs` | 案例形状与读盘（唯一事实源是磁盘上的案例目录） |
| `src/装载声明.rs` | 经接缝 `GetPlatformInfo` 取被验扩展的声明 + 自检 |
| `src/错误码.rs` | 错误码登记（生成物 + 适配器当场取）+ 段位到层 |
| `src/回执.rs` | 回执行 · git 读数 · UTC 时间 · 追加 |
| `src/跑.rs` | 主流程：观测 · 比对 · 汇总 |

怎么跑（在仓库根）：

```sh
. 构建环境/进入.sh
cargo run --locked -p v1-case-runner
```

### 6.1 实测撞到的一处硬矛盾：接缝符号有两个定义

**底座也导出了一个 `GetPlatformInfo`**（`运行内核/装载入口/src/底座静态声明.rs::取平台信息`
当年手写的那条 `export_name` 属性），
与被验扩展的那个**同名**（`扩展根目录/原子支持库/编译器支持库/src/lib.rs::取平台信息`
上的同一条属性）。
同一个进程里静态链接两份，链接器只解析得到一个（**实测：扩展那份赢**）。后果：

1. `运行内核/装载入口` 自身的 `取平台信息()` 也被绑到了扩展那份上 ⇒
   `适配器::装载(v1_loader::底座声明())` = **`载入(标识串非法)`**（底座的身份自检
   `是底座自有声明` 拿扩展的地址比底座的地址 ⇒ 假）。**底座在这个进程里载不进来。**
   实测两个函数的返回地址逐位相同：`0x1030235b0`。
2. 所以跑案例的**声明根只放被验扩展这一份**（放底座反而整体失败）。
3. 取声明时**核对**「接缝的 C 符号」与「同源的 Rust 只读取用口」指向同一份静态声明；
   不等就**炸**（工具错误，退出码 2）—— 否则跑的是另一份声明，那就是假绿。

这是**既有件之间的一处矛盾**，不是本件能修的（`运行内核/装载入口` 不归本件）。原样报。

### 6.2 判据 ⑪-3 的扫描器把 match 分支当成调用点（假红，实测）

`构建装配/一键验证/一键验证.py` 的判据 ⑪-3 数「调用内核入口 `载入` 的处数」用的是**文本扫描**
（正则 `(?<![\w])载入\s*\(`），只排除 `fn 载入(` 与裸的枚举变体声明行。于是本件原来那行

```rust
装载失败::载入(内) => { … }
```

被数成了**第二处 `载入` 调用点**，报「多出来的就是第二条腿」——而本件**一个
`v1_loader::载入` 调用点都没有**（`grep -c 'v1_loader::载入'` = 0）。这是
`判据的可信性.md` 第三节第 5 条那一类（判据的解析器坏了 ⇒ 假红）。

处置：**本件改自身的写法**，用元组变体的字段名形式绕开文本形状（语义完全一样，实测 rustc 接受）：

```rust
装载失败::载入 { 0: 内 } => { … }
```

**没改判据**（`构建装配/` 不归本件）。这是**绕开**，不是修好——扫描器仍然分不清
「match 分支」与「调用」，下一个写 `载入(` 的人还会撞上。修法在扫描器（按语法而不是按文本数）。

### 6.3 变体名 ↔ 错误码：按名对齐，查不到就记 `已登记: false`

`载入错误`（判定六步）与 `建表错误`（`运行内核/统一注册表/src/建表.rs`）的**变体名逐字取**
`契约声明/错误码表/<码>.json` 的 `名称` —— 码表是名称的唯一登记处，按名对码是运行期把变体换成码的唯一办法。

**查不到时不许替它编一个码**：记 `已登记: false`，把缺口暴露在回执里（`错误码.已登记` 是旁路项，
见 §二）。契约写着「未登记的错误码不许抛出」⇒ 记 `false` 就是一条缺陷证据。

变体与码的对照关系**不在这里复述**（复述必漂）：它住在 `测试验证/案例/跑案例/src/错误码.rs::载入错误名`
与 `::建表错误名`，一处一个变体一行。

**改名前先看 `契约声明/作废号表.json`**：号**只增不改** —— 改语义要**加新码 + 作废旧码**，不许原地改名。

## 八 门禁怎么装

`.git/hooks/pre-commit` **不进版本库**，所以版本化的那一件是安装脚本：

```sh
sh 测试验证/案例/装门禁.sh
```

它把钩子装上去（**幂等**：认标记 `# 装门禁标记`，是自家钩子就整体重写；不是自家钩子就
**拒绝覆盖**，别人的钩子不许被踩掉）。钩子的**四步**行为：

1. **先比哈希**：读 `git rev-parse HEAD`，与回执**最新一行**的 `提交哈希` 比。不一致就当场
   说清「最新那份回执不是这个提交的 ⇒ 本次必须重跑（旧回执不算数）」——这一步让
   「回执是旧的」与「代码坏了」分得开（本件 §四）。
2. **跑全部案例**：跑案例的程序自身把读数追加进 `运行回执.jsonl`。
   **任一失败即拒提交**（退出码 1；工具错误退出码 2 也拒，且那一档**不写回执**）。
3. **复核**：新写出的回执必须绑在 `HEAD` 上，否则说明回执写坏了（判据坏了）⇒ 也拒。
4. **暂存回执**：`git add 运行回执.jsonl` —— 证据跟着提交走，提交后工作区不残留一行。
   （回执里的哈希是**父**提交，读法见 §四。）

钩子**只判「拒或不拒」，自身绝不 `git commit`**（第 ④ 步的 `git add` 只**暂存**，不提交）。

## 九 明确不做

| 不做 | 为什么 |
|---|---|
| 不做「案例专用断言语言」 | 判据只有封闭枚举的那几个变体：没有变量、没有表达式、没有运算符、不能组合。加一种判据 = 加一个变体 = 改实现；**加不出「写一条新断言」这回事** |
| 不把期望值抄进代码 | 期望值只有一个来源：案例目录里的 `期望.json`。代码里没有任何一个具体能力编号参与判定 |
| 不做「跳过失败的开关」 | 没有「跳过」这一档。案例文件坏了是**工具错误**（退出 2，不写回执），不是「跳过这个案例」 |
| 不在跑案例的程序里再写一遍装载或调用 | 装载只有 `适配器::装载`，调用只有 `适配器::调用能力`。再写一遍就是第二套实现 |
| 不用「重跑一次看看」当处置 | 那是把假红变成运气（`判据的可信性.md` 第四节） |
| 不把空集算成通过 | 案例根下 0 个案例、步骤 0 步 ⇒ **工具错误**，不是通过 |

## 十 「运行结果」的判据形状（#101 的落法 · 2026-09-27）

**要解决的问题**：计算器那类例程要期望的是**运行结果**，而上面那五个产物判据
（`不判` / `空槽` / `错误槽` / `非空字节集` / `逐字节等于文件`）里**没有一个**说得清
「谁输出、怎么表示」。裁决已下（`项目文档/决策记录/2026-09-27_待裁九项按老仓设计哲学裁决.md`
裁决 8），本节把裁决**落成形状**——三条，逐条都可判。

### 10.1 载体 = 返回值槽（三条形状）

| 形状 | 是什么 | 判法 |
|---|---|---|
| **① 载体是返回值槽** | 「运行结果」= **能力返回值槽里的字节集**（`能力契约.返回类型` = 5 时那一段） | 案例期望只许用 §1.2 那五个产物判据表达；判据本体读的是 `适配器::调用能力` 交回的**槽**（`观测.rs::观测产物`） |
| **② 标准输出与退出码是旁路** | 调用方**看不到**被测能力的 `stdout` / 退出码，也不许拿它们当结果 | 期望里出现「标准输出 / stdout / 退出码 / exit code」这类键即**旁路** ⇒ 案例**工具错误**（退出 2，不写回执）——与「案例文件坏了」同等，因为它是**用错了载体** |
| **③ 纯确定性必须写关键值断言** | 老仓 9.4①：相同显式输入 ⇒ 相同输出，**必须写关键值断言** | 纯确定性能力的期望不许停在 `非空字节集`（那只说「有东西」）；**必须**写成 `逐字节等于文件`（或等强度的关键值判据）。判据：⑪-3 那条扫描器同源的形状——**能力类别已登记、且类别属「纯确定性」档**的案例，其期望用 `非空字节集`/`不判` ⇒ 红 |

**为什么②是「工具错误」而不是「案例失败」**：第 7.4「**统一调用接口铁律**：所有能力无论对外暴露
还是内部被调用，**只允许走 `调用能力(能力id, 参数)`**」＋ V1 宪法 3（跨边界只有一条路）。
期望里写 `stdout` = 给这条链**另立一个出口** —— 尺子坏了（拿旁路当被测面），不是被测对象坏了。
同 §五：工具错误**不写回执**（回执的不变量是「失败必有结构化错误码」，工具错误没有码）。

### 10.2 「关键值断言」在案例里的**唯一现有形态**

**不新造判据变体**（§九 第一条：加不出「写一条新断言」这回事）。关键值断言就用**已有**的
`产物判据::逐字节等于文件`（`跑案例/src/案例.rs`）：把**期望的字节**落到案例目录里一个文件，
期望写 `{"判据":"逐字节等于文件","文件":"<那个文件>"}`。于是：

- **正向形状**（计算器那类例程将来长这样）：
  `输入.程序文本` + `输入.期望结果`（期望的返回槽字节）+ 期望里
  `{"产物":{"判据":"逐字节等于文件","文件":"输入.期望结果"}}`；
- **反向形状**（把断言写坏 ⇒ 必须报红）：同一份输入，把 `输入.期望结果` 的第一个字节改掉，
  或把那一步的期望降级成 `非空字节集` —— 前者报**逐字节不符**（`判定.rs::首处差异` 给偏移），
  后者由**本节 10.1③ 那条判据**报红（纯确定性不许只写「非空」）。

**读数**（本节的两条样本 · 可复跑）：

```sh
python3 测试验证/查案例形状.py            # 查全案例根的三条形状（违反 + 未判，都带读数）
python3 测试验证/查案例形状.py --自测      # 反向样本（内存里造坏期望 ⇒ 必须报红）
python3 测试验证/查案例形状.py --样本      # 落盘样本：真案例 `往返逐字节` 演正反两端
```

**读法的诚实口径（别把「通过」读大）**：本件**不猜**哪个能力是纯确定性的（那要有语言与
运行时的形状 —— 正是 #101 说的缺件）。它判的是**可判的那一半**：**能指出关键值**时才成立
（能指出 = 案例目录里备了 `输入.期望结果`，或期望已写 `逐字节等于文件`）。于是现有五份案例
的读数里会有**未判**（`反解真容器` · `往返逐字节` 第 1 步 · `真程序文本` 第 1/2 步）——
那些案例证明的是「不假成功 / 往返一致」，**还没到「算得对」那一步**，所以如实报未判、
**不算通过**（`判据的可信性.md` 第二节）。计算器那类例程落地时才该备 `输入.期望结果` 并写
关键值断言。

`形状检查/` 是那个检查器的实现（`形状.py` 判 · `常量.py` 一处写死键名与白名单 ·
`自测.py` / `样本.py` 配样本）；`查案例形状.py` 是路由（零实现）。

### 10.3 与 §七 的关系（计算器什么时候能真进来）

本节只把**判据形状**立出来 —— 计算器要真进来还缺 §7.2 那张表里的 **1106 编译**（保留项）。
两件事分开：**形状**是本件的事，**实现**是语言主线的事。1106 落地那天，按 10.2 写期望即可。
