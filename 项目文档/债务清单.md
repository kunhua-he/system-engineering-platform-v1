### 候选装载预检与冷启动效率

- 历史阻塞：当时预检把10秒效率目标当作失败截止；正式候选两次没有在该窗口就绪。独立冷缓存样本真实启动9.902秒；旧10.199秒读数与本次不是同一次试验，不能混成一条基准。
- 根因取样：44个扩展候选、33个支持库。冷样本主线程8,568个样本中89.7%位于`dlopen`、87.4%在dyld `fcntl`调用栈；同一制品复用33个缓存文件后启动0.613秒。证据支持动态库装载/文件状态是主要热区，不足以断言`fcntl`具体系统语义，也未将缓存写入和dyld成本拆开。
- 预算处置：已将候选预检限时改为项目既有90秒失控护栏，10秒继续作效率报告线；放宽等待不等于性能根因修复，效率超线也不能改写为能力失败。
- 阶段读数（已落地）：`准备执行映像/映像准备.py` 在真实生产启动链上按单调时钟切三段并随准备结果返回 `阶段读数`——`首字节秒`（exec + dyld + 底座自身装载）、`扩展装载秒`（首个到最后一个「装上」之间，逐个 dlopen 扩展库）、`就绪收尾秒`（最后一个「装上」到「监听 127.0.0.1」），并给 `装上扩展数`。
- 读数实测（制品 b504cff38ddd-85440def97e05164，热缓存，两轮）：总计 0.592 / 0.555 秒 = 首字节 0.004 / 0.003 + 扩展装载 0.588 / 0.552（35 个）+ 就绪收尾 0.000。结论：热态耗时几乎全在扩展逐个 dlopen，首字节与就绪收尾可忽略。
- 冷态口径：冷缓存 9.902 秒样本与 89.7% 在主线程 `dlopen` 的采样一致指向同一处热区；本机不再人为制造冷缓存（需清系统页缓存），升级线索是「减少启动时要 dlopen 的扩展数或预打包」，不是放宽预检限时。
- 隔离候选历史验收：此前候选`GET /接口`及图任务提交、查询、释放、释放后查询通过；PID、端口与自建运行根已按归属停止/清理，正式口未动。该HTTP证据不包含本次源码修改后的当前候选验收。
- 当前源码定向验证：部署所有权8项通过，含真实轻量进程/锁交接；本轮效率测试须另证预检使用90秒护栏。模型、浏览器、组件与工作区业务HTTP仍未覆盖。
- 判据：`python3 构建装配/上线切换/上线所有权验证.py .`；正式候选命令仍为`python3 构建装配/上线切换/上线切换.py 装载 b504cff38ddd-747642d013d685de`，不得以局部测试代替。
超过五秒本身不再是缺陷判据；历史和当前测量必须按实际路径分开报告。

### 可靠存储与恢复（阻断，部分保存失败需统一收尾）

- 已修源码：运行态日志传播打开/写入/同步错误；登记及执行意图保存失败不会进入叶子；完成保存失败保留内存执行事实并阻止新准入；坏行与未知阶段拒绝恢复；释放与淘汰先写墓碑再删内存；同根唯一写者持文件锁。最终写者析构先显式解锁再关闭，避免 macOS 并行 Command fork/exec 的继承窗口造成重锁假失败。
- 新增实测缺口（仓外受控探针）：第二根启动保存失败时，第一根尚未进入叶子、叶子调用数为0，却已出现执行中阶段及开始时刻；停机合流后仍不收口。完成保存故障与真实活根并存时实例确实等待活根，开闩后才返回未确认。
- 静态边界：`任务表.rs::阶段`在检查节点前遇存储错误即返回未确认，绕过活分支应报收尾中的判定；该私有路径未做接口实测，不写成 HTTP 事故。
- 已施工：`图驱动.rs::冲刷`先把工作项纳入实例内队列再写执行意图；保存失败后统一收束待执行项与仍可确认未执行的就绪节点，使用现有内核完成边界闭合，提交路径统一通知等待者；真进入叶子后才写开始时刻。`任务表.rs::阶段`不再因存储故障抢先报未确认，仍有活节点时保持收尾中。
- 仍保留的边界：存储故障后的内存记录可能保留最后一次成功持久前的执行阶段；它不等于叶子已执行。未确认最终结局由存储故障事实主导，不伪造能力失败或未知。
- 反证：新增第二根启动保存失败、全队列收束、依赖后继跳过及无叶子调用测试；修前退出101，修后该用例通过。仓外活分支探针已证真实阻塞等待与开闩后未确认；当前包回归通过，但活分支与任务表公开接线仍需候选/HTTP复验。

### 未知与资源退场（重要，提供者异常须分别反证）

- 证据层：本节已对照当前集成树源码；尚未模拟远端任务失联或进程回收失败，不把控制流缺口写成活执行重入事故。
- 已有保护：`进程池/域句柄定义.rs::保证在按前提`与`进程池.rs::崩溃重拉`在新启动前核验旧格的`回收已确认`，未确认即拒绝替换；`回收.rs::移除一域按回收`未确认不摘格。`击杀并确认退出`仅在`try_wait`确认退出后归还进程额度；宿主调用租约归还只减在途，不等于释放进程额度。
- 资源分层：图键是实例、图任务、代次与节点标识，调度器逐图持有；它不是跨图的真实服务句柄锁。跨进程域事务锁、数据库连接锁和模型活生成许可仍各有既有保护，不能据图租约释放推断这些保护失效。
- 进程池失步（已收口）：`帧收发.rs::废弃失步通道`改为按收尸结论分档——`回收已确认` 为假一律报新增的 `0039 退场未确认`，不再把「没确认」报成 `0034 通道断开`（后者说明写的是「确认过进程没了」），归属与进程额度一律保留，重拉继续由 `保证在按前提` 的 `回收已确认` 闸挡住。两条定点用例：`收尸未确认报未确认退场且保留归属`、`收尸确认后沿用按存活判错`；适配器包 254 项通过、0 失败、3 项原有忽略。
- 进程池析构（已收口）：`进程池::drop` 逐格读回收结局，未确认即打一行读数（域标识 + 结局），不再一声不响收场。
- 浏览器失步（已收口）：`会话状态` 新增 `失步` 位，收发失败即置位并弃连接，后续指令立即报 `7004 连接失败`；会话仍占归属（Chrome 进程与临时目录都在），只能经 `关闭会话` 收掉再重建。公开实测（制品 b504cff38ddd-c18b24cbb439a7d8）：创建→导航→读标题地址正常；外部强杀 Chrome 后两次读页面分别 1 毫秒、0 毫秒返回 7004（旧行为会在 10 秒预算里空等），`关闭会话` 为真，关闭后转 7002 会话不存在，浏览器进程与候选端口零残留。
- 浏览器连接半死（已反证，2026-11-07 · 制品 7d638589c1f9）：主进程活着但不回帧（SIGSTOP 冻住 Chrome 主进程）时，读页面**不会永久挂死**——10,002 毫秒后返回 `7004`，恢复进程后再读**仍是 7004**（失步不可自愈，只能关闭会话重建），`关闭会话` 为真且临时根与进程零残留。读数含义：10 秒是这条链的连接等待上限，不是「卡死」；要更快发现半死，得把上限做成可配（目前未做，属优化项不是缺陷）。
- 浏览器目标页消失（**已反证**，2026-11-07 · 制品 7d638589c1f9）：入口不是命令行里的 `--remote-debugging-port=`（那里取不到），而是会话临时根下的 **`<会话根>/v1-browser-*/DevToolsActivePort`**——首行就是真端口。用它 `GET /json/list` 找到页面目标、`GET /json/close/<id>`（HTTP 200）关掉目标页后，读页面**1 毫秒**返回 `7004`（不空等、不静默成功），再读一次仍是 `7004`；`关闭会话` 为真，Chrome 进程与临时根零残留。附带反证：单杀一个 `--type=renderer` 子进程**不算**目标页消失（一会话下并行多个渲染进程），那条构造无效，别再当反例。

- 模型远端（口径 = 已知限制，不立债务）：取消只置本侧标志并关本侧流；远端是否停止由提供方决定，底座不做远端取消确认，也不为此加第二套控制通道。对外只保证「本侧退场已确认（`is_finished`）/未确认（返回假、归属保留）」。要远端也停，由部署方在服务端设断流即停（OpenAI 兼容实现普遍如此），底座不代其承诺。
- 向量与重排（已核，无需退场位）：`向量与重排.rs::发送` 是同步阻塞调用，无跨调用句柄，失败即返回上游失败；不存在「已发未回执」的挂账对象。
- 施工：保持现有正常重拉挡板，按旧工作格与旧代次上送退场事实；未确认资源交既有回收所有者继续持有，不另建图资源池或第二状态机。确认直接子进程退出不能外推整组后代均已退出。
- 本地同步调用已返回或展开后才判超预算，该次栈上执行已退出；预执行拒绝和未发业务的锁等待超时不需要虚构退场等待。

### 释放、淘汰与持久判重（重要）

- 事实（已收口）：释放与淘汰走同一口 `任务表.rs::移除` —— 先按任务号写 `追加释放(任务标识, 请求标识)` 墓碑，落盘成功才从内存摘记录并删判重键；`适配器接线.rs::释放任务` 的重启快照支路同样先写墓碑再删快照与幂等。写盘失败一律不摘记录（返回假），不出现「内存没了、盘上还在」。
- 反证（真实 HTTP，制品 b504cff38ddd-85440def97e05164，隔离运行根）：首提交取号1 → 释放为真 → 查询转「任务不存在」；同键再提交取号2（≠1）；重启后号1/号2 均「任务不存在」，同键提交仍回号2（判重跨重启成立）；再释放号2、重启后同键提交取号3（墓碑跨重启清键）；连发 140 个任务触发容量淘汰，重启后号3「任务不存在」（被淘汰者不复活）、最近任务仍可查；淘汰后同键提交取号144、释放后再重启提交取号145，发号只增不回退。140 个提交总耗时 2.5 秒。
- 附带修一条口径缺陷：`运行态日志.rs::对账` 原先把「无未知」一律写成已取消，导致**全节点已成功**的任务（进程在写任务级终态前被停）重启后报已取消。现按已确认节点收口：有未知⇒未确认；无未知但有失败节点⇒失败；全成功⇒成功；其余⇒已取消。新增用例 `对账全节点成功收成成功`。

### 独占写者与当前态压实（重要）

- 事实：同根跨进程写者已用终身文件锁挡住；包级红的具体充分机制已独立复现：macOS 上另一线程经普通 `Command::status()` fork/exec 时，文件锁 FD 的继承窗口会使持有者 `drop(File)` 后紧接着重开 `try_lock()` 仍短暂 `WouldBlock`，即使 FD 已设 `CLOEXEC`。无子进程对照31673次为0，普通并发两轮分别16/64129、11/27689，最终所有者先显式 `unlock()` 对照27817次为0。原包级红瞬间没有FD持有者记录，故只称机制复现、不能断言追溯锁定特定子进程。
- 修法：任务落盘仅让最终独占写者守卫持锁；其析构先显式 `unlock()` 再关文件，保证构造失败与最后引用释放路径一致。不在clone析构提前解锁，不以 `try_lock` 重试藏错。
- 反证：新增确定性继承描述符用例修前退出101、修后通过；同根第二写者仍拒、显式释放后立即接管通过；原包级红用例与写者跨进程用例通过。此轮没有串行化或降低并发。
- 压实：超 4 MiB 在启动时按当前态原子重写（账本头载最大号 + 每个活任务最新一态），丢弃被覆盖的历史行与已释放任务行；失败只告警不阻断启动。公开实测 50003 行 7,613,793 字节 → 2 行 319 字节，已释放旧任务仍查不到、发号不回退、同请求标识跨重启同号、在留任务重启后仍在。

## 五、不为销账新增的功能

- 第三档请求中止：保留现有放弃与等收口。内核已有协作取消原语，不等于图执行体已打通；没有消费方就不加一条假通道。
- 未知自动自愈：保持未知正确；先修资源与凭据混账，不做自动重发。核实凭据后再由业务决定是否重放。
- 远端取消确认：取消只关本侧流，远端停不停由提供方决定；不加远端控制通道，也不把「本侧已退场」说成「远端已停」。
- 字段级输入引用：当前冻结合同是整槽，原先已否决字段引用，不把未实现误登记成待修缺陷。
- 生命周期通知子号：四个常量在单处定义且有消费者，未进声明 JSON 不等于功能失效；外部需要独立生成协议时再冻结。
- 保活定时器与大结果句柄：导航明确尚未承诺；没有真实需求不扩能，不以功能未实施给已有回收缺陷免责。
- 第二传输入口（大返回走二进制直传）：既有结构化编码已实测够用——8 MiB 文件经 `字节集` 出 HTTP 200、46 毫秒、JSON 11,185,258 字节、base64 还原与原文件逐字节一致、膨胀 1.333；1/4/8 MiB 三档均一致。未登记引用类型不被任何能力声明使用（扫全仓能力声明只出现 1/2/3/4/5/6/7/100/101/103），编码器对未知标签直接拒收。没有真实消费方，不新增第二条腿。
- 节点级自动重试：无当前调用需求；结果未知时尤其不能把可重试标记当幂等承诺。
- 兼容双路径：不保留；迁移后只留唯一执行口和唯一事实源。
