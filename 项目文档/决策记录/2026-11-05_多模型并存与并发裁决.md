# 多模型并存与并发请求的裁决

> 用户提的场景（原话）：不同模型应该分配不同端口；有时候 LLM 需求不高的用 13B，
> 也可能同时放一个 26B 或 32B 的等待调用；**如果同时请求多个模型，这个是如何裁决的**。
> 机器扛得住，这也算常规业务场景。

## 一、现状实测（真调正式口 43110）

同时拉起三个模型服务：

| 项 | 结果 |
|---|---|
| 服务句柄 | `900002` / `900003` / `900004` 三条并存 |
| 监听端口 | `40002` / `40003` / `40004` 各自独立 |
| 进程 | 三个独立进程，互不影响 |
| **推理许可** | **只有第一个拿到 `800001`，第 2、3 个直接「排队超时」** |

结论：**端口分配、服务表、进程共存都已经是多模型形态**；
**卡死点在推理许可 —— 全局只有一把锁**。

## 二、裁决（定案）

### 1. 端口：一个模型一个端口，互不复用

- 传 `0` = 底座自动分配，范围 `40000-49999`，同时避开「已在监听」和「服务表已登记」两种占用。
- 传具体端口 = 照用；被占就报错，不偷偷换。
- `{端口}` 占位符让模型进程知道落在哪个端口 —— 自动分配后它也得知道。

### 2. 共存：服务表允许多条，谁都不挤谁

- 一个模型 = 一个服务句柄 + 一个端口 + 一个进程。
- 拉起、查状态、释放都按服务句柄走，互不串扰。
- 待命（已经起来、没人请求）**不占许可**，可以长期挂着等调用。

### 3. 许可：从「全局一把锁」改成「按服务分槽」

这是要改的核心。

| 层面 | 现在 | 改成 |
|---|---|---|
| 持有者 | `Option<持有记录>` 全局单槽 | `HashMap<服务句柄, 持有记录>` |
| 排队 | 一条全局队列 | 每个服务一条队列 |
| 跨模型 | 互相锁死 | **各自独立，可同时推理** |

语义说清：

- **同一个模型**的并发请求 → 排队。理由是同一进程共享一份 GPU 上下文与 KV 缓存，
  放两个请求进去只会互相拖慢，还读不出是谁在吃算力。
- **不同模型** → 各走各的许可，同时跑。理由它们是各自独立进程，
  GPU 由驱动调度显存与算力，底座不该替驱动做串行决定。

### 4. 内存预算：拉起之前先算，不够就拒绝

- 估算需求 = 模型文件大小 × `1.15`（权重 + 上下文 KV 系数）+ 固定开销。
- 可用内存取 `vm_stat` 的空闲 + 非活跃，再打八折当安全余量。
- 不够就回 `资源受限`，并在错误说明里写清「要多少、还剩多少、可以先释放哪个」。
- 绝不允许「先拉起再说，撑爆了让它 OOM」—— 那会把整台机器拖慢，且事后查不出是谁做的。

### 5. 等待与超时：3 秒拿不到就明确报忙

- 全仓超时硬顶 5 秒，等待类参数封顶 3 秒（顶到 5 秒会先被内核判超时）。
- 3 秒内拿不到许可 → `2511 排队超时`，由调用方退避重试。
- 不静默降级成「没排队直接跑」，也不无限等。

### 6. 常驻与回收

- 待命不占许可，但**占内存**。所以「常驻哪几个」由内存预算兜着，不靠人工记。
- 释放按服务句柄走：句柄释放 ⇒ 进程退 ⇒ 端口回收，三件一起收干净。

## 三、典型场景走一遍

需求不高的用 13B，同时挂 26B 和 32B 等调用：

```text
底座 43110
├─ 901001  Qwen3-13B      端口 40001  待命中（常驻，不占许可）
├─ 901002  Qwen3-26B      端口 40002  待命中
└─ 901003  Qwen3VL-32B    端口 40003  推理中（持许可 800003）
```

- 这时来个 13B 请求：拿许可 `800001`，立刻跑，**不排在 32B 后面**。
- 再来个 13B 请求：拿不到 `800001`（13B 那个许可正被占着）→ 排队等 3 秒或报忙。
- 32B 跑完放掉 `800003`，26B 来请求就能直接拿，不用等 13B。

## 四、不做什么

- 不做「按 GPU 利用率来决定放不放行」：利用率冲高是推理的正常现象，不是判据。
- 不做全局串行队列：那等于用一把锁把整台机器的并行能力废掉。
- 不做按端口号或进程名归因：归属一律认服务句柄。
- 不做后台定时器扫租约：租约过期只在下次申请时顺手回收。
