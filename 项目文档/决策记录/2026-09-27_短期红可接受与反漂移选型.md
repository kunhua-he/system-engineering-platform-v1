## 一 裁决一：**短期红可接受，不逐点验证**

原话：「暂时红无所谓，主要是能快速做好，后面再拼接也行，人类的想法是允许短期亏损的。等全部做完，再一次性维修红的就行了，**不需要做一点，验证一点**，这样子效率太低。」

### 规则

| 改 | 不改 |
|---|---|
| **收口节奏**：一批落地 → **一次性**跑门禁 → 一次修完红 | 判据的**真实性**（读数不许编、不许粉饰） |
| **腿的纪律**：改动做对，门禁**跑一遍**，红了**如实报** | 单条命令的**五秒硬顶**（宪法级，无例外） |
| **提交节奏**：允许中间提交带着红（只要如实写在提交信息里） | 「纯搬家不许顺手改逻辑」 |
| **验证频率**：按**批**验证，不按**步**验证 | 「公开面逐字不变」 |

### 为什么这不是「放弃验证」

它换的是**验证的粒度**，不是**验证的有无**：
- 红**仍然要报**——「暂时红」的前提是**红是已知的、被记下来的**。不报的红是假绿。
- 「一次性维修」的前提是**维修清单在手里**：每条腿回来必须给出「我改了什么 · 哪条门禁红了 · 为什么」。
- 判据三元读数（真 / 假 / **未判**）不变：**空集是「未判」，不是「通过」**。

### 反面样本（不许这么做）

- 「反正是短期红」⇒ 把没做完的报成做完了。**那不是短期红，那是假绿。**
- 「反正是短期红」⇒ 不跑门禁就报绿。**没跑过的门禁，读数只能是「未判」。**

## 二 裁决二：**选型判据 = 哪种形态不容易漂移**

原话：「什么代码不容易漂移就用什么代码。代码类型无所谓了。主要是好维护就行。」

⇒ 选型时**先问「它会不会漂」**，再问语言、性能、风格。

### 漂移的形态与对策（本仓已有实测样本）

| 漂移形态 | 实测样本 | 不漂的形态 |
|---|---|---|
| **手抄镜像**（同一事实抄两处） | `README.md` 手抄 crate 个数（写 9、实际 13）；`扫实现.py` 文件头注写死「24 处 / 16 个」而实测 50 / 41 | **指落点**：成员清单以 `Cargo.toml` 为准；计数指 `--读数` |
| **条目里写「现在是什么」** | 台账 #4 写「505 处 / 45 文件」，实测已 539 / 57 | 写**量法**（按哪个口径数），不写数 |
| **注释里写台账号** | 全仓 158 处「台账 #N」，其中 123 处的号已不在册 | 引 `决策记录/… §节名` 或 `路径::符号名` |
| **两份实现同一件事** | `一键验证.py::前端逻辑模式` 与 `前端呈现/网页应用/自检.sh::PATTERN` | **一份实现**，另一处调它 |
| **生成物手改** | — | 生成物禁手写（`代码形态分工.md` §3）；改源头重跑 |

### 一句话判据

> **同一件事实只许有一个落点；其余地方只能「指过去」，不许「抄一份」。**

**代码类型无所谓**：Rust / Python / JSON / 生成的常量表，哪个能把事实**收在一处**就用哪个。
本仓已有的好样本：`契约声明/*.json` → `声明数据.rs` 是**生成的**；`行数基线.json` 是**量出来的**。
坏样本：文档里复述代码里的数。

## 三 与旧纪律的关系（哪条被替换、哪条还在）

| 旧纪律 | 现在 |
|---|---|
| 「一批一收：腿全落地 → 全绿 → 提交」 | **改成**：腿全落地 → 提交 → 一次性修红 |
| 「每条腿做完要 6 条门禁全绿才报」 | **改成**：跑一遍，红如实报，不必追绿 |
| 「不许在腿在飞时改存量」 | **保留**（一腿一工作树已经把它变成「不撞车」而不是「不并行」） |
| 「读数一律带退出码」 | **保留** |
| 「判据三元读数：空集是未判不是通过」 | **保留** |
| 「五秒硬顶，无例外」 | **保留**（宪法级） |
