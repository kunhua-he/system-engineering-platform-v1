# 组件句柄式交互裁决（2026-11-02）

## 一、这条裁决解决什么

网页界面支持库（`4928 渲染组件树`）出的是**死 HTML**：一次渲染，一次性文本。
组件渲染出来之后没有身份，谁也找不到「刚才那个表格」；想让它排序、翻页、收起来，
只能让页面里的脚本原位计算，或者让业务项目在页面里另写一段 JS。

后果有三条，都是架构问题，不是功能问题：

- 页面成了第二处算力：排序在前端算、分页在前端切，底座不知道它渲染过什么。
- 页面成了第二条调用腿：脚本自行发请求、自行拼回执，绕开唯一调用入口。
- 业务项目被迫写前端逻辑：V4 本该只出声明、传参、贴返回。

## 二、定下来的形态：组件有句柄，操作传参给句柄

对齐大语言模型支持库现成的范式（提交任务拿任务句柄 → 读取 → 取消 → 释放），
组件按同一套路走，不多造机制：

- **拉起**：`4928` 每渲染一次，把声明里需要交互的组件登记成**组件实例**，
  给每个实例签发一个**组件句柄**（走 `0006 句柄` 类型，跨边界只是数值）。
  渲染出的节点带组件句柄，页面据此知道「我操作的是哪一个」。
- **操作**：`操作组件(组件句柄, 操作名, 参数对象) → HTML 片段`。
  排序、翻页、展开、收起、选中、改名，都由底座按实例里存的声明与当前状态重算，
  只渲染这一个组件，返回片段。**排序是底座算的，不是浏览器算的。**
- **读状态**：`读组件状态(组件句柄) → 状态对象`（当前排序键、页码、展开项、选中项）。
- **释放**：`释放组件句柄(组件句柄) → 真/假`，幂等；不存在的句柄返回假，不报错。

页面侧只剩一件事：把「句柄 + 操作名 + 参数」交回宿主（V4），宿主调能力、
把返回片段替换到该句柄所在节点。页面不含任何业务算法。

## 三、三层分工（唯一口径）

- **底座（公共能力层）**：组件的结构渲染、组件状态、操作算法、句柄登记与回收。
- **V4（业务层）**：页面声明（JSON）、传参调能力、把返回片段贴回页面。
- **浏览器**：只有一份公共引导脚本，负责把节点事件转成一次宿主调用；不含算法、不发业务请求。

判据一句话：凡是「算」的都在底座，凡是「说是什么」的都在 V4，浏览器只做搬运。

## 四、句柄的归属与回收

- 每个组件实例登记四样：组件句柄、所属页面/会话标识、节点路径、最后访问时刻。
- 回收按**归属**杀，不按端口/进程盲杀：会话结束或页面卸载时释放该归属下全部句柄。
- 超时未访问的实例按归属批量回收，回收后旧句柄一律按「句柄无效」处理，不复用。
- 组件句柄永不回收再用，与能力号同一原则：用了就废，避免旧页面操作到新实例。

## 五、今天这批前端脚本怎么处置

- **表格排序 / 分页**：退掉前端算法，改为 `操作组件`（底座算，返回片段）。
- **表单提交**：已退回原生 form，提交到调用方路由，由调用方调能力；底座不自带发请求脚本。
- **提示 / 确认 / 右键菜单 / 拖放**：属纯观感与事件转交，保留为声明字段；
  但触发后的动作一律交回宿主，不在页面里办业务。
- **窗口位置尺寸**：仍归 V4 业务态（一机一库），经底座读写库能力落地，不在底座留产品观感。

## 六、号段

网页界面支持库当前只占 `4928`。本裁决要求扩容后新增：

- `4929 操作组件`
- `4930 读组件状态`
- `4931 释放组件句柄`

取号先进 `包声明.json` 的能力号段，再落能力声明；号段只往后长，不回收、不迁移。
