## 一 号段归属：不迁号，域语义以落位为准，取号按本库声明段

**裁**：能力号**永不回收、永不迁移**。号段图 1000–6999 只作粗粒度分区（按「来源 + 域」划大块），
库与段的语义对不齐时**不改号、不改段**，改为两条写实口径：

1. **取号以库自身为准**：新增能力必须落在该库 `包声明.json` 的 `能力号段` 之内（现测：33 个支持库全部满足，
   无一号越界）。号段图不承担「按库点名」的职责 —— 它只说清每一大段归谁，不说某号属于某库。
2. **历史域错位登记在案、不迁**：以下五处是既有落位，语义域与所在大段不完全一致，**保留原号**：

| 库 | 现落段 | 号段图对该段的语义 | 实情 |
|---|---|---|---|
| 数值计算支持库 | 1324–1335 | 1000–1999「核心支持库 · 语言自身」 | 属三方封装，不是语言自身 |
| 文本计算支持库 | 6301–6302 · 6801–6802 | 6000–6999「界面与呈现」 | 实为文本/代码语义，且跨了两个子段 |
| 代码解析支持库 | 6305–6310 | 同上 | 实为文本解析 |
| 大语言模型支持库 | 2501–2511 | 2000–2999「系统与环境」 | 实为三方封装 · 模型调用 |
| 浏览器支持库 | 7001–7099 | 7000–7999「模块（扩展）」 | 支持库落在了模块段 |

- **为什么不迁号**：号一旦回收或改义，历史制品、`作废号表`、`冻结登记`、全仓调用点、组合模块库的程序文本
  会同时失效；换来的只是表面整齐，代价是全链路回归。编号的价值在「永不变」，不在「排得好看」。
- **被否决的做法**：① 把号段图改成一库一段的全表 —— 底座不认识扩展（判据 ⑯），逐库点名等于让底座持有一份扩展名册，
  第二事实源；② 按语义把上面五处挪到大段里去 —— 违反「编号永不回收」，且不产生任何功能收益。

**验收**：`扩展根目录/原子支持库/*/包声明.json` 的 `能力号段` 覆盖本库全部 `能力声明/*.json` 编号（现测 33/33 覆盖、界外 0）。

## 二 能力准入：先扩字段，后开新号；三条硬门

**裁**：新增能力前必须依次过三道门，任一门能过就**不许**加号：

1. **能扩字段就不加能力**：现有能力能否用 `外观属性` / `形态变量` / `筛选` / `放大` 这类声明字段表达？
   能表达就不加叶子、不加能力（4928 的组件树就是这么长出来的）。
2. **能并进既有库就不开新库**：同域已有库能承接就并进去；新库只在「域全新且不可归属」时才开。
3. **加号必须过重复审计**：按 `开发文档/临时文档/2026-11-02_A04重复能力审计.md` 的口径逐条核
   「真重复 / 门面层 / 提供者层」，机械按名字合并被否决（同一能力可能合法地存在门面与提供者两层）。

**淘汰线**：零调用方的能力不自动删 —— 先看它是不是「已登记但无调用」的通用件；确有调用方的能力不因「长得像」
合并。删除走 `作废号表` 登记，号永不回收。

**被否决的做法**：设一个「能力总数上限 N」的硬数字护栏 —— 上限会逼着把有调用方的能力硬合，也会挡住真正的新域；
准入看的是「能不能不加」，不是「已经有多少」。

## 三 单点能力的自保（底-A26 · A27 · A28 的落地口径）

1. **4928 是唯一界面腿**：V4 全部界面压在这一个能力上 ⇒ V4 启动时必须先探活（真实调用一次带最小树的 4928），
   探活失败走 V4 侧错误页，不让用户看到空白界面。底座侧不新增「自检能力」（那会变成第二个入口）。
2. **容量护栏可配**：`网页界面支持库/src/组件树.rs::树最大深度` 与 `::树最大节点数` 现在是常量；
   V4 确有更深页面时，改为「能力参数可覆盖、缺省取常量」，参数名与常量同名，不新增能力号。
3. **字段按域分组**：`外观属性` 已含 11 个数值 + 3 个枚举 + 6 组形态变量，再加字段必须归入既有域
   （尺寸 / 颜色 / 间距 / 形态 / 状态），一个域内凑不出归处才允许新开一组；禁止继续平铺成第二个 CSS。

## 四 重复能力的逐组裁法（底-A04 · 六组审计结论）

审计正文：`开发文档/临时文档/2026-11-02_A04重复能力审计.md`（192 份能力声明，逐组核调用方）。

| 组 | 裁定 | 理由 |
|---|---|---|
| 图像 6501 / 6502 | **删 6502** | 6502 的输出是 6501 的严格子集，实现同走一条链，无独立逻辑；零调用方，删了不丢信息 |
| 解码 4001 / 6305 | **两件都留** | 4001 是文本→字节（编码），6305 是字节→文本（解码，BOM 优先且回报实际编码），方向相反；6305 同时是代码解析库的内部解码步骤上提 |
| 过滤 6301 / 6302 / 5205 / 5206 | **四件都留** | 作用对象与返回形态都不同（多重集计次 / 时间窗 / 首项文本 / 新数组），合并会破坏既有样本 |
| 摘要 5204 / 5212 / 5213 / 5219 | **四件都留** | 四条递归与口径互不相同，无薄封装 |
| 业务 6801 / 6802 | **能力留，族待迁** | 业务语义落在通用文本库，属族归属问题；迁族不是本次范围，先登记 |
| 转换 6116–6119 | **四件都留** | 6116 是前置探测，6117/6118 各自取程序路径并不互相调用，6119 独立 |

- **为什么不把 6305 并进 4002**：并了就必须让代码解析库跨库调用另一库的能力（支持库之间只能经唯一调用入口），
  一次解码要变成一次网关往返 —— 为了表面去重，把内部步骤变成跨库调用，属负优化。
- **不许再新增同类**：以后出现「输出是既有能力子集」的候选，按本节口径直接判删，不再走一遍审计。
- **验收**：删 6502 后 `扫实现.py` 与 `一键验证.py` 全过、`作废号表` 有 6502 一行、图像处理库零调用方报错。
