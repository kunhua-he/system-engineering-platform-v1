## 三 语义定盘（已定，不再二选一）

### 3.1 取消：两档已落地，第三档挂起

字段 `取消档位`（协议「取消档位」两值：`放弃` / `等收口`，缺省 `放弃`）。

| 取值 | 对在跑节点 | 回执时机 | 回执阶段 |
|---|---|---|---|
| `放弃`（缺省） | 照实跑完，结果保留 | 立刻 | 有在跑 ⇒ **收尾中**；一个都没有 ⇒ 已取消 |
| `等收口` | 照实跑完 | 窗口内等到真收口；没等完就照实回收尾中 | 真终态（成功 / 失败 / 已取消，看节点真实终态） |
| ~~`请求中止`~~ | 需协作通道（能力侧接取消令牌） | **挂起**：通道未定前不做，不做假承诺 |

**取消不打断在跑节点**：只有 `等待依赖 / 就绪 / 等资源` 的节点被置「已取消」。
所以只跑一个节点就取消、而它已起跑 ⇒ 它跑成功后整图阶段是 **成功**，不是「已取消」——这是真话，不是漏标。

档位名 → 等待窗口的翻译在接口面（协议翻译归它），适配器只认窗口 `Option<Duration>`：
接缝层不做业务判断（闸 ⑫）。

真机读数（2519 引本地模型做慢节点，八个并发）：`放弃` 提交 0.00s → 取消 0.000s → 阶段 **收尾中**、在跑 8；
`等收口` 取消耗时 **2.015s** → 阶段 **成功**、在跑 0。

### 3.2 等待截止：只管等待，不管任务

提交字段 `请求等待截止`（整数毫秒时间戳）：到点只让这次请求早点交回任务标识，
**不终止任务、不进失败或已取消**。缺省不设。同 `同步等待毫秒` 取较小者，再受五秒硬顶。

旧名 `截止时刻` 收到即 400 并点名新名——不许让调用方按旧协议误以为「到点图会停」。
真截止（到点终止整图）不做，理由见 §五。

### 3.3 失败判定顺序与两阶段终态

顺序写死（多条件同时命中只能报一个理由）：**失败策略 → 重试预算 → 截止**。
「决定失败」与「写终态」分两步：先标「即将失败」→ 停本地子进程 / 等回执 flush → 再写「失败」。
否则会出现「回执说失败了，子进程还在跑」。

### 3.4 收尾与回收

只对终态任务回收 · 删前再取一次状态校验 · 回收是独立 tick 可单独关 ·
**保留最后一试的回执与错误摘要**（K8s 删 Job 会连日志一起带走，这是它的问题不是优点）。

### 3.5 任务表六列：随所属批次进入，不一次加齐

| 列 | 进入批次 |
|---|---|
| `状态` | 已有 |
| `请求等待截止` | 已落地（只是请求等待窗口，任务表不必存） |
| `取消请求时刻` | 已落地（`取消档位` 两档，§3.1） |
| `尝试号` · `下次尝试` · `最近进度` | 批二（重试） |

### 3.6 资源车道：现状定盘 —— 节点独属，没有同键争用

键 = 实例号 / 提供者 / 代次 / **节点标识**（`图任务车道键`）⇒ 同一张图里任意两节点的键都不同。
于是：异节点真并行、同键争用**不存在**、「等资源」阶段在图任务路径**不可达**（内核那一档留着当安全网）。

因此**不报队位**：一个永远为空的字段就是垃圾。判据钉住三件事 —— 四节点真并行（至少一对区间重叠）、
全程没有节点进过「等资源」、键形态写死。

要变成"排队"得先有共用车道，两种走法都缺前提：① 按能力编号共用（同一能力并发的语义没人要）；
② 调用方显式声明「这几个节点抢同一样东西」（协议里没这个字段）。真要做，闸外排队与队位报序
**在同一批里一起做**；在那之前先把 `提供者试取` 那套没人调用的口删掉。

### 3.7 数据传递：产出体积上限已落地

**先量再立限，顺序不能反**：没有上限时，一个节点的产出可以把进程内存吃掉一半，而调用方只看到「图在跑」。

实测（2026-11-06 真实调用，不是估算）：3112 受控读文件读 324KB 文本 ⇒ 返回槽 **480,032 字节**（本批最大）；
4001 编码转换 6,000 字符 ⇒ 10,700；2519 一次对话 ⇒ 268；1108 / 1329 / 6110 / 3113 都不到 100。
另有三个大输入能力**在入口就拒**（不是这一层的事）：4601 摘要 108K 原文、4001 转换 108K、3113 写 2MB ⇒ `资源受限`。

定值 `单槽字节上限` = **2 MiB**（最大实测的 4.37 倍，口径要求不少于 4 倍），落 `任务对外/产出体积.rs`。
超限**当节点失败**并给实测字节与上限，**不截断**——截断看起来像「能力只返回了这么多」，那是最坏的一种谎。
单能力路径不受此限（它不经过产出槽）；图任务路径受。

~~命名槽（按名取复合值里的某一项）~~ **不做**：与 §3.8 冲突——输入引用只支持整槽，
按名取已经被否掉（协议里连字段都没有了）。两处口径只能留一处。

### 3.8 输入引用只支持整槽

`输入引用` 只有 `目标参数` 与 `来源节点` 两个字段：上游只交一个返回槽，按名取复合值里的某一项做不到。
协议里的 `来源参数` 已删除；收到即 400 并说明「要传上游结果就整槽引用」。

不静默忽略：带着它提交的调用方会以为按名取生效了，实际拿到整槽——那是更坏的结果。

### 3.9 持久化：落最小集，载体是追加日志

**落什么**：一条任务一行 —— `任务标识 · 请求标识 · 图摘要 · 任务阶段 · 全部节点阶段`，
正好是内存里那份任务记录的形状加上判重键。**不落事件历史、不落时刻、不做重放**：
时刻是实例内单调钟，跨进程没有意义；重放要的是工作流引擎那套语义，本平台明确没有。

**载体为什么不是 SQLite**：平台侧没有 Rust SQLite 绑定，唯一 SQL 通道是能力 5101/5102
（每调用一条独立连接 + 参数编组），而任务状态写在**热路径**上（节点每收口一次就变）。
拿它落运行态，等于每次节点变化都过一次跨语言转发 —— 比写一行本地日志更慢也更脆。
故用 `运行数据根/数据库/调用任务运行态.jsonl`：单写者、只追加、每行 `fsync`。
与本节原方案的差别只有载体，落点（新增运行态落盘、不进治理库、只存最小集）与范围一字未改。

**重启对账**：读回落盘 → 任务阶段 `排队中/执行中/收尾中` ⇒ **失败·已中断**；
节点 `执行中/收尾中` ⇒ **失败**，`等待依赖/就绪/等资源` ⇒ **已取消**。已经是终态的一个都不动。
**绝不把不知道死活当成成功**。

**回执怎么答**：内存查不到 → 从重启快照答（阶段 + 节点阶段），**不给时刻、不给批号**——
编一个出来就是假证据。失败说明里点名「进程重启前中断」。

**发号接历史**：装载时把发号计数器抬到「历史最大号 + 1」（只抬不降），重启后新号绝不与旧号相撞。

**释放也落盘**：释放是真删（内存 + 判重键），日志追加一条释放标记；不落的话重启后任务又冒出来，
等于释放没生效。跨重启的释放同样走这条路。

**判重跨重启**：`请求标识` 命中重启快照即回原任务标识（同图才回，不同图照旧冲突）。
窗口口径不变（仍是内存任务表 128 条内），但**已经落盘且未被释放的那些**重启后仍认。

**已知限制（写清，不装没有）**：
① 两个进程同时开着时共写一条日志 —— 靠短行追加，坏行读回时跳过，不保证严格互斥；
② 日志只增不减，没有清理策略（量级：一条任务几行、每行约 100 字节，十万任务约十 MB）；
③ 落盘失败一律静默降级成纯内存（磁盘抖动不许掀翻在跑的图），此时重启会丢 —— 这是刻意的取舍。

### 3.10 重试：**不做**，理由与将来开工的硬口径都留在这里

**当前裁决：不做。** 依据是本节定的门槛 —— 「真有调用方要，才开这批」。全仓至今 0 处节点级重试，
也没有一个调用方提出要。没有真实调用方的功能只会在协议里长出一堆没人走的分支。

更要紧的是：我们的「失败」里包含「结果未知」，能力可能已经做了一半副作用；
自动重放等于替能力承诺幂等，而它只自报了「可重试」这一位。默认开就是给调用方挖坑。

**将来真要开，按这套硬口径做**（写在此处，防止重新推演走样）：
新增节点阶段 `待重试` 属于**未终态集合**但写结束时刻与本次时长，下游不许在其上就绪 ·
只存内部值 `总次数上限`（含首次），对外 `重试次数` = 总次数 − 1 并写死「不含首次」·
退避 `底数 × 乘数^(已失败次数−1)` 双重封顶，**抖动确定性**（节点标识与批号哈希，不用随机数）·
到期时间**落列**只比较不重算 · 连续失败在出现一次成功时清零 · 失败策略只两档（`忽略` / `立即失败`），
匹配用「错误类别 + 连续同错次数」· 重试不改节点标识只递增批号，尝试记录只增不改。

**落点**：加 `待重试` **不动内核** —— 节点阶段枚举与跃迁表都是 `契约声明/调用任务协议.json` 派生的，
内核 `运行内核/调用调度` 只是再导出 + 包错误类型（文件头写明「本件不写第二份规则」）。
改协议 JSON → 重生派生件 → 适配器侧判定。

### 3.11 未知：**状态机只放确认过的节点**，不替能力宣布结局

**口径**：节点阶段只许写「有证据支撑」的东西。成功有产出槽为证，失败有回报为证；
**两样都没有时，只能写未知**。把「不知道」写成「失败」是拿平台的记账口径替能力宣布结局。

**三处来源，全是「没有回报」而不是「回报了失败」**：

| 来源 | 事实 | 旧写法（猜） | 现在 |
|---|---|---|---|
| 调用超时 | 内核 `超时` 注释原文「可能还在跑」 | 节点失败 | 节点 **未知** |
| 执行体崩溃 | 内核注释原文「可能已经改了扩展内部状态」 | 节点失败 | 节点 **未知** |
| 进程重启 | 执行体随进程消失，没有任何一方回报过 | 节点失败 · 任务失败 | 节点 **未知** · 任务 **未确认** |

**不算未知的（确认失败，照旧报失败）**：能力回错误槽（业务失败，4 位码在槽里）·
执行前判掉的失败（`提供者未载入` / `命令已废止` / `参数个数不符` / `输入形状不符`——一次都没进扩展）·
重入被拒（守卫都没拿到，确定没执行）。

**阶段与跃迁**：节点阶段加 `未知`（码 9，终态）；任务阶段加 `未确认`（码 6，终态）。
跃迁表只加两条：`执行中 → 未知`、`收尾中 → 未知`。释放照旧可做（调用方裁决不再关心）。

**收口顺序（写死在 `收口判据::定结局`）**：成功 → 已取消 → **确认失败** → **未确认** → 裸失败。
成功与确认失败排在未知前面，是因为它们**有证据**，不被「还有事不知道」推翻；
但只要没有确认失败，就绝不能落到「裸失败」——那正是把未知写成失败的那一步。

**前驱未知的后继**：不当作「前驱成功」推起来，按内核既定行为**跳过** ——
这不是猜前驱成败，是「拿不到有效输入 ⇒ 确定跑不起来」。所以 `跳过` 的说明改成
「前驱失败/跳过/取消/**未知**而跳过」，跳过的原因在回执里可查。

**两本账各管一件事（不合并）**：内核那格仍会记「失败」（它只有成功/失败两格，且是冻结件）；
适配器记录那本账写「未知」。对外（回执 · 落盘 · 重启恢复）一律以记录为准：
`节点报读` 先看记录里是不是未知，是就报未知，**取消旗也改不动它**（未知是「不知道做到哪」，
不是「已确认停手」）。

**未确认不带失败读数**：没有失败就不许摆一份失败出来。回执只给 `任务阶段 = 未确认` +
逐节点 `未知`，节点名与来源段位在结局里（`段位: Option<调度错误>`），单能力路径据此回
`转发结果::失败(原段位)`。

**已知边界**：未知是终态，不会自愈 —— 平台没有「事后继续观察」的能力，重发由调用方决定。
将来若要做「未知自动复查」，前提是能力侧给出可查询的幂等凭据（本次未做）。

**实测**（候选 `9842e8434373-c97c648546f63d6f`，临时端口 `50198`/`50439` → 重启 `50690`）：

## 四 标准进化流程

### 4.1 每批固定七步（顺序不许调）

| 步 | 动作 | 判据 |
|---|---|---|
| 1 冻结 | 写清本批**改哪几件、哪些件不许碰**，落进台账 | 落点件路径逐个存在，禁碰清单点名 |

| 4 定向验证 | 只跑受影响的 crate 与测试件，不跑全量 | 适配器 / 接口面 / 内核 三个数各自报，**不合并成一个"全绿"** |

## 五 明确不做（连理由，防反复）

| 不做 | 理由 |
|---|---|
| 协作取消通道 / 第三档「请求中止」 | 要改能力声明面；在跑节点怎么收手没定，先不做假承诺 |

| 用 petgraph/daggy 做调度 | 只做图算法，不管状态与资源；环检测已有 |
