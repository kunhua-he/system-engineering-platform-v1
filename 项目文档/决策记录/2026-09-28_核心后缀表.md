# 核心后缀表：制品后缀一律自定义

日期：2026-09-28 ｜ 裁决人：华哥（原话：「支持库的后缀和模块的后缀，不是自定义的吗？……肯定不是用系统级原生的啊。毕竟我们的代码，直接单独解析我们自定义的后缀的就完事了。不然后面每个系统的后缀不同，还要写几个不同的解析器，还更麻烦」「别再搞 `.dylib`/`.so`/`.dll` 了……本质上后缀表，除了 `rs`/`md`/`py` 这种代码文件，但是制品文件，本质上就一定是自定义的。不然，后面会乱个半死。我觉得你应该是要专门做好一个自定义的制品的后缀的统一表。给他一个声明」）

**落点**：`扩展装载/后缀表.json`（**唯一权威**）· 两侧读方 `对外接口面/调用接口面/src/扫扩展根.rs` · `构建装配/上线切换/构建制品/扩展.py`

---

## 一 裁决：三个核心后缀

| 后缀 | 角色 | 容器 | 谁解析 / 载入 |
|---|---|---|---|
| **`.程序文本`** | 源码（人写 · agent 改） | —（就是文本） | 1101 / 1102 / 1103 |
| **`.支持库`** | 支持库制品（`1xxx–6xxx`） | 能力包件（接口说明 `16` + 能力码 `17` + 指纹 `18`） | 底座载入器 |
| **`.模块`** | 模块制品（`7xxx`） | 同上三段 | 底座载入器 |

技能（`8xxx`）**没有制品** —— 本体就是一份 `说明.md`（散文），不含实现。

**口径**：后缀是**角色标签** —— 看后缀就知道「这是什么、谁解析它」。**容器格式只有一个**（能力包件），**后缀按种类给**。

## 二 为什么制品后缀必须自定义（华哥的理由）

用系统原生后缀（`.dylib` / `.so` / `.dll`），就是**每个系统一套后缀 + 一套解析器**；我们的代码只认**一个**自定义后缀、只写**一个**解析器，跨系统不变。这与 `能力包件.md` §五「**不用原生共享库当包**」是同一条理由（不跨系统；每个系统一个二进制就是 N 条腿）。

⇒ **`.dylib` / `.so` / `.dll` 从底座的后缀面退休**。代码 / 数据文件的后缀（`.rs` `.md` `.py` `.js` `.json`）不属本表 —— 那是**工具链**的，不是底座定义的。

## 三 `.能力包件` 的地位

`.能力包件` 原写作「编译产物的扩展名」。本裁之后它**降为容器格式名**（**能力包件** = 那套三段容器），**不再是文件后缀** —— 后缀按种类给（`.支持库` / `.模块`）。

## 四 待裁 / 待施工（如实登记）

| # | 项 | 现状 |
|---|---|---|
| 1 | **码段装什么** | 支持库 = **本机机器码**（它是本机原生实现）；模块 = **WebAssembly**（本体是程序文本，由 1106 编译产出）。⇒ `能力包件.md` 段 `17` 的定义要从「WebAssembly」放宽为「可载入的机器码」，并注明按种类分 |
| 2 | **容器写 / 读** | 装配侧要把编出的 cdylib 字节**包成 `.支持库`**；底座要**解析 `.支持库`、取码段、装载**。两样都没有 |
| 3 | **切面顺序** | **不许先删 `.dylib` 再实现** —— 会把已经跑通的运行期热载入打断。顺序：先做容器写 / 读 → 跑通 `.支持库` 载入 → 再切扫描面、退休旧后缀 |
| 4 | 一处**同名两义** | `.支持库` **已是本仓语言的源码关键字**（易语言指令 `.支持库 <名>, <版本>`，语料 23 次；见 `说明/真文本覆盖.md` 的关键字表）。拿它当**文件后缀**会出现「同名两义」—— 是否改名（如 `.库件` / `.支持库件`）由裁决方定；表只有一处落点，改一行即可 |

## 五 防回潮

**判据**（本件落盘后立）：制品后缀表里**不许出现** `.dylib` / `.so` / `.dll`；全仓**不许有第二处后缀表**（两个读方都只读 `扩展装载/后缀表.json`，不许自带副本）。
