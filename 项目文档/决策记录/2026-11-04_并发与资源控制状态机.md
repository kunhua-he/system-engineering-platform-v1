# 并发与资源控制状态机 —— 现状盘点与收敛口径

> 起于 2026-11-04 华哥提问：底座能不能「选串行还是多线程」，加载/释放/收拾干净，别打爆内存 CPU GPU。
> 本文是**唯一权威口径**：先说清现状有什么（按代码位置取证），再写缺口，再写补法与默认值。

## 一、术语对齐

华哥说的「核心状态机」，专业上分三件事，本项目分别对应三处现成件：

| 俗称 | 专业名 | 本项目落点 |
|---|---|---|
| 选多线程还是串行 | 并发度控制 / 连接级并行 | `对外接口面/调用接口面/src/网关.rs` |
| 决定能不能起、起几个 | 准入控制（admission control） | `跨语言适配/适配器实现/src/原池执行/进程池/进程额度.rs` |
| 忙了就收、闲了就还 | 动态配额 / 背压 | `…/进程池/动态预算.rs` |
| 收拾干净 | 生命周期回收 + 资源回落验收 | `…/进程池/回收.rs` · `…/进程池/资源读数.rs` |

一句话：**底座已经有这套东西，而且默认就是并行、压力上来自动收缩**。缺的是「GPU 没进预算」「运行中不能缩放」「单个请求不能选模式」三样。

## 二、现状（逐条带代码位置）

### 2.1 网关层 · 连接级并发（可配，含串行）

- `网关.rs::跑服务()` —— 生产入口，并发度 = `默认并发线程数()`。
- `网关.rs::跑并发(工作线程数)` —— 起 N 个工作线程，各自 `accept` + 处理；**N=1 就是串行**。
- `网关.rs::默认并发线程数()` = `std::thread::available_parallelism()`，取不到退 1（不猜一个数）。
- `网关.rs::请求停止()` —— 置标志 + 连 N 次叫醒阻塞在 `accept` 上的线程，作用域结束必然汇合，不留游离线程。

所以「串行与多线程都支持」这条**已经成立**，但只能**启动时定**（见缺口二）。

### 2.2 执行池层 · 原子额度（超发不可能）

- `进程额度.rs::申请进程额度` —— 所有**首次启动与重拉共用同一个** `Arc<AtomicU32>`；
  用 `fetch_update` 的 CAS 判「已占用 < 上限」再 +1，并发首拉挤不穿。
- 返回值是**租约** `进程额度租约`，`Drop` 里 `fetch_sub` 归还 —— 借了不还这个错在类型上就写不出来。

### 2.3 执行池层 · 动态预算（压力上来自动收缩）

- `动态预算.rs::重算` 的收缩规则（硬上限记作 N）：
  - CPU 忙碌 75–100% ⇒ `CPU承压`，上限按 `N × (100 − CPU忙碌) / 100` 收缩（最少 1）
  - 内存压力 警告(2) ⇒ `N/2`；危急(4) ⇒ `1`
  - 最终上限 = `min(硬上限, CPU上限, 内存上限)`
- **250 ms 采样节流**：`上次采样.elapsed() < 250ms` 直接回缓存上限，不反复压系统。
- 两条硬边界：**不取消在途任务**、**不改配置里的硬上限**（预算只是在硬上限之下临时收紧）。
- `样本可信` 标记：CPU 或内存任一样本读不出 ⇒ 标不可信，**不假装知道**。

### 2.4 执行池层 · 回收与「收拾干净」的验收

- `回收.rs` —— 进程**组**强杀（不是杀单个 pid）+ 池 `Drop` 收尾，不留孤儿。
- `资源读数.rs::域资源读数` —— 四类**现读**：进程数 · 句柄数 · 文件数 · 常驻字节；
  **读不出给 `None` 而不是 0**（不假零 —— 把「不可判」说成「零占用」正是这口要防的假绿）；
  读数带实例代次 ⇒ 能判「这是不是同一批进程」。

## 三、缺口（华哥这轮点到的正是这三条）

1. **GPU 没进预算**。`取系统压力样本()` 只采 CPU 忙碌度 + 内存压力（macOS 走 `host_statistics` + `sysctlbyname`）。
   本地跑大模型时 GPU 打满而 CPU 不满 ⇒ 预算不收缩，进程继续起。
2. **运行中不能缩放**。`跑并发(N)` 一次性 `spawn` N 个线程后数量固定；想从 32 降到 4 必须重启服务。
3. **单个请求不能表达模式**。「这条我就要独占串行」现在没有地方写 —— 串行/并行只是启动参数。

## 四、补法（按依赖顺序）

| 序 | 补什么 | 落点 | 判据 |
|---|---|---|---|
| 一 | GPU 利用率进预算样本 | `动态预算.rs` 的 `取系统压力样本()` 扩成三元组 | GPU ≥ 90% 时上限按剩余比例收缩；读不到 ⇒ `样本可信=false` 且**不缩**（不猜） |
| 二 | 并发线程数可运行时调 | `网关.rs`：线程数已在 `AtomicUsize`，工作循环里比对目标值 | `目标 < 当前` ⇒ 多出的工作线程退出；`目标 > 当前` ⇒ 补拉；当前/目标 与真实存活线程数三个读数一致 |
| 三 | 请求级 `并发模式` | 契约参数（`自动` / `串行` / `并行N`），默认 `自动` | 省略 = 现状不变；`串行` 走独占租约；越界 N 当场拒 |

**默认值决策（自裁，不改现状）**：
- 网关默认并发度**保持** `available_parallelism()`（华哥机器性能抗打，不该默认掐成 1）。
- 动态预算默认**启用**，但只在压力真上来时收缩。
- GPU 读数**读不到就不缩、也不假装**（与 `样本可信` 一致），不因为「拿不到读数」把并发打到 1。

## 五、不做什么

- 不做「默认串行保平安」—— 那是拿性能换心安，华哥明确反对。
- 不做「按端口/进程名盲杀」回收 —— 回收一律按状态机登记的归属与资源指纹。
- 不把预算读不到的数当成 0 或 100 —— 读不到就标不可信。

# 第二部分：模型活性与 GPU 排队（2026-11-04 追加）

> 华哥定的口径：**GPU 利用率不是判据** —— 正常调用模型瞬间 100% 很正常。
> 真正的核心是「模型/对应进程**是否在工作**」。没工作还占资源（干烧）才是浪费；
> 一直在工作就让它占。多个模型同时用 GPU ⇒ **内置排队**。其余瞬时占用不管。

## 六、三个问题必须分开

| 问题 | 判据 | 现状 |
|---|---|---|
| 进程在不在 | 进程 / 端口存在 | 已有（进程池额度）|
| **是不是真在工作** | 最近请求 + CPU 时间增量 | **空白** |
| GPU 归谁用 | 谁持用「一次推理」许可 | **空白** |
| 收拾干净 | 进程组强杀 + 四类资源现读 | 已有 |

## 七、活性读数（抓「干烧」与「卡住」）

对每个模型服务 / 工作进程记三样，全部来自内核，不估算：

- `最后活动时刻`：最近一次请求进出
- `累计 CPU 时间`：**增量**才说明真在算
- `在途请求数`：队列里还有几件

四态判读：

| 在途请求 | CPU 时间 | 判读 | 处置 |
|---|---|---|---|
| 有 | 在涨 | **在工作** | 正常占用，不该掐 |
| 无 | 不涨 | **空闲** | 可让位、可回收 |
| 无 | 在涨 | **干烧** | 告警（真浪费就在这里） |
| 有 | 不涨 | **卡住** | 超时回收 |

只看「进程在不在」这四态一个都分不出来 —— 所以旧预算看不到干烧。

## 八、GPU 排队：一次推理独占，不是进程独占

- 一张全局 GPU 使用许可，**并发默认 1**；要跑推理先申请、跑完还。
- 两个模型同时要用 ⇒ 自动排队（FIFO · 等太久可超时 · 能查「谁在等、等多久、现在谁在用」）。
- 常驻服务待命时**不占**许可 ⇒ 多模型常驻不冲突，真算的时候才排队。
- 模型以外的瞬时占用（截图编码等）**不进**这个队列。

这条是「内置排队」的唯一落点：调用方不另写锁，一律经底座申请许可。

## 九、自适应参数按机器算，不写死

开机探测一次并缓存：核数 · 统一内存总量 · GPU 核数/型号。
由这三样推：进程池硬上限 · 帧缓冲上限 · GPU 队列并发（默认 1）。
**换机器不改代码** —— 底座的自适应对象是「跑它的这台电脑」。

## 十、收敛路径（三步，每步单独可验收）

| 步 | 补什么 | 验收 |
|---|---|---|
| 一 | 活性读数（最后活动 / CPU 时间增量 / 在途数） | 真起两个模型压，四态判读对得上 |
| 二 | GPU 独占队列 + 可观测 | 两个同时打，确认串行且排队可查 |
| 三 | 活性接进预算（空闲收 / 干烧报 / 卡住超时回收） | 造空闲、造干烧、造卡住三个样本各报对 |

## 十一、已知边界：外部常驻服务也要管得到

底座拉起的扩展进程能直接读活性；外部常驻的模型服务（如 launchd 自启的 `llama-server`）不归底座启动，
必须靠**端口 + 进程归属登记**去读（`进程归属支持库` 已有端口/路径登记，扩成活性读数）。

**这条边界正是「绕开底座直接拉模型」的漏洞所在** —— 见第十三节实证。

## 十三、为什么「空闲自动退出」没生效

看门狗本体：`~/Library/Application Support/AI模型服务/看门狗.py`（PID 1552，系统 Python 3.9）。

**规则原文取证**：

- `空闲秒数 = int(os.environ.get("IDLE_SECONDS", "300"))` —— 空闲回收是 **300 秒（5 分钟）**，不是 15 分钟。
- 回收循环：每 `30` 秒扫一遍服务表；`if 空闲 < 空闲秒数: continue` 否则 `杀掉(端口)`。
- `杀掉()` 的实现：`端口进程号(后端端口)` 用 `lsof -iTCP:<后端端口> -sTCP:LISTEN -t` 取 PID，再 `SIGTERM`。

**命门在服务表**：`看门狗.py` 的 `服务表` 只有两项 ——

| 外部端口 | 后端端口 | 服务 |
|---|---|---|
| 40019 | 40119 | 重排器 Qwen3-Reranker-4B |
| 40020 | 40120 | MLX 视觉 32B 稠密 8bit |

**实际占内存的四个进程，端口是 40013 / 40017 / 8015 / 8006 —— 一个都不在服务表里。**
看门狗只会回收「表内后端端口上的进程」，表外的它既不认、也不管 ⇒ 永远不会在这些进程上触发空闲回收。

三个 launchd 自启的（PPID=1）属于部署事实：它们从开机就在，本来就没打算被按需回收。
唯独 **8006 那个 8B 是 Hermes 直起的孤儿**：父进程是 Hermes agent 的 python 运行时，
既不归看门狗、也不归底座进程池，还没人记住它的存在 ⇒ 白占 22 小时。

## 十四、活性判读（按第七节口径实测）

`ps -o time,%cpu` 两次采样（间隔 3 秒）：

| 进程 | CPU 时间 | 增量 | 判读 |
|---|---|---|---|
| 98997（8006 · 8B） | `1:00.49` → `1:00.49` | **0** | **空闲**（22 小时总共只用 1 分钟 CPU ⇒ 早已不干活） |

这条实测正好证明第七节的必要性：只看「进程在不在」，它长得跟正常服务一模一样；
只有把「CPU 时间增量」和「最后活动时刻」一起读，才看得出这是个吃内存不干活的空转进程。

## 十五、处置口径

| 对象 | 动作 | 理由 |
|---|---|---|
| 8006 那个 8B（Hermes 直起的孤儿） | 释放 | 空转 22 小时，CPU 时间冻结，且不属于任何受管表 |
| 40013 / 40017 / 8015（launchd 自启） | 报告后由华哥决定 | 属部署事实，不是本轮造成的；先确认有没有下游在用 |
| 看门狗服务表 | 只加「底座要管的模型」，不把 launchd 常驻件塞进去 | 否则会被空闲回收误杀 |

# 第五部分：推理许可（2026-11-04 第二批）

## 二十一、为什么是「推理级独占」而不是「进程级独占」

GPU 利用率不是判据 —— 正常推理瞬间冲到 100% 很正常。真正浪费的是**没活干还占着**，
以及**两个模型同时抢一块 GPU**：结果是两边都变慢，读数也没法归因到谁。

所以许可的粒度定为**一次推理**：常驻模型服务待命**不占**许可，只有真正要算的时候才申请。
这样"多模型共存"与"GPU 不打架"两件事不再互相牵制。

## 二十二、三个新能力（2516-2518）

| 编号 | 名称 | 返回 | 语义 |
|---|---|---|---|
| 2516 | 申请推理许可(服务句柄, 等待毫秒, 租约毫秒) | 许可句柄 | 无人持有即刻授予；有人持有则排队 |
| 2517 | 归还推理许可(许可句柄) | 逻辑型 | 真 = 已释放并让出 GPU |
| 2518 | 取推理排队快照() | JSON 文本 | 持有者 / 队列 / 累计授予 / 超租约回收次数 |

新错误码：`2511 排队超时` · `2512 许可无效`。

**排队与租约的裁决口径**：

- 拿不到许可**不静默降级**：等满 `等待毫秒` 就报 `2511`，要不要加大等待由调用方定。
- **租约上限 5 秒、等待上限 3 秒**（全仓超时硬顶）：调用方崩溃没归还，许可能在下一次申请时被强制回收（计入 `累计超租约回收`）。
  代价要认：一次推理超过 5 秒时若有别人来申请，本许可会被当成超租约回收 —— 宁可罕见误回收，也不破全局 5 秒硬顶。
  等待上限**必须低于** 5 秒：顶到 5 秒会先撞内核调用预算，调用方拿到的是 `4 超时`（内核自有码）
  而不是本能力的 `2511 排队超时` —— 实测踩过，改成 3000 后正常。
  回收只发生在「下一次申请」时，不跑后台定时器 —— 底座不替调用方做不可观测的清理。
- 申请前校验服务句柄，已释放的服务报 `2508`，防止拿许可去抢一个不存在的模型。

## 二十四、这一批踩到的三个真坑（都值得记）

1. **`静态声明.rs` 的号段是硬编码的**：`底座能力号段` 写死 `2501-2515`，只改 `包声明.json` 没用，
   装载直接报 `声明不自洽 { 命令号: 能力号(2516) }`。**加能力必须同时改这两处**：
   `包声明.json` 的 `能力号段` 与 `src/静态声明.rs` 的 `底座能力号段`。
2. **能力声明的 `可抛错误码` 必须与 rs 里那个数组逐项同序**：实现是 `[2511,2512,2508]`，
   声明写成 `[2501,2506,2508,2511]` 就不自洽 —— 声明与实现是两份文件，改一个必须改另一个。
3. **`lib.rs` 的模块声明带 `#[path]`**：往中文模块名旁边插新模块时，若把 `#[path="编号与码面.rs"]`
   与 `mod 编号与码面;` 拆开，会得到 `E0754 non-ascii identifier name` 且新模块找不到函数。
   `#[path]` 必须紧贴在对应 `mod` 上一行。
4. **`参数个数已核条数` 是「命令项数」不是「参数总数」**（断言是 `== 项表.len()`），加 3 个能力就是 18，
   不是 19；`函数表项数` 是另一个独立常量，也要一起改成 18。
