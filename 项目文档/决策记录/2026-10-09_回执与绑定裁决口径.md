# 回执与绑定裁决口径

> 决定「回执长什么样」「文件绑定什么时候自动」「撞车怎么裁」。
> 口径由华哥 2026-10-09 定，参照易语言「句柄 = 连接(地址, 账号, 密码…) —— 返回就是那个值本身」。

---

## 一、回执：只给结果本身

**返回就是那个值，没有成功/失败包装。** 失败不另标真假，直接给失败原因。

| 情形 | 回执 |
|---|---|
| 单条改成功 | `修改成功` |
| 批量改 | `1-修改成功` / `2-修改成功` / `3-失败：盘上没有这段原句` |
| 登记 | `v1-100721`（＋工作树路径） |
| 查东西 | 结果本身（数字 / 对象 / 表） |
| 失败 | 失败原因一句；**不写** `成功:false` |

**参数全空 = 返回「怎么调」**（操作目录，现已具备）。

### 传参：扁平值表，没有键、没有嵌套

```text
传参('v1-100721', '改', '开发工具/信息核心/未完成.json', '原句', '修改句')
传参('v1-100721', '批量改',
     '开发工具/信息核心/未完成.json', '原1', '新1',
     '开发工具/MCP服务/协议.py',     '原2', '新2',
     '开发工具/MCP服务/协议.py',     '原3', '新3')
```

- 位置固定：`开工ID · 操作 · 路径 · 原内容 · 新内容`。
- 批量按**每 3 个一组**切；同文件改多处就重复写路径（省掉嵌套，不丢信息）。
- **回执编号对齐传参顺序**（第 N 组 ↔ 第 N 行）。

---

## 二、绑定：未绑即自动绑

- **写盘前该文件没被绑定** ⇒ 自动绑定（省掉「先认领」这一步）。
- 第 ② 道闸由「强制前置」改为「**自动补**」；**其余四道一条不动**：
  1. 原句必须真在盘上（指纹对不上就拒）
  2. 禁改面（生成物 / 只读参考 / 制品产物）
  3. 命名登记
  4. 字面禁项

  这几道才是防改错的，不放松。

### 开工ID 三档

| 给的东西 | 行为 |
|---|---|
| 已有 ID | 直接用 |
| 新 ID | **自动登记**（不必先单独跑一步） |
| 不给 | 用当前唯一「进行中」；没有就报错 |

**回执第一行必须把实际用的号报回来**，否则调用方不知道起了什么号：

```text
v1-100721（自动登记）
1-修改成功
2-修改成功
```

## 三、释放：改完即释放（原子写，不是锁）

**动作**：改动落盘 + 提交后 ⇒ **立即释放绑定**。释放后其他支线可接着改同一文件。

**明确定位（不许误解）**：这个窗口只有几毫秒 ⇒ 它是**原子写**、防「同一瞬间两人写坏同一个文件」，
**防不住「两条腿各改一遍」**。别把「改完即释放」当成防撞车手段 —— 撞车发生在**合并期**，不在这里。

---

## 四、撞车：工具流水账单 + 提交时出裁决清单

### 账单（已有件，扩三个字段即可）

现状：`开发工具/MCP服务/工具流水.py` 在**每次带开工ID的工具调用后**自动记一行白名单元数据
（工具名 · 操作 · 开工号 · 时刻 · 退出码 · 写前/写后指纹 · 作业任务ID），落**同一本**开工账本库。
它已经就是「账单」：**谁改过、改的是哪个文件（写前/写后指纹）**，全在。

**只差三个字段**：`文件 · 行起 · 行止` —— 从 `v1_edit` 的分组结果里取（改动表本就带路径与定位区间）。

### 提交时的动作（两条分支）

提交时读这张账单，比对**其他开工号**：

| 分支 | 条件 | 动作 |
|---|---|---|
| 一 | 对方**已释放**（它的改动已落盘） | 出裁决清单**放进本支线**，并**删掉流水** |
| 二 | 对方**还没释放** | **只出裁决清单**（放进本支线），提交照常，**流水不删** |

两条分支都**不阻塞提交**。

### 「谁清理」：最后离场者清

- 改 B 的开工先提交 ⇒ 走分支一：清单放它支线 + 删流水（已消费）。
- 改 A 的开工后提交 ⇒ 流水已被删 ⇒ **无需再清理**（没有垃圾可留）。
- 反过来则清理由另一个方向的开工完成。

⇒ 不必按开工号排序去定「谁负责清」，**哪一个最后离场，就由它把垃圾清掉**。

### 为什么这样够用

裁决**不在提交时真做**（提交时不合并、不裁决），只**出清单**。
真裁决在**合并那一步**（冲突才浮现，且此前已有重叠核与接管集成两道现成出口）。
因此：提交零阻塞、裁决信息不丢、也不引入新状态机。

**不同处改动自动合**（台账按行号做主键重放、源码走三方合并保留双方独有改动）⇒ 绝大多数根本不出清单。

### 为什么不引入 PR

PR 的零件在此处已有对应物：腿 = 待合入提议、重叠核 = 冲突检测、接管集成 = 手工解冲突、台账 = 变更记录。
**缺的只是「待裁决队列 + 裁决记录」**，给重叠核加一个出口即可。
引入 PR 会变成**第二套状态机**，与「只留一套路径」的设计哲学冲突。

## 五、落地顺序（分三条腿，各自可验）

**腿一 · 事务闭环（先做 · 独立可验）**
1. **传参/回执形状**：`v1_edit` 收扁平值表，回执按编号对齐；对模型那面只给一句话。
2. **自动绑定**：第 ② 道闸改自动补 + 开工ID 自动登记。
3. **改完即释放**：提交后释放绑定。

**腿二 · 账单（依赖腿一）**
4. **流水扩三字段**：`文件 · 行起 · 行止`（`工具流水.py` 的记流水扩列）。

**腿三 · 裁决清单（依赖腿二）**
5. **提交时读取比对**：读账单，比对其他开工号，按上文两条分支动作。

若作一条腿做，则腿三必须**排在最后**（它读的数据由前两步产出）；
一腿做完须用真实两次改盘验证「清单 + 流水清理」两个动作。

**分层约束（改动前必读）**：内部探针链（如 `反馈帧样本.py::取码`）直接读信封里 `退出码` 判业务码。
收口必须分两层 —— 对模型那面只给那一句话；内部/stdin 面先保留 `退出码` 供探针读，
探针链迁到新形状后再一起撤。**一步砍到底 ⇒ 26 条探针齐报 `-99`（已真实发作一次）。**
