# 模型请求参数速查

> 2026-11-05 实测（含闲置自动退出改造）：能力走正式口 `http://127.0.0.1:43110`，模型直连各自端口。每条都是真跑出来的读数。
> 本文件是**调用方唯一的传参依据**；底座声明表里写什么、这里就写什么，两边不一致以本节实测为准并立刻修。

## 一句话

**参数一个都不能少；列表 / 对象必须显式写 `{"类型标签":N,"值":…}`；标量给裸值。**

**绝大多数参数没有默认值** —— 必须由调用方表态，漏传报「缺参数「X」：本能力这一行没有声明默认值」，一眼能看懂缺哪个。

只有**整数型**参数能带真默认值（枚举型塞不进底座的 const 声明表）。目前只有 `2512` 的两个超时：`闲置超时秒` 默认 `900`、`载入超时秒` 默认 `120`，不传就走默认，其余一律必传。

## 拉起模型服务（2512）—— 八个参数

```json
{"编号": 2512, "命名值": {
  "模型引用": "/Users/hekunhua/Documents/AI模型/文本模型/Qwen3-8B-Q4_K_M.gguf",
  "可执行文件": "/opt/homebrew/bin/llama-server",
  "启动参数": "-m {模型文件} --host 127.0.0.1 --port {端口} -c 4096 --no-webui",
  "监听端口": 0,
  "就绪路径": "",
  "模型类型": "LLM文本模型",
  "闲置超时秒": 900,
  "载入超时秒": 120
}}
```
回执：服务句柄 `900001`（端口用 `2514` 查）

> **拉起立刻返回，不等载入**：回执只有句柄，模型还在载入。要发请求就轮询 `2514` 看状态变 `已载入`。

| 参数     | 说明                                                                                          |
|----------|-----------------------------------------------------------------------------------------------|
| 模型引用 | **绝对路径**（推荐，会校验存在，不存在当场报 `2513 模型文件不存在`）或纯 model 名              |
| 可执行文件 | 推理引擎，如 `/opt/homebrew/bin/llama-server`                                               |
| 启动参数 | 支持 `{端口}` 与 `{模型文件}` 两个占位符 —— 路径只写一遍，两边不会打架                        |
| 监听端口 | **传 0 = 自动分配**（40000-49999 里第一个既没在听、也没被服务表登记、也没被预占的）；固定端口照传，被占就报错不偷换 |
| 就绪路径 | 传空 = 按模型类型取默认（`ASR语音识别模型` 取 `/`，其余 `/health`）                            |
| 模型类型 | **必填**，五个词之一（见名表）                                                                |
| 闲置超时秒 | 连着这么多秒**没人真正使用**就自动退出内存，下次要用再载入。默认 `900`（15 分钟）。**不建议传 0**（见下节） |
| 载入超时秒 | 载入最多允许多久，超了状态转 `载入失败` 并由巡检收掉进程。0 = 不限。默认 120                    |

**拉起前会先算内存预算**：需求 = 模型文件字节 × 1.15 + 512MB；可用 = `vm_stat` 的 free + inactive 页 × 页大小，再打八折。需求超过可用就报 `2506 资源受限`，不会把机器撑爆。路径读不到或内存读不到时跳过这一步放行。

## 载入状态与闲置退出（滑动过期）

**四个状态，只有这四种**（`2514` 的 `状态` 字段）：

| 状态 | 含义 | 调用方该做什么 |
|---|---|---|
| `载入中` | 进程起来了，还没真就绪 | 继续轮询，别发请求 |
| `已载入` | 真就绪过一次，可以服务 | 立刻发请求 |
| `载入失败` | 过了 `载入超时秒` 仍未就绪 | 巡检会收掉进程；重拉并查日志 |
| `已退出` | 进程没了 | 要用手就重新拉起 |

**闲置退出是滑动的**：

```
载入完成 ──► 每次「真正使用」都把计时清零 ──► 连续闲置满 闲置超时秒 ──► 自动退出内存
                                                                    └─► 下次要用再载入
```

- **什么叫「真正使用」**：调 `2516 申请推理许可`（= 要发请求了）。这是唯一刷新计时的信号。
- **什么叫「不算使用」**：调 `2514 查状态` **不刷新**。故意的 —— 否则监控程序一直轮询，模型永远退不掉。
- **所以用模型前必须走 `2516`**。绕过许可直接连模型端口发请求，底座不知道，模型可能正被用却被判闲置退出。

**关于「传 0 = 永不自动退」**：能力是有的，但**不推荐**。

理由：`0` 等于回到「拉起就一直占着内存」，那正是这套机制要解决的问题。实测踩过「模型进程空转 22 小时白占内存、还查不出是谁拉起来的」—— 一旦允许长期 `0`，这个口子就又开了。

真需要常驻（比如反复载入代价很大的大模型），**优先给一个长值**（如 `3600` 一小时），而不是 `0`：

- 给长值：有人用就续，真没人用了仍然会退 —— 保留兜底
- 给 `0`：只能靠人记得手动释放 —— 一定会忘

`0` 留给「确实不能退」的少数场景（如对外提供稳定端点的服务模型）。

`2514 取模型服务状态` 的回执字段（实测 16 个，全部只读）：

| 字段 | 含义 |
|---|---|
| `状态` | 四态之一：`载入中` / `已载入` / `载入失败` / `已退出` |
| `存活` | 进程还在不在 |
| `端口就绪` | 就绪路径真通没通（`载入中` 时是假） |
| `进程号` | 系统 PID |
| `监听端口` | 实际端口（传 0 分配到的就是这个） |
| `模型短名` | 底座翻出来的 model 名，如 `Qwen3-8B-Q4_K_M` |
| `模型路径` | 校验过的完整路径；拉起时传纯名字则为空 |
| `模型类型` | 五个词之一 |
| `就绪路径` | 这个服务用的就绪判定路径 |
| `运行秒` | 进程活了多久 |
| `CPU毫秒` | 累计 CPU 时间 —— 连查两次增量为 0 = 进程在干烧 |
| `闲置秒` | 距上次真正使用过了多少秒 |
| `距自动退出秒` | 还剩多少秒自动退；`闲置超时秒` 为 0 时是 **`null`**（永不退） |
| `闲置超时秒` | 这个服务当初设的闲置阈值 |
| `载入超时秒` | 这个服务当初设的载入阈值 |

**推荐用法（不阻塞）**：

```
拉起 2512          → 拿到句柄，状态「载入中」
循环 2514 查状态   → 直到「已载入」，每次间隔 1~2 秒
2516 申请许可      → 拿到许可（这一步同时刷新闲置计时）
直连模型端口发请求 → 用完 2517 归还
```

巡检每 5 秒跑一轮，所以退出最多晚 5 秒生效（不是精确到秒的定时器）。

## 释放模型服务（2513）—— 两个参数，幂等

```json
{"编号": 2513, "命名值": {"服务句柄": {"类型标签": 6, "值": 900001}, "强制": false}}
```

| 参数     | 说明                                                                     |
|----------|--------------------------------------------------------------------------|
| 服务句柄 | `2512` 的回执                                                             |
| 强制     | **假** = 常规释放：进程不退就保留条目、待下次重试；**真** = 不管退没退一律摘除条目、解封句柄与端口 |

- **幂等**：句柄本来就不在（从没起过 / 已被别的请求释放）也回真。并发释放同一个句柄，全都回真，不会有人收到「服务无效」。
- **强制=真** 是逃生口：进程彻底卡死（SIGKILL 也收不走）时，用它解封。代价是可能留下孤儿进程，必须由调用方明确选择。

## 多模型并存：端口、许可、内存

端口**一模型一个**，服务表允许多条同时存在。同时请求多个模型时的裁决：

| 问题 | 裁决 |
|---|---|
| 端口怎么分 | 传 0 自动分配，**分配与预占在同一把锁内完成**，并发也不会撞（实测 8 线程同时拉起 → 8 个端口全不同） |
| 谁能同时推理 | **按服务分槽**：同一个模型内排队（同进程共享 GPU 上下文与 KV 缓存，挤进去互相拖慢、读数归因不到谁）；**不同模型并行**（各自独立进程，由驱动调度） |
| 待命占不占许可 | 不占。已拉起但没人请求的模型不占推理许可 —— 但它**会在闲置超时后自动退出内存**（默认 15 分钟），不是永久挂着 |
| 内存会不会爆 | 拉起前算预算，不够就 `2506 资源受限` |

三个许可能力：

| 能力 | 用法 |
|---|---|
| 2516 申请推理许可 | `服务句柄` + `等待毫秒` + `租约毫秒`；等待上限 3 秒（传 5000 会先撞内核 5 秒预算判 `4 超时`）；租约 5 秒 |
| 2517 归还推理许可 | `许可句柄`（2516 的回执） |
| 2518 取推理排队快照 | 无参数；看每个服务当前几个持有、几个在排队 |

## 模型引用转化器（传路径，别传名字）

`2501` 的 `模型` 和 `2512` 的 `模型引用` **都收模型文件绝对路径**，底座负责翻译：

| 你传什么 | 底座怎么翻译 | 效果 |
|---|---|---|
| `/…/Qwen3-8B-Q4_K_M.gguf` | 先校验文件在不在 → 取名去扩展名 `Qwen3-8B-Q4_K_M` | 不存在当场报 `2513`，不等推理才炸 |
| `qwen3`（纯名字） | 原样当 model 名 | 兼容老写法；但机器上没有这个模型不会报错 |

**为什么坚持传路径**：传纯名字时底座无从校验——模型在不在本机没人知道，要等推理那一步才炸；传路径当场炸，错得早、错得准。

模型类型**不从文件名推断**，全靠调用方写。猜测值顶替调用方表态等于留后门，这条已经删掉了。

## 四个坑（都是真撞出来的）

| 错误写法           | 真实报错                                             |
|--------------------|------------------------------------------------------|
| 漏传任意一个参数   | 400 缺参数「X」：本能力这一行没有声明默认值          |
| 静态请求头传 {}    | 25 输入形状不符                                      |
| 消息列表传普通数组 | 400 每一项必须是 {"类型标签":N,"值":V}               |
| 元素字段用裸值     | 同上（元素本身也要 101 对象）                        |

**结论：复合参数不能靠「裸值自动装箱」，必须显式写出来。**

## 缓存：模型层有，底座层没有

同一段 652 token 前缀连发三次：

| 第几次 | 耗时    | prompt token | 命中缓存   |
|--------|---------|--------------|------------|
| 1      | 0.67 秒 | 652          | 0          |
| 2      | 0.44 秒 | 652          | 646（99%） |
| 3      | 0.44 秒 | 652          | 646        |

- 模型层：llama-server 的 prompt cache **默认就开**，不用配
- 底座层：**不缓存**，每次真请求

**三铁律**：

1. 长期不变的内容（身份、产品资料、规则）放最前面，越长越划算
2. 历史只追加、不改写 —— 中间插一句前缀就断，后面全部重算
3. 会变的东西（时间戳、请求 ID、本次参数）只放当前问题那一条里

反例：把「今天是 X 月 X 日」拼进系统提示词 ⇒ 每次前缀都不同 ⇒ 命中率归零。

## 模型服务的三个必查口径

| 项       | 正确口径                                   | 错误口径                             |
|----------|--------------------------------------------|--------------------------------------|
| 就绪判定 | 端口在听 + 就绪路径 200 + `/health` 非 503 | 只看端口 / 只看 `/v1/models`         |
| 等待上限 | 单次 ≤ 3 秒，慢就循环调                    | 传 5000（撞内核预算，报成 `4 超时`） |
| 空闲判定 | `2514` 的 `闲置秒`（距上次真正使用多久）    | 看 GPU 利用率                        |
| 干烧判定 | 连查两次 `CPU毫秒`，增量为 0                | 看 GPU 利用率                        |
