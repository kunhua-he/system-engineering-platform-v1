# 全局连接器与全局网关（拓扑保证：造不出第二条腿）

上级：系统工程平台 V1 ／ 落点：`项目文档/设计文档/全局连接器与网关.md`
相关：`README.md` 第六节（分层与依赖方向）· `资源网关口.md`（资源那一侧的同一条规则）· `多语言兼容实现.md`（跨边界只走定长槽）· `开发规范.md` B2/B5

**本文是一条裁定**：**一个全局连接器 + 一个全局网关，一层一层往下**。

**要保证的东西**：**不会造出第二条腿。**

---

## 一 为什么纪律保证不了，拓扑才能保证

「不许造第二条腿」写成纪律，只能事后判红。真正想保证它，得让第二条腿**无处可接**：

> **每条腿都是一条「从上层通到下层的路径」。路径要存在，就必须有一个出入口。**
> **出入口是可数的。所以「只有一条腿」等价于「每类出入口恰好一个」。**

纪律说「不要造」，拓扑说「造了也接不上」——后者才是保证。

---

## 二 拓扑（一层一层往下）

```text
        前端呈现（纯 UI，零逻辑）
              │  ← 同源相对路径，前端不写死端口
              ▼
   ┌──────────────────────────┐
   │  全局网关（对外接口面）    │  全平台唯一的对外门
   └──────────────────────────┘
              │  ← 唯一腿
              ▼
   ┌──────────────────────────┐
   │  全局连接器（跨语言适配）  │  全平台唯一的跨边界收口
   └──────────────────────────┘
              │  ← 唯一腿
              ▼
   ┌──────────────────────────┐
   │  运行内核（唯一底层）      │  任何调用都必须经此
   └──────────────────────────┘
          │              │
          ▼              ▼
   扩展装载（能力）   资源网关口（资源）
   提供能力           访问不透明外部
```

**三条规则**：

1. **每一层只跟下一层说话**，不跳层、不反向、不同层互依（README 第六节）。
2. **每一类出入口恰好一个**。多一个就是第二条腿。
3. **上层不许有自己的通往下层的路**。前端不许直连内核；网关不许绕过连接器直连扩展实现。

---

## 三 两个「全局」各管什么

| 全局件 | 管什么 | 唯一性体现在 |
|---|---|---|
| **全局网关** | **对外**：一切来自外面的请求都从这里进 | 全平台只有一个对外门；不许有第二个 HTTP 面、第二个 CLI 入口、第二个 SDK 专用入口 |
| **全局连接器** | **跨边界**：一切跨进程 / 跨语言 / 跨机器的访问都从这里走 | 全平台只有一个 C ABI 边界；不许给某语言开专用通道（`开发规范.md` B5） |

**两者都不做业务判断。** 网关只做协议翻译，连接器只做形状翻译——业务判断在内核与扩展里。

---

## 四 可判定的判据（这是本节的价值所在）

「只有一条腿」是**可数的**，所以能机器判。每类出入口恰好 1 个：

| # | 判据 | 怎么数 |
|---|---|---|
| 1 | 全平台只有一个**对外监听**（socket / HTTP 面） | 全仓搜监听调用点，恰好 1 处 |
| 2 | **宿主侧**的对外 C ABI 边界恰好 **1 组** | 搜导出符号，但**排除扩展接缝**——见下面的「两个方向」 |
| 3 | 全平台只有一个**内核入口**（读契约 → 建注册表 → 交控制权） | 恰好 1 处调用 `载入` |
| 4 | 全平台只有一个**资源出入口** | 恰好 1 处读资源清单 / 派发资源调用 |
| 5 | **不许跳层 · 不许反向** | 抽「依赖边」（一个包依赖另一个包）。每条边必须连接分层链上**相邻**的两层，且方向必须自上层向下层 |
| 6 | 前端**不出现**解析 / 生成 / 校验逻辑 | 前端目录里恰好 0 处 |

### ★ 判据 2 要分方向：接缝是「每个扩展一组」，对外面才是「全平台一组」

实测抓出来的洞：`GetPlatformInfo` 是**扩展 → 宿主**那条**接缝**的导出——**每个扩展都有一个**，它不是「全平台的对外边界」。等编译器扩展导出自己的那份，按原写法数会变成 2 组、判据误报。

| 方向 | 谁导出 | 数 | 是什么 |
|---|---|---|---|
| **扩展 → 宿主**（向内） | 每个扩展各导出 `GetPlatformInfo` | **每个扩展恰好 1 个** | **接缝**。底座读扩展的声明就靠它 |
| **宿主 → 外面**（向外） | **全局连接器**（`跨语言适配/`） | **全平台恰好 1 组** | **对外边界**。任何语言、任何上层都只经它 |

判据 2 数的是**后者**。前者的正确判法是「每个扩展目录恰好 1 个导出」——它是接缝纪律，不是拓扑唯一性。

### ★ 第 5 条原先写错了（实测抓出来的）

**原写法**：「同一对层之间不许有两条边」。**这条是空转的**——层对只有一个，边数恒为 1，判据恒真。实测反证：适配器依赖 `装载入口` · `统一注册表` · `调用调度` **三个包**，那是**一条路**（一个节点要用下层的三样东西），按目标包算会被误报成「三条边」。

**改成「不许跳层 · 不许反向」**，因为**第二条腿的真身就是「跳过中间层」**：

- 前端直连内核（跳过网关与连接器）⇒ 跳层，报红
- 网关直连扩展实现（跳过内核）⇒ 跳层，报红
- 下层 import 上层 ⇒ 反向，报红

这两条判得了、也判得准：**跳层与反向都是「多了一条路」的充分表现**，而「边数」不是。

---

## 五 为什么这样就不会有第二套实现

「同一件事不许有两种形态」这条硬判据（`代码形态分工.md` 第五节）之所以难守，是因为**两个实现可以住在不同层、用不同语言，长得完全不像**。

拓扑把它变成一个**结构性事实**：只要出入口只有一个，两套实现就必然抢同一个出入口——要么合并，要么其中一个显式声明「我绕过了网关」。而后者是可判定的违规（判据 1/2/3/4 会同时报）。

**结论**：第二套实现不再靠「大家自觉不要写」，而是**写出来就会红**。

## 六 明确不做

| 不做 | 为什么 |
|---|---|
| 不做按用途分门（查询门 / 执行门 / 管理门） | 那是给人用的分法；agent 每多一个门就多学一套入口，成本乘在调用次数上 |
| 不做按语言分门（Python 专用口 / JS 专用口） | 一个适配器适配所有语言（宪法第 9 条）；专用口就是第二套实现 |
| 不做按资源种类分门（数据库口 / 文件口 / 参照实现口） | 资源种类会长，门不能跟着长；种类是**声明**里的事，不是拓扑里的事 |
| 不做「临时通道」 | 临时通道从不通临时；它只会在下次改动时变成既定事实 |
| 不让网关或连接器持有状态 | 持有状态就得管理状态的生命周期，那是内核的事；两者必须无状态，才可重启、可多实例 |
| 不用「全局单例」实现「全局唯一」 | 「唯一」指的是**拓扑上只有一条路**，不是指进程里只有一个对象。用单例实现唯一性，就同时丢掉了多实例安全 |
