# 接口面形状（冻结）

上级：系统工程平台 V1 ／ 落点：`项目文档/设计文档/接口面形状.md`
相关：`README.md` 第二节（两个角色）· 第八节（冻结项）· `两个角色与接口面.md`（为什么这样分面）· `多语言兼容实现.md`（槽与类型标签）· `代码形态分工.md`（各节点形态）

**本文是冻结件。** 它冻结的是 `对外接口面/` 的**对外形状**：端点 · 请求体 · 返回体 · 错误体。冻结项一旦公布，**只许新增旁路字段，不许改旧字段含义、不许改旧端点语义**（README 第八节）。

**为什么现在就要冻**：`对外接口面/调用接口面/`（Rust）与 `前端呈现/网页应用/`（纯 UI）两件都只能照着形状写。形状不冻，两件会各自长出一套，然后靠联调对齐——那就是漂移。

---

## 一 一条判据决定全部取舍

> **使用角色：第一次用不需要读文档就能调对。**

这条判据把设计逼成一个形状：**根端点自己就是说明书**。agent 的第一次调用是 `GET /接口`，它的返回里同时给出「有哪些端点」和「有哪些能力」。从此不需要第二份文档。

推论（都是判据的直接后果，不是偏好）：

| 由此得出 | 因为 |
|---|---|
| **不做鉴权、不发 token** | 「要先拿 token」就是违反判据 |
| **只监听回环地址** | 没有鉴权，就必须只对本机开放 |
| **不做分页** | 契约读一次就是全量；「翻页查能力」是第二个动作 |
| **不做握手 / 会话 / 连接管理** | 入口无状态；不存在「先连上再调」 |
| **不做版本协商** | 契约版本随根端点一起返回，客户端不需要协商 |
| **端口只有一个来源** | 端口写在 `契约声明/平台声明.json` 里；前端**不写死端口**，用同源相对路径（上一版就是前端默认端口与网关端口不一致，两头各写一份） |

## 二 端点总表（四个，就这些）

传输：本机 HTTP/1.1，请求与响应体一律 `application/json; charset=utf-8`。

| 方法 | 路径 | 角色 | 做什么 |
|---|---|---|---|
| `GET` | `/接口` | 使用 | **自描述根**：端点表 + 能力总清单 + 契约版本 + 端口来源 |
| `GET` | `/接口/能力/<编号>` | 使用 | 单条能力的完整契约：参数表（**行序即契约**）· 返回表 · 可抛错误码 |
| `POST` | `/接口/调用` | 使用 | 报编号 + 按行序填值 → 结构化结果 |
| `POST` | `/接口/声明` | 维护 | 写一份声明（面先校验，过了才落盘到 `契约声明/`） |

维护侧的**读**走 `GET /接口/能力/<编号>` 与 `GET /接口`（读与调同一个入口，不另开一套文档接口）；**待分配号**由 `POST /接口/声明` 的 `编号` 字段留空时由面分配（见 §五）。

## 三 使用侧形状

### `GET /接口` → 自描述根

```json
{
  "契约版本": { "主": 0, "次": 1, "修订": 0, "构建": 1 },
  "声明格式号": 20000101,
  "端口来源": "契约声明/平台声明.json 的 接口端口；前端一律用同源相对路径，不写死",
  "端点": [
    { "方法": "GET",  "路径": "/接口",             "说明": "本清单" },
    { "方法": "GET",  "路径": "/接口/能力/<编号>",  "说明": "单条能力的契约" },
    { "方法": "POST", "路径": "/接口/调用",         "说明": "体：{\"编号\":N,\"值\":[...]}；值按契约行序" },
    { "方法": "POST", "路径": "/接口/声明",         "说明": "写声明；面校验通过才落盘" }
  ],
  "能力": [
    { "编号": 1105, "名称": "反解容器", "参数个数": 1, "返回类型": 5 },
    { "编号": 1106, "名称": "编译",     "参数个数": 1, "返回类型": 5 }
  ]
}
```

`能力` 是**全量**，不是首页。未载入的扩展其能力不在表里（宪法第 6 条：未命中返回空，不是报错）。

### `POST /接口/调用`

请求：

```json
{
  "编号": 1105,
  "值": [ { "类型标签": 5, "值": "<base64 字节集>" } ]
}
```

- `值` 按契约 `参数表` 的**行序**对位；空位写 `{"类型标签":0,"值":0}`（空槽），**不许省略位次**（省略就是改行序）。
- 每个值都是**带类型标签的定长槽**（宪法第 3 条：类型标签在槽内）。
- 文本 ⇒ `值` 是 JSON 字符串（UTF-8，长度由 JSON 自带）；字节集 ⇒ `值` 是 base64 字符串。两者靠 `类型标签` 区分，不靠形状猜。

成功返回：

```json
{
  "成功": true,
  "值": [ { "类型标签": 5, "值": "<base64 字节集>" } ],
  "耗时微秒": 812
}
```

失败返回：

```json
{
  "成功": false,
  "错误": {
    "码": 1,
    "段位": 0,
    "名称": "提供者未载入",
    "可重试": false,
    "可自愈": true,
    "需人工": false
  },
  "耗时微秒": 8
}
```

**失败不抛 HTTP 5xx。** HTTP 状态码只表达「请求本身合不合法」（400 = 请求形状不合法），业务失败一律 200 + `"成功": false`。理由：失败是**可编程处理的数据**（本项目三条补缺陷之一），把它塞进 HTTP 状态码就等于让调用方去解析协议层，而协议层不该承载业务。

### 返回必须同时回答三件事（判据）

| 问 | 答在哪 |
|---|---|
| 成功没成功 | `成功` 布尔，不靠猜、不靠异常 |
| 拿到什么 | `值` 数组，每项自带 `类型标签`，不需要二次解析 |
| 失败为什么 | `错误.码`，且四项登记（`段位 · 可重试 · 可自愈 · 需人工`）随包带回 |

**判据**：把这个返回原文直接喂给另一个 agent，它不需要额外上下文就能决定下一步做什么。

## 四 维护侧形状

### `POST /接口/声明`

请求（写入形状 = 冻结项）：

```json
{
  "类别": "能力",
  "编号": null,
  "正文": { "名称": "反解容器", "说明": "…", "参数表": [ … ], "返回类型": 5, "可抛错误码": [1101] }
}
```

- `类别` ∈ `能力` · `类型` · `错误码` · `通知号`。
- `编号` 为 `null` ⇒ **面自动分配**（手填必然撞号；「一个号一个文件」已把撞号变成文件名冲突，自动分配再省一步）。自动分配只从该层号段的空洞里取，**永不回收作废号**。
- `正文` 的字段形状 = `契约声明/格式说明.md` 里那一类 JSON 的形状，**逐字一致**。面不改名、不重排、不加壳。

面校验通过：

```json
{ "成功": true, "编号": 1105, "落盘": "契约声明/能力声明/1105.json", "指纹": "…" }
```

面校验失败：

```json
{
  "成功": false,
  "校验": [
    {
      "项": "编号落在自己那一层号段内",
      "缺什么": "1105 落在支持库段 1000–6999，但类别 能力 的编号必须与声明层一致",
      "为什么不能自愈": "层号段由 平台声明.json 固定；面不能替调用方换层，换层等于换归属"
    },
    {
      "项": "可抛错误码都已登记",
      "缺什么": "1101 不在 错误码表/ 里",
      "为什么不能自愈": "错误码必须先登记四项（段位·可重试·可自愈·需人工）才允许被抛出；面不替它编四项"
    }
  ]
}
```

**`为什么不能自愈` 不许写「需要人工确认」这种废话。** 必须写清是哪一个事实挡住了自动补全；能自愈的当场自愈并在返回里报告（例如补上可推导的 `段位` 字段）。

### 面的两条硬规则

1. **面是 `契约声明/` 的唯一写入口。** 绕过面直接改文件 = 违规（判据见 README 第九节）。
2. **面只做结构校验，不做业务判断。** 面不判断「这个能力该不该存在」，只判断「它合不合契约形状」。

## 五 部署形状（前后端怎么分开）

```text
浏览器 / 纯 UI（前端呈现/网页应用/）
        │  同源相对路径 fetch，前端零逻辑、零端口硬编码
        ▼
对外接口面（Rust，本机 HTTP）── 唯一对外门
        │  唯一腿：转调 跨语言适配/适配器实现/
        ▼
跨语言适配/适配器实现/ ── 读契约 → 装载内核 → 转发调用（全平台只此一个）
        ▼
运行内核（装载入口 · 统一注册表 · 调用调度 …）
```

三条不许：

1. **前端不许有解析/生成/校验逻辑**——前端是纯 UI。任何判断都在后端。
2. **接口面不许绕过适配器直连扩展实现**（分层链：`契约声明/ ← 运行内核/ ← 跨语言适配/ ← 对外接口面/ ← 前端呈现/`）。
3. **不许出现第二个对外门**——`对外接口面/` 只有一个；多一个门就多一套形状要同步。

静态文件（前端构建产物）由接口面进程托管，**同源**，所以不需要 CORS、不需要第二个端口。

## 六 待裁与待实测

| # | 待什么 | 现状 |
|---|---|---|
| 1 | 接口端口的具体数值 | 未定数。写进 `平台声明.json` 的 `接口端口` 字段（唯一来源） |
| 2 | 单次调用是否要带 `调用方标识` | 未裁。倾向不带（带了就是变相鉴权，违反 §一 判据） |
| 3 | 大返回（例如容器往返的字节集）走 JSON base64 还是直传二进制 | 未裁。倾向 JSON base64 先跑通，实测超时或体积不可接受再开旁路端点 |
| 4 | 前端托管方式（同进程静态文件 / 独立 dev server） | 未裁。倾向同进程——同源省掉 CORS 与第二个端口 |
| 5 | 声明编写面的可读页面形态 | 未裁。倾向**两者兼有**：结构化端点（agent 写）+ 纯 UI 页面（人看，非主线） |
