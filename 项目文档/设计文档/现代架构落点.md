# 现代架构落点

上级：系统工程平台 V1 ／ 落点：`项目文档/设计文档/现代架构落点.md`
相关：`项目文档/设计文档/语言选型对照.md`（语言层）· `README.md`（架构层）

**本文解决的问题**：V1 的九条宪法与三条补缺陷是**不变量**，但它们要在今天的部署环境里跑。哪些是架构、哪些只是落点，必须先分开，否则换个部署形态就要动宪法。

---

## 一 先把「架构」与「落点」分开

| | 架构 | 落点 |
|---|---|---|
| 是什么 | 不变量：唯一入口 · 静态契约 · 定长数据槽 · 所有权单向 · 双向通知 · 按号取用 · 号段只增 · 多形态 · 语言无关 | 具体技术：进程模型 · 传输载体 · 存储引擎 · 隔离手段 · 部署方式 |
| 换一个要动什么 | 动它就要重审全部实现 | 换它只动装配，不动任何能力实现 |
| 判据 | 跨形态必须一致 | 每个形态各一套，可整体替换 |

**判据：如果某个选择一换就得改宪法，那它根本不是落点，是架构漏进了落点。** 本文所有内容都必须是「换掉不影响任何能力实现」的东西。

---

## 二 现代架构的六个形态（要能落的靶子）

今天真实存在的部署形态，收敛成六个。V1 必须能落进**全部六个**，且能力实现代码不变。

| # | 形态 | 谁在用 | 典型诉求 |
|---|---|---|---|
| 1 | **单机单进程**（内嵌库） | 桌面应用 · 命令行 · 插件宿主 | 零依赖分发、启动快 |
| 2 | **单机多进程**（宿主 + 能力进程） | 要求隔离与故障不扩散的场景 | 一个能力崩不带走整机 |
| 3 | **容器化服务**（一份制品多副本） | 服务端、多租户 | 水平扩展、滚动升级 |
| 4 | **前置网关 / 边车** | 已有服务网格、需要协议转换与鉴权限流 | 不改能力实现就接进既有体系 |
| 5 | **边缘沙箱**（WASM / 浏览器 / 轻宿主） | 不可信代码、多租户插件 | 硬隔离、按调用计费 |
| 6 | **事件驱动 / 按次** | 无服务器、批处理、定时任务 | 无常驻进程、按次拉起 |

**六个形态共用同一份 `契约声明/`**。形态差异只体现在 `构建装配/形态装配/` 与 `跨语言适配/边界协议/`。

---

## 三 边界协议的四种落点（最关键的决策）

宪法说「只有一个边界」，落点说「边界可以有四种载体」。两者不矛盾：**边界是形状，载体是传输**。

| 落点 | 载体 | 何时用 | 代价 |
|---|---|---|---|
| **A 进程内 ABI** | Rust `cdylib` + `extern "C"` + 由契约生成的绑定 | 形态 1、2（同机）；延迟要求最苛刻 | 崩溃同进程扩散（靠形态 2 的多进程补偿） |
| **B 本机 IPC** | Unix domain socket / 命名管道；线协议 | 形态 2、3（同机跨进程） | 一次序列化 + 拷贝；要定帧与背压 |
| **C 网络** | HTTP/JSON · gRPC · MCP 形态 | 形态 3、4、6；跨机与对外 | 网络不可靠必须显式处理；超时与重试口径要统一 |
| **D WASM 组件** | WASI 组件模型 | 形态 5；不可信代码 | 需宿主提供全部系统能力；数据交换有拷贝成本 |

**四种载体都读同一份契约，都产出同一套号段与错误码。** 调用方在 A 上拿到的错误段位，在 D 上必须一模一样——否则「错误可编程」就只在一个形态里成立。

这就是参照物最值得借的一点：**契约是数据，不是接口**。它一旦被物化成静态可读的结构，边界就能随便换载体；反过来，契约只存在于代码里，换一次载体就要重写一遍。

## 四 逐节点落点对照

| V1 节点 | 形态 1 单进程 | 形态 2 多进程 | 形态 3 容器服务 | 形态 5 边缘沙箱 |
|---|---|---|---|---|
| `契约声明/` | 编译进制品 | 编译进制品 | 随制品发布 + 可被外部读取 | 随组件发布 |
| `运行内核/装载入口/` | 进程内初始化 | 每个能力进程各一次 | 每副本一次 | 宿主侧一次 |
| `运行内核/统一注册表/` | 静态表 | 每进程一份只读副本 | 每副本一份 | 宿主侧 |
| `运行内核/定长数据槽/` | 进程内指针 | 序列化过管道 | 序列化过网络 | 线性内存 |
| `运行内核/内存分配器/` | 单一分配器 | 各进程各自分配器，跨进程只传值 | 同左 | 由宿主分配 |
| `运行内核/实例状态/` | 实例句柄 | 实例句柄 + 进程边界 | 实例句柄 + 副本局部 | 每次调用独立 |
| `运行内核/调用调度/` | 同步超时 | 进程级超时与配额 | 副本级 + 上游超时 | 宿主级 |
| `运行内核/调用留痕/` | 本地环形缓冲 | 各进程汇总 | 导出到外部可观测后端 | 由宿主代记 |
| `跨语言适配/边界协议/` | A | B | B 或 C | D |
| `跨语言适配/语言绑定/` | 生成静态库/头 | 生成客户端 | 生成客户端 + SDK | 生成宿主接口 |
| `能力实现/*` | **同一份代码** | **同一份代码** | **同一份代码** | **同一份代码**（受沙箱能力限制的除外） |
| `前端呈现/*` | 内嵌 UI | 内嵌 UI | 独立前端 | 宿主 UI |
| `构建装配/形态装配/` | 出静态库/可执行 | 出宿主 + 能力进程 | 出镜像 | 出组件包 |
| `构建装配/上线切换/` | 覆盖文件 + 重启 | 滚动替换能力进程 | 滚动升级 + 灰度 | 版本化组件 |

**看最后三列**：能力实现一栏是同一份代码。这就是「落点可换」的证明方式——如果换形态要改能力实现，说明架构没落干净。

## 五 状态落点

宪法说状态显式持有，不落进程级全局。落点层面：

| 状态种类 | 落点 | 说明 |
|---|---|---|
| 调用期临时状态 | 调用栈 / 实例句柄 | 不进任何全局 |
| 跨调用会话状态 | 显式会话句柄，由调用方持有 | 调用方负责释放，对应「所有权单向」 |
| 需持久化的状态 | 进程内嵌入式库 → 可换外部存储 | 存储引擎是落点；换引擎不动能力实现 |
| 跨副本共享状态 | 外部存储 | 只在形态 3 出现，且必须显式声明 |

**明确不做**：把状态塞进中间件来换取「无状态」的表象。那只是把全局变量搬到别处，多实例下照样互相污染，而且污染路径更难查。

## 六 可观测落点（对应「调用留痕」）

| 层 | 落点 |
|---|---|
| 记录形态 | 结构化事件（谁 · 调什么 · 入参指纹 · 结果 · 耗时 · 追踪号） |
| 落盘方式 | 本地环形缓冲，**不阻塞调用**；满了按策略丢弃并计数 |
| 导出 | 可选对接既有可观测后端；导出失败不影响调用 |
| 追踪号 | 一次调用一个，跨进程/跨网络透传，四个边界载体都带 |

判据：**留痕缺席时调用照样成功，留痕存在时调用不变慢。** 做不到这条就说明留痕长在关键路径上，是架构问题不是落点问题。

## 七 交付与上线落点

对应 `构建装配/`：

| 环节 | 落点 |
|---|---|
| 可重现构建 | 固定工具链版本 + 锁文件 + 去掉时间戳类不可复现输入 |
| 制品指纹 | 构建产物内容指纹，随契约版本一起公布 |
| 完整性校验 | 装载前校验指纹；不匹配即拒绝装载（对应「可装载性判定」） |
| 上线方式 | 形态 1 覆盖文件；形态 2 滚动替换进程；形态 3 灰度；形态 5 版本化组件 |
| 回退 | 上一版制品必须仍可装载（对应宪法第 6 条「旧调用方调新内核不得崩」） |

**两条已裁的边界（2026-09-27，依据 `项目文档/决策记录/2026-09-27_待裁九项按老仓设计哲学裁决.md` 裁决 4 / 5）**：

- **完整性 = 内容指纹，不做签名 / 信任根。** 制品身份是**构建指纹**（源内容摘要 + 生成器版本 +
  契约版本），装载前重算指纹比对、不符即拒 —— 它已能回答「这份制品是不是这份源出的、有没有被改过」。
  签名要密钥与信任根，而「**相对安全，不做绝对安全**」（老仓第 9.5）·「**0 加密**」（第 9.1）·
  「**不做的结论同样是结论**」（第 11.1）。**不做**的结论与理由记在 §八。
- **多副本 / 灰度不进底座，落在编排器那一层。** 底座只覆盖形态 1 / 2 的**单机单实例**；形态 3 的
  滚动升级与灰度是**编排器**的事（§九 形态 3 的「上线方式」列）。现在**不立项**，理由记在 §八。

## 八 现代架构里我方明确**不落**的东西

现代架构里有一批流行做法与我们的宪法直接冲突。逐条写明不做，避免后人按惯例补回来：

| 流行做法 | 为什么不做 |
|---|---|
| **服务发现 / 动态注册** | 宪法第 2 条要求读一次就知道有什么。注册表是静态的，不需要运行时发现 |
| **分布式配置中心** | 契约声明是唯一事实源。多一个配置源就是多一处漂移 |
| **每服务一份契约** | 契约分裂是微服务最常见的病。我方一份契约、多个形态 |
| **编排 / 工作流引擎进平台** | 平台不做业务判断。编排属于调用方 |
| **用消息队列掩盖同步失败** | 失败必须可编程处理。把失败异步化等于让它不可见 |
| **为了「无状态」把状态搬进中间件** | 见第五节：只是把全局变量挪个地方 |
| **边车做协议转换时改写语义** | 边车只能换载体，不能改号段、错误码与调用形状 |
| **按语言分家做多套实现** | 违反宪法第 9 条。一个适配器，绑定由契约生成 |
| **给每个能力单独设超时口径** | 超时是调度层的事，口径必须唯一，否则单项超时不可解释 |
| **把留痕做成必需路径** | 见第六节判据：留痕不能进关键路径 |
| **制品签名 / 信任根 / 供应链校验** | **不做**（2026-09-27 裁）。制品完整性沿用**内容指纹**（§七）：构建指纹 + 制品不可变判据已能回答「是不是这份源出的、有没有被改过」。签名要密钥与信任根，而「相对安全，不做绝对安全」（老仓第 9.5）·「0 加密」（第 9.1）；按「不做的结论同样是结论」（第 11.1）写明。**反向样本**：出现签名机制而拿不出「更快 / 更稳」的实测两列 ⇒ 违第 11.1 |
| **多副本 / 灰度 / 双跑分担进底座** | **不做**（2026-09-27 裁）：它是**编排器那一层**的事（形态 3 的落点，§九），不是底座能力。底座只有「单机单实例」这一种上线方式（覆盖 + 重启）。现在**不立项** —— 按第 11.1「不做的结论同样是结论」，理由写在这里，不许默认补回来 |

## 九 一页速查

| 形态 | 边界载体 | 状态落点 | 隔离手段 | 上线方式 | 首要风险 |
|---|---|---|---|---|---|
| 1 单机单进程 | A 进程内 ABI | 实例句柄 | 无（同进程） | 覆盖文件 + 重启 | 一崩全崩 |
| 2 单机多进程 | B 本机 IPC | 实例句柄 + 进程 | 进程边界 | 滚动替换 | 进程管理复杂度 |
| 3 容器化服务 | B 或 C | 外部存储（显式） | 容器 | 灰度 + 滚动 | 状态与副本一致性 |
| 4 前置网关 | C 网络 | 由下游决定 | 网关 + 下游 | 与下游联动 | 边车改写语义 |
| 5 边缘沙箱 | D WASM | 每次调用独立 | 沙箱硬隔离 | 版本化组件 | 宿主能力不足 |
| 6 事件驱动 | C 网络 | 外部存储 | 平台级 | 版本化函数 | 冷启动与超时口径 |

## 十 待实测与待裁

### 十.0 已裁（2026-09-27）：沙箱是「模式」，不是第二载体（#23）

**裁决**：`载体 = 进程内 | 进程池 | 沙箱` —— 这三者是**同一个载体形状的三个模式**，**不是三种载体**。
沙箱（与进程池）是**可选的收紧手段**：**默认走 `进程内`**（能力不受牺牲），要隔离 / 白名单时**只换模式号**，
而调用形状、号段、错误码**逐字不变**。**不新建载体、不加第二原语。**

**依据**（老仓《设计哲学》，来源链见 `项目文档/决策记录/2026-09-27_待裁九项按老仓设计哲学裁决.md` 裁决 4）：

- **第 8 条②**「底子不同但格式一样 ⇒ **加「模式」变量**（输入 / 输出 / 存储格式一样、目的一样），
  **用户只选模式号，不感知内部差异**」—— 进程内 / 进程池 / 沙箱正是「底子不同（谁在执行）、格式一样
  （定长数据槽）」⇒ 落成**模式**，不落成新载体。
- **第 9.5①**「隔离 / 白名单类机制一律定位为**可选的收紧手段**，默认不得牺牲能力」—— 沙箱是收紧手段，
  **默认是进程内**；把它当第二载体，等于让默认路径也要迁就它。

**为什么不是第二条腿**：`黑盒体` 是**载体无关的形状**（`项目文档/设计文档/资源网关口.md` §四：数据只走
定长数据槽，槽自描述 ⇒ 换载体不改形状）。既然形状不因载体而变，**第二载体不产生任何新表达力**，
只会多一条「同一件事两套实现」的路（第 8.2）。这正是第 8 条② 的「加模式」—— **它不是新增，是收拢**。
**反向样本**：出现第二种**载体形状**（而不是模式值）⇒ 违第 8.2。

> 另见 `项目文档/设计文档/进程隔离方案.md`：它推荐的「A 子进程（每个扩展一个进程 + IPC）」是本条的
> **`进程池` 模式**的一种落地，**不是第二种载体形状** —— 模式号变，形状不变。

**从本条推不出的（仍未裁）**：哪些能力**不能**进沙箱（见下第 3 条）· 进程池 / 沙箱的进程管理落点（第 2 条）。

1. **边界载体 A 与 B 的同一性实测**：同一份契约在进程内与跨进程下，错误码与调用形状是否逐字一致。这是「四种载体同一套语义」的唯一验证方式。
2. **形态 2 的进程管理落点**：能力进程池由谁拉起、崩了谁重拉、与 `调用调度/` 如何分工。未裁。
3. **形态 5 的能力边界**：哪些能力实现**不能**进沙箱（需要真实文件系统、真实网络、真实设备的），需逐能力标注。未裁。
4. **留痕的丢弃策略**：环形缓冲满时是丢最旧还是丢最不重要的，以及计数如何暴露。未裁。
5. **与 `语言选型对照.md` 的联动**：若最终边界载体以 C 网络为主，语言自由度变大，Rust 的首选理由会从「ABI 可控」转向「无 GC 停顿 + 漂移抵抗」。
