# 两个角色与接口面

上级：系统工程平台 V1 ／ 落点：`项目文档/设计文档/两个角色与接口面.md`
相关：`README.md` 第二节（角色）· 第五节（目录树）· `语言选型对照.md`（语言层）· `现代架构落点.md`（部署层）

**本文解决的问题**：平台首先是给 agent 用的。agent 有两个身份——**调用的 agent** 和 **维护的 agent**。这两个身份要的东西正好相反：调用要极简到不用学，维护要轻到一条命令。本文把这两个面各自「简到什么程度」写成可判定的规格。

---

## 一 为什么要按角色分面，而不是按功能分面

按功能分面（查询面、执行面、管理面、配置面）是给人用的分法：人愿意学四套东西。agent 不愿意——每一次调用都要重新理解一次入口，成本乘在调用次数上。

按角色分面只有两个门，判据也因此只有两条：

| 角色 | 面 | 判据 | 违反的表现 |
|---|---|---|---|
| 使用角色 | `对外接口面/调用接口面/` | **第一次用不需要读文档就能调对** | 要先读接口说明、要先注册、要先握手、要先拿 token |
| 维护角色 | `对外接口面/声明编写面/` + `构建装配/一键验证/` | **改完一条命令、全量验证秒级返回** | 要跑多条命令、要等分钟级、要选模块跑 |

**这两个判据是本仓的验收线。** 任何设计只要让其中一条变难，就是设计错误，不是"以后优化"。

## 二 使用面：极简到什么程度

### 一次调用的完整形状

```text
输入：能力编号 + 按契约行序排列的值
输出：结构化结果 —— 成功拿值，失败拿错误段位
```

就这些。没有第二个动作。

### 明确的「不做」

| 不做 | 为什么 |
|---|---|
| 不握手、不注册、不连接管理 | 入口无状态。不存在"先连上再调" |
| 不发 SDK 才算能用 | 绑定由契约生成；不生成绑定时，任何语言直接按边界说话也能调 |
| 不另开一套文档接口 | 读（有什么 · 怎么调 · 返回什么）与调走**同一个入口**。契约本身就能被读 |
| 不用异常当失败通道 | 失败是带段位的结构化码，调用方能编程判断可重试/可自愈/需人工 |
| 不做分页式发现 | 契约读一次就是全量。不存在"翻页查能力" |
| 不要求调用方记住状态 | 状态显式持有并作为句柄传回，调用方持有、调用方释放 |

### 一次返回必须同时回答三件事

1. **成功没成功**——不靠猜，不靠抛异常。
2. **拿到什么**——值与值的类型标签，不是一个需要二次解析的字符串。
3. **失败为什么**——错误段位（归属域 + 序号），且该段位在 `契约声明/错误码表/` 里登记过「可重试 · 可自愈 · 需人工」。

**判据**：把返回原文直接喂给另一个 agent，它不需要额外上下文就能决定下一步做什么。

## 三 维护面之一：声明在页面上写，不在文件里手改

### 为什么必须有一个面

手改声明文件，格式必然漂移：漏一个字段、编号撞车、引用了不存在的类型、错误段位没登记。这些错误在运行期才爆，而运行期是使用角色在承受。

所以 `契约声明/` **不接受手改**，写入只有一条路：`对外接口面/声明编写面/`。面是**结构化编辑器 + 校验器**，写下去就是合法的。

### 面上写什么

| 字段 | 面替你保证什么 |
|---|---|
| 能力编号 | 不重复、不复用；删除的号作废不回收（宪法第 7 条） |
| 名称与说明 | 非空、与编号一一对应 |
| 参数表 | 每一行必须来自 `契约声明/类型声明/`；**行序一旦公布即为冻结项** |
| 返回表 | 同上；返回类型必须显式（含类型标签） |
| 错误段位 | 必须是已在 `契约声明/错误码表/` 登记过的段位；**未登记的段位不许提交** |
| 形态适用 | 哪些部署形态支持该能力（联动 `现代架构落点.md`） |

### 面的两条硬规则

1. **面是唯一写入口**。绕过面直接改文件 = 违规（判据见 README 第九节）。
2. **面的写入形状是冻结项**。面的字段一旦公布，只许新增旁路字段，不许改旧字段含义（README 第八节）。

### 面同时要能被读

面不只写，也读：agent 想知道「现在有什么能力、怎么调」，走的是面的只读侧。人也能看，但**不是为好看设计的**——它是结构化面，不是给人填的表单。

## 四 维护面之二：一条命令，秒级全量

### 形状

```text
验证
→ 通过数 / 失败数
→ 逐条明细：哪一条 · 缺什么 · 为什么不能自愈
```

一条命令。一次全量。**没有第二个必跑动作。**

### 两档

| 档 | 做什么 | 耗时 | 何时跑 |
|---|---|---|---|
| **静态验证**（默认档） | 只做声明层比对：读全部声明 + 扫全部实现的公开符号 + 比对结构 | **秒级** | 每次改完都跑 |
| **实测验证**（按需档） | 静态验证的全部内容 + 超小型实测 | 慢一档 | 改动涉及行为时跑 |

### 分钟级是缺陷，不是档位

**没有"分钟级"这一档。** 全量验证跑到分钟级，那是纯粹的代码 bug，按 bug 处理。

修法是**并发**，不是放宽判据：

- **多线程**读声明与扫文件（IO 密集，等 IO 的时间远大于算的时间）。
- **多进程**做解析与比对（CPU 密集，用满核数）。
- **分片**：按能力、按文件、按类型切成互不依赖的分片，各自跑完再归并；片与片之间不许有共享状态。
- **不许串行复跑**：一处失败不触发"全量重跑一遍"，只重跑该分片。

判据：**默认档墙钟秒级。出现分钟级，先当 bug 查并发度与串行点，不许改判据、不许"再等等"。**

历史教训：上一版慢的真因不是磁盘慢，是**全仓串行扫描 + 并发下缓存失效**；把串行点去掉之后吞吐提升了一个数量级。所以"慢"通常不是机器的问题，是有一段代码在替所有分片排队。

### 为什么秒级可行

因为默认档验证的是**结构一致性**，不是行为正确性：

1. 读声明——纯文件读取，可并行。
2. 扫实现的公开符号——纯静态解析，**不编译**。
3. 比对——编号、参数行序、类型标签、错误段位、返回形状，全是集合比较。

全程没有编译、没有启动进程、没有跑用例、没有网络。这三件事都是纯 CPU 且可并行，秒级是设计的结果，不是优化出来的。

反过来，如果把「验证」做成「编译 + 启动 + 跑用例」，那必然是分钟级——那是行为验证，是另一档，**不该混进默认命令**。上一版把这两件事混在一起，代价就是默认命令慢到没人愿意跑。

### 明细必须说清「缺什么导致不能自愈」

只报红不给原因，等于把定位成本推给维护者。每条失败必须回答：**哪一条 · 缺什么 · 为什么不能自动补上**。能自愈的当场自愈并报告，不能自愈的给出人/agent 该补的那一个东西。

## 五 两个角色的接缝：契约一变，使用方零改动

```text
维护角色：在声明编写面上新增一个能力 → 跑一次静态验证（秒级）
                ↓  （同一份 契约声明/）
使用角色：下一次调用就能按新编号调到它，客户端一行不改
```

**判据**：新增一个能力，使用角色零改动即可调到它。如果要做下面任何一件事，说明契约不是唯一事实源：

- 给客户端发新版本
- 重新注册 / 重启 / 刷新缓存
- 改调用方的参数顺序
- 让调用方去读另一份说明

## 六 明确不做

| 不做 | 为什么 |
|---|---|
| 不做人类友好表单 | 人类用的概率不大。面是结构化面，不是给人填的表 |
| 不做"先注册再调用" | 宪法第 2 条：读一次就知道有什么，不需要运行时发现 |
| 不做多档超时口径 | 超时是调度层唯一口径，否则单项超时不可解释 |
| 不把验证做成"选模块跑" | 一次全量才有意义；选着跑等于把漏检藏起来 |
| 不让声明绕过面写入 | 手改声明就是格式漂移的源头 |
| 不在面上写业务判断 | 面只做结构校验；平台不做业务判断 |

## 七 待裁与待实测

1. **声明编写面的具体形态**：纯结构化端点 / 可读页面 / 两者兼有。未裁。
2. **静态验证的秒级目标要定数**：先定一个上限（例如全仓全量 ≤ 3 秒），再按它设计扫描面与并行度。未定数。
3. **实测验证的"超小型"要定判据**：多小算小、覆盖什么、多久算超时。未定。
4. **面与实现的先后**：先建面还是先建实现。倾向先建面——面定下来，声明形状就冻结了，实现只能跟着走。
5. **编号的分配方式**：面上自动分配还是手工填。倾向自动分配，手工填必然撞号。
