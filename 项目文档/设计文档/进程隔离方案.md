## 一 结论：进程内 `dlopen` ⇒ 一崩全崩

**取证到行**：扩展的机器码与网关**同地址空间** —— 装载走进程内 `dlopen`/`dlsym`（`对外接口面/调用接口面/examples/启动网关.rs::main` 的 `取扩展声明`，句柄不释放、全仓无 `dlclose`），调用走 `运行内核/统一注册表/src/占位项.rs::命令槽::已载入` 里的**裸函数指针** `执行`（`契约声明/src/lib.rs::执行函数`），`运行内核/调用调度/src/调度核心.rs::调度` 里 `unsafe { 执行(...) }` **同进程直接跳进扩展机器码**。

⇒ 扩展内一次越界写 / `panic!`（release 档 `panic = "abort"`）/ 死循环，都是**网关进程自身**的 SIGSEGV / abort / 挂死；网关**无信号处理器、无 `catch_unwind`、无看门狗、无 supervisor、单线程 accept**（`网关.rs::服务::跑` = `loop { self.处理一个连接()?; }`），超时只能事后判（`调度核心.rs` 与 `资源网关口` 都写明「进程内无法抢占执行方」）。**结论：一个外部扩展崩，网关进程整体终止，其余扩展随之不可用** —— 与准入判据 ①「不终止网关进程，剔除并报原因，其余照常服务」正面冲突。

**隔离 / 看门狗 / 重启机制：现在都没有**（子进程 / fork / exec 跑扩展 0 处；`看门狗`/`supervisor` 命中 0；`重启` 只描述部署动作；`catch_unwind` 生产代码 0 处；信号处理器 0 处；资源网关口 `载体::进程内 + 崩溃影响面::仅本资源` 被判 `隔离不自洽`）。

## 二 三个候选（一句话）与推荐

**共同前提**：边界只走定长数据槽（`跨语言适配/边界协议/边界协议.md` §三「槽自描述 ⇒ 换载体不改形状」）⇒ 三案都不动能力实现的参数/返回形状。

| 候选 | 一句话 |
|---|---|
| **A 子进程** | 每个扩展一个进程，网关经 IPC（载体 B）递槽调它；子进程边界由 OS 提供 |
| **B WASM 沙箱** | 扩展编成 WASM、网关用运行时在沙箱里实例化（载体 D）——需 WASM 运行时（违反零第三方依赖）+ wasm32 构建腿 + 1106 后端，三样都没到位 |
| **C 进程内 + 兜底** | 进程内不变、加看门狗重启；进程内无法可靠从 SIGSEGV 恢复，且看门狗随进程一起死 ⇒ 实质仍需外部监督进程，仍不满足判据 ① |

**推荐 A 子进程**：只有 A 今天就能交付判据 ① 要的硬边界（OS 提供进程边界），且它是把 `现代架构落点.md` 形态 2（单机多进程）落下来、不是新开形态；顺带让「超时」可落成真抢占（强杀扩展进程）。A 仍**恰好导出 `GetPlatformInfo`**（IPC 是宿主↔能力进程的载体，不是第二个导出面）。**WASM 在本项目首先是 `.能力包件` 的码段格式（包装形态），不是运行形态**（`能力包件.md` §一/§五）。

**A 的前置（未裁，先裁再施工）**：**进程管理落点**（谁拉起 / 崩了谁重拉 / 与 `调用调度/` 如何分工）——`现代架构落点.md` §十 待裁 2；以及「扩展进程崩溃被剔除」的结构化错误码（现无）；并需一条裁决把宿主↔能力进程通道归为**载体 B**（避免被判据 5 误判成第二条腿）。
