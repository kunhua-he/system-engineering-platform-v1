## 一 现状取证

### 1.1 扩展怎么被装进来的（扫描 → 装载 → 判定）

四段，全部落在**网关进程内**：

**① 扫描** —— `对外接口面/调用接口面/examples/启动网关.rs::main` 第二步。
读 `扩展装载/扩展根声明.json` 的 `种类[].目录`，对每个目录调 `子目录()`（按名字排序）得直接子目录，
逐个交给 `取扩展声明()`。`取扩展声明` 用 `是可装载库()` 判「后缀是不是 `.dylib/.so/.dll`」，
**要求目录内恰好 1 个可装载库文件**（`库文件.len() != 1` 即剔除）。

**② 装载（dlopen，不是别的）** —— 同一个 `取扩展声明()` 内：

```text
dlopen(路径串.as_ptr(), RTLD_NOW)        →  句柄
dlsym(句柄, c"GetPlatformInfo")          →  符号
core::mem::transmute::<_, extern "C" fn() -> *const 平台信息>(符号)  →  取平台信息
指针 = 取平台信息()                        →  &'static 平台信息
```

- **载体是进程内 `dlopen` / `dlsym`**（`启动网关.rs` 直接声明 libc 的 `dlopen`/`dlsym`/`dlerror`，
  零第三方依赖）。**不是**子进程、**不是** WASM、**不是** 网络。
- `RTLD_NOW`：装载时把符号全部解析掉（缺符号当场失败）。
- **句柄不释放**：`dlopen` 的句柄「只装载不释放（本进程活到服务停）」（`取扩展声明` 注释原文），
  全仓**没有 `dlclose`**（grep 命中 0）。
- 符号名硬编码 `GetPlatformInfo`（`扩展装载/扩展根声明.json` 的 `扫描.找什么` 同值）。

**③ 判定（六步，只判不载）** —— `启动网关.rs::main` 试装：把候选声明根交给
`跨语言适配/适配器实现/src/lib.rs::适配器::装载声明根`，后者对每份声明调
`运行内核/装载入口/src/装载.rs::载入` → `运行内核/装载入口/src/判定.rs::判定可装载`
（①格式号 → ②标识串 → ③号段 → ④版本 → ⑤依赖 → ⑥自洽）→ `运行内核/统一注册表/src/建表.rs::注册表::建表`。
**全仓恰好 1 处调 `载入`**，就在 `适配器::装载声明根`（拓扑判据第 3 条）。
判定不过 → 进 `剔除的` 列表并打一行原因（`启动网关.rs::说清启动失败`），**不中断**。

**④ 装完的调用走哪条路** —— 两条入口，终点同一个：

```text
HTTP： 服务::处理一个连接 → 服务::应答 → 分发::处理 → 适配器::调用能力
C ABI： 边界面.rs::平台_调用 → 对外边界::调用 → 适配器::调用能力
                                                      ↓
                              v1_dispatch::调用 → 调度核心.rs::调度
                                                      ↓
                                      unsafe { 执行(返回槽, 实际, 参数表) }
```

`执行` 是 `运行内核/统一注册表/src/占位项.rs::命令槽::已载入 { 声明, 执行 }` 里的
**`执行函数` 裸函数指针**（`契约声明/src/lib.rs::执行函数` =
`unsafe extern "C" fn(*mut 数据槽, u32, *const 数据槽)`），由扩展的 `平台信息.函数表` 提供、
经 `dlopen` 拿到的同一份静态数据。**这一句就是在网关进程里直接跳进扩展的机器码。**

### 1.2 崩了会怎样（进程内 ⇒ 一个扩展 SIGSEGV 带走整个网关）

**这条链是推论，未实测**（按要求不跑崩溃样本）。成立点逐条列在下面：

1. **扩展的机器码与网关同地址空间**。`执行` 指针来自扩展 `dlopen` 出来的 `.dylib`
   （§1.1 ②④），`调度核心.rs::调度` 里 `unsafe { 执行(...) }` 是**同进程直接调用**。
   ⇒ 扩展内的越界写 / 空指针解引用，产生的是**网关进程自己的 SIGSEGV**。
2. **网关进程没有信号处理器**。全仓生产代码搜 `sigaction` / `signal(` / `setjmp` / `longjmp` /
   `sigaltstack`：**命中 0**（唯一 `SIGSEGV` 字样在 `项目文档/未完成事项.md` 的台账里）。
   ⇒ SIGSEGV 按默认处置**终止整个进程**。
3. **panic 也终止进程，而且 `extern "C"` 里本就不可 unwind**。根 `Cargo.toml`
   `[profile.release]` 明写 `panic = "abort"`（为「制品形态裁剪」）。⇒ 扩展里一次 `panic!`
   在 release 档 = `abort` = 网关进程死。生产代码里**没有任何 `catch_unwind`**
   （唯一一处 `std::panic::catch_unwind` 在 `运行内核/装载入口/src/装载测试.rs`，是测试）。
4. **监听循环是单线程、无监管**。`对外接口面/调用接口面/src/网关.rs::服务::跑` =
   `loop { self.处理一个连接()?; }`，一个线程串行 accept。**没有**看门狗、**没有** supervisor、
   **没有**重启分支。⇒ 进程一死，`跑` 不再返回，服务整体消失。
5. **死循环 = 永久挂死，超时只能在事后报**。`调度核心.rs::调度` 的耗时用 `Instant::now()`
   在**执行前后**各取一次，超时判定在 `执行` **返回之后**。扩展若不返回，这个唯一的 accept
   线程就永远卡在 `执行` 上。`运行内核/调用调度/src/lib.rs` 与
   `跨语言适配/资源网关口/src/lib.rs::关口` 都写明「**进程内无法抢占执行方**」——
   「真正强杀要跨进程（`现代架构落点.md` 形态 2）」。

**结论（推论）**：现在一个外部扩展 SIGSEGV / abort / 死循环，**网关进程整体终止**，
其余扩展随之全部不可用。这与准入判据 ①「不终止网关进程，剔除并报原因，其余扩展照常服务」
**正面冲突**。

## 二 三个候选方案对比

先说一条**共同前提**（三个方案都靠它）：边界只走**定长数据槽**，
`跨语言适配/边界协议/边界协议.md` §三 明写「槽自描述 ⇒ 换载体（进程内 / IPC / 网络 / WASM）不用改形状」。
所以**换隔离载体不改调用形状**，三案都不动能力实现的参数/返回形状。

| | A 子进程 | B WASM 沙箱 | C 进程内 + 兜底 |
|---|---|---|---|
| **怎么隔离** | 每个扩展一个进程；网关经 IPC（Unix domain socket / 命名管道，载体 B）递槽调它，像 language server | 扩展编成 WASM，网关用 WASM 运行时在沙箱里实例化，经线性内存递槽（载体 D） | 进程内不变；加看门狗重启 + 崩溃落痕，把「不带走服务」降级成「秒级自愈」 |
| **代价** | ① 新增 IPC 帧/背压/序列化；② 进程生命周期（拉起·健康·重拉·强杀）——**正是 `现代架构落点.md` §十 待裁 2 未裁的落点**；③ 每调用一次拷贝 + 跨进程延迟；④ 要为「扩展进程崩溃被剔除」立码（判据①的「报原因」） | ① 需一个 WASM 运行时 ⇒ **违反「零第三方依赖」**（`Cargo.lock` 现无 wasmtime/wasmer）；② 需 Rust→wasm32 构建腿（`能力包件.md` §六 待办 2）；③ 后端要能出 WASM 码段，而 **1106 编译未做**（台账 #168）；④ 沙箱能力边界逐能力标注（`现代架构落点.md` §十 待裁 3） | ① 进程内**无法可靠从 SIGSEGV 恢复**（信号处理返回后无法安全续跑）；② 看门狗若在同一进程内，随进程一起死 ⇒ **实质仍需要一个外部监督进程**，那时就不是「进程内不变」；③ 死循环仍无法抢占（`调度核心.rs::调度` 只事后判超时）⇒ 判据 ① 与 ③ 都过不了 |
| **与既有设计的冲突** | 与「单腿铁律」需一条裁决：把 IPC 归类为**边界协议的载体 B**（`边界协议.md` §三 已列），不是第二组导出面；同时把默认部署从形态 1 挪到形态 2，而形态 2 的进程管理落点未裁 | 直接撞两条硬约束：**零第三方依赖** + **单腿铁律**（WASM 运行时会成为新的进制品的腿）；且 1106 无路可依 | 结构上不冲突，但**不满足判据 ①**；且要真有用必须引入外部监督进程 ⇒ 与「进程内不变」自相矛盾 |
| **能否保住「扩展恰好一个导出」冻结形状** | **能**。子进程仍是普通扩展 cdylib，仍恰好导出 `GetPlatformInfo`；IPC 是宿主↔能力进程的通道，不是扩展的第二个导出（需一条裁决归类，见上） | **能，但口径要重述**。WASM 模块的导出表恰好一个 `GetPlatformInfo`；但装载从 `dlopen` 变成「实例化 `.能力包件` 的能力码段」，**装载这条接缝要改** | **能**（完全不动） |

### 2.1 关于 B 的关键查证：WASM 在本项目服务的是「包装形态」还是「运行形态」

**查证结论：目前是「包装形态」（编译产物的分发格式），不是「运行形态」；运行形态只是候选。**

证据：

1. **`.能力包件` 是编译产物，不是运行载体**。`项目文档/设计文档/能力包件.md` §一 定义
   `.能力包件` 三段：接口说明段 `256` · **能力码段 `257`（WebAssembly）** · 指纹段 `258`。
   同文件 §五 明写「**包是被载入的，不是被运行的。它没有自己的入口，只有导出表**」。
   ⇒ 它服务的是**「扩展怎么打包分发、agent 怎么读接口」**，即**包装形态**。
2. **今天的运行期根本不读 `.能力包件`、也不跑 WASM**。§1.1 已证：装载走
   `dlopen` 原生 `.dylib/.so/.dll`，调用走进程内函数指针。**全仓无 WASM 运行时**
   （根 `Cargo.toml` 与 `Cargo.lock` 零第三方依赖，无 wasmtime/wasmer/wazero）。
3. **WASM 作为「运行形态」仍是候选，且有明确前置缺口**：
   `现代架构落点.md` §三 把「D WASM 组件」列为**边界协议四种载体之一**（形态 5 边缘沙箱），
   §十 待裁 3「哪些能力不能进沙箱」**未裁**；`能力包件.md` §六 待办 2 缺「WASM 目标与工具链」；
   台账 #168 记 1106 编译未做、「能力码段 = WASM 无路可依」。
4. `跨语言适配/资源网关口/src/声明形状/载体与入口.rs::载体` 有 `沙箱` 枚举值，
   但 `资源网关口/src/lib.rs` 缺口 5 明写「**本节点只给进程内这一条路**（进程池 / WASM 沙箱未裁）」。

**一句话**：WASM 在本项目**首先是 `.能力包件` 的码段格式（包装形态）**；
把它用作**运行形态（沙箱载体 D）**是**尚未落地、且与当前两条硬约束（零依赖、单腿）冲突**的候选。
所以不能凭「能力码段本来就是 WASM」直接推出「WASM 就是终态运行载体」——**这是两件事**。

## 三 推荐

**我推荐 A 子进程**，作为**外部热接入支持库/模块的隔离落地形态**；理由与代价如下：

**为什么是 A（不是 B、不是 C）**

1. **只有 A 今天就交付判据 ① 要的硬边界**。子进程边界由 OS 提供，扩展进程 SIGSEGV/abort
   只死它自己；网关侧收到 IPC 断开即「剔除 + 报原因」，其余扩展照跑——**这正是判据 ① 的字面要求**，
   不需要等任何新工具链。
2. **A 与既有架构同向，不是新开一条腿**。`现代架构落点.md` §二 形态 2（单机多进程）已写
   「一个能力崩不带走整机」，§四 逐节点表把 `装载入口/` 映射成「每个能力进程各一次」、
   `调用调度/` 映射成「进程级超时与配额」。A 是**把已写好的形态 2 落下来**，不是发明新形态。
3. **A 顺带关掉判据 ③**。跨进程后「超时」可落成**真抢占（强杀扩展进程）**，
   不再是「事后判有没有越界」——`调度核心.rs` 与 `资源网关口` 现在都卡在「进程内无法抢占」。
4. **A 保住「恰好一个导出」**。子进程仍是普通扩展 cdylib，仍恰好导出 `GetPlatformInfo`；
   IPC 是宿主↔能力进程的**载体**（`边界协议.md` §三 载体 B），不是扩展的第二个导出面。

**为什么不选 B**：WASM 是**包装形态**的既定选择（§2.1），但作为**运行形态**它今天需要
「一个 WASM 运行时 + 一条 wasm32 构建腿 + 1106 后端」三样都到位，前两样直接违反
「零第三方依赖」与「单腿铁律」，第三样未开工。**B 是长线终态候选，不是近期落点**。

**为什么不选 C**：C **不满足判据 ①**（进程内无法可靠从 SIGSEGV 恢复），死循环也无法抢占；
要让它有意义必须加一个**外部**监督进程——那已经是弱化的 A，却仍拿不到 A 的硬边界。

**A 的代价（要如实认）**

1. **新增 IPC 载体**：帧协议 · 背压 · 一次序列化与拷贝；每调用增加跨进程延迟。
2. **进程生命周期是未裁项**：谁拉起能力进程、崩了谁重拉、与 `调用调度/` 如何分工——
   正是 `现代架构落点.md` §十 待裁 2，**必须先裁再施工**（本腿不裁，只标注它是 A 的前置）。
3. **要立码**：判据 ① 的「剔除并报原因」需要一组「扩展进程崩溃 / 被剔除」的结构化错误码，
   现无（`契约声明/错误码表/` 段位 0 只有「提供者未载入」一类）。
4. **要一条裁决归类 IPC**：把宿主↔能力进程通道归为**载体 B**，避免被
   `边界协议.md` §四 判据 5「不许出现第二个 `extern "C"` 导出面」误判成第二条腿。
5. **并发短板仍在**：网关单线程 accept（`网关.rs::服务::跑`）与适配器未给 `Send`/`Sync`
   保证（判据 ⑯）不因 A 而消失，A 之后仍要单独做。

**落地次序建议**（供裁决，不在本腿施工）：先裁 §十 待裁 2（进程管理落点）→ 定 IPC 帧与
「崩溃剔除」码 → 再落 A。
