# 扩展装载与开发标准

上级：系统工程平台 V1 ／ 落点：`项目文档/设计文档/扩展装载与开发标准.md`
相关：`README.md` 第五节（底座与扩展）· 第七节（号段）· `现代架构落点.md`（部署形态）

**一句话**：底座不认识任何扩展。扩展自带一份静态声明，底座读它、判它能不能载、然后按契约载入。**载入与卸载都是热的，不用重启底座。**

---

## 一 底座与扩展的分界

| | 底座 | 扩展 |
|---|---|---|
| 是什么 | 契约 · 内核 · 适配 · 接口面 · 构建验证 · 工具 · 文档 | 支持库 · 模块 · 技能 |
| 号段 | 0xxx（内核自有）· 9xxx（工具类） | 1xxx–8xxx |
| 谁维护 | 底座维护者 | 扩展作者 |
| 节奏 | 稳定优先，只增不改 | 随时新增，热载入生效 |

**分界判据**：**改一个扩展，不需要动底座一行代码，也不需要重发底座。** 做不到就说明底座里混进了扩展知识。

---

## 二 载入机制（怎么载）

### 2.1 扩展提供的是「声明」，不是「接口」

底座**不问**扩展「你有什么」，而是扩展**声明**自己有什么。声明是静态可读的结构，底座读一次就掌握全部可装载性（宪法第 2 条）。

这条决定了后面一切：因为声明是数据，所以载入不需要执行扩展的代码；因为不需要执行，所以载入是安全且快的；因为载入快，所以可以热载入。

### 2.2 声明里必须有什么

| 字段 | 作用 | 判定影响 |
|---|---|---|
| 声明格式号 | 声明本身的版本 | 不匹配 → 拒绝载入 |
| 标识串 | 扩展的唯一身份 | 重复 → 拒绝载入 |
| 扩展版本 | 扩展自己的版本 | 供依赖判定 |
| 要求底座版本 | 我需要在什么底座上跑 | 不满足 → 拒绝载入 |
| 要求内核版本 | 我需要在什么内核上跑 | 不满足 → 拒绝载入 |
| 名称与说明 | 给人 / 给 agent 看 | — |
| 能力表 | 编号 · 参数表 · 返回表 · 错误段位 | 决定号段归属 |
| 类型表 | 本扩展新增的类型 | 与底座类型表合并 |
| 常量表 | 本扩展的常量 | — |
| 依赖清单 | 我要哪些别的扩展 | 缺失 → 拒绝载入或降级 |
| 号段范围 | 我占用哪一段 | 与别人冲突 → 拒绝载入 |

### 2.3 判定顺序（fail-closed，任一步不过就拒绝）

```text
① 声明格式号匹配
② 标识串唯一（没有第二个同身份的扩展）
③ 号段不冲突（与已载入扩展、与作废号表都不冲突）
④ 要求底座版本满足 · 要求内核版本满足
⑤ 依赖清单里的扩展都在（或按声明的降级策略可缺）
⑥ 声明自洽：参数类型都在类型表里 · 错误段位都登记过 · 编号不重复
─────────────────────────────────────────────
全过 → 载入；任一步不过 → 拒绝载入（不是崩溃，也不是半载）
```

**不允许"半载"**：要么完整可用，要么完全不进注册表。半载会让调用方拿到一个时灵时不灵的编号，比直接失败更难查。

### 2.4 载入失败必须保住编号不塌

若某扩展没载入，而别的扩展或调用方引用了它的编号，**用占位项占住那个编号**：

- 调用占位项 → 返回一个明确的错误段位（「提供者未载入」），**不是崩溃**。
- 编号在表里的位置保持不变。

为什么必须这样：**编号是对外契约，塌一个索引会让后面所有编号错位，而错位是静默的——比崩溃更坏。** 崩溃至少看得见。

### 2.5 热载入与热卸载

| 动作 | 要求 |
|---|---|
| **热载入** | 不重启底座；新编号即时可见；不影响已在跑的其他扩展 |
| **热卸载** | 走生命周期号段；**卸载要能被拒绝**——扩展还在被引用时，允许它请求延迟释放，等引用清零再卸 |
| 卸载必须收回 | 注册表项 · 类型表项 · 常量表项 · 分配出去的内存 · 打开的资源 · 已注册的通知 |
| 卸载之后 | 该编号变为占位项状态（**不是消失**）；已发布的号永不回收（宪法第 7 条） |

**热卸载最容易漏的两件事**：一是引用计数（谁还在用），二是延迟释放（有扩展挂了别的组件的钩子，不能立刻拆）。这两件必须在生命周期号段里有对应通知，不能靠"应该没人用了"。

### 2.6 生命周期号段

```text
2000–2999   装载 · 卸载 · 退出（含延迟释放请求与应答）
```

## 三 开发标准（怎么开发）

### 3.1 必备件

| 扩展类 | 号段 | 必备件 |
|---|---|---|
| **支持库** | 1xxx–6xxx | 声明 · 实现 · 类型表 · 错误段位表 · 用法说明 · 指纹 |
| **模块** | 7xxx | 声明 · 流程定义（引用能力编号 + 顺序 + 数据流转）· 用法说明 |
| **技能** | 8xxx | 声明 ＋ **一份 md 描述**（怎么用底座能力做事，**不含实现**）。**是三种扩展里唯一可分发、可翻译的一类**（见 §3.6） |

### 3.2 SDK 形态

- **声明模板**：照着填，格式由模板保证。
- **实现骨架**：一类扩展一个骨架，骨架里已经把边界形状（数据槽、所有权、错误段位）写对。
- **本地自检工具**：**在扩展仓里就能跑，秒级，不需要底座在场**。它检查声明自洽（编号不重复、类型都在类型表里、错误段位都登记过、号段没冲突）。

### 3.3 开发循环

```text
在扩展仓里：写声明 → 写实现 → 本地自检（秒级）
        ↓ 通过
放进扩展根 → 底座按契约热载入 → 使用角色即可调用（零改动）
```

**全程不动底座。** 若某一步需要改底座，说明这个扩展越界了（例如它想组合却写成了支持库，或者它直接调了第三方）。

### 3.4 版本与号段纪律

- **号只增不复用**：扩展删了，号作废，永不回收。
- **参数行序是冻结项**：已公布的参数行序不许重排、不许插入（要加参数只能新增旁路）。
- **三个版本各自独立递增**：扩展版本 / 要求底座版本 / 声明格式号，不许混成一个。
- **声明格式号变了**，所有扩展的声明都要重审——所以这个号要最保守。

### 3.5 三类扩展的硬边界

1. **支持库不组合**——它只出原子能力。一个库在编排多个能力，那是模块放错了地方。
2. **模块不直连第三方**——模块里出现对第三方库或系统接口的直接调用即为越界；第三方只存在于支持库。
3. **技能不含实现**——技能只有说明与依赖清单；技能要干活，靠的是它依赖的能力编号。

### 3.6 技能 = 一份 md 描述（2026-09-27 定）

**技能的本体是一份 md**：讲「怎么用底座的能力把这件事做出来」。人读，agent 也读。
它对外是一个能力编号（8xxx）—— **调它就取回这份 md**。

四条能力，缺一条它就不成其为技能：

| 能力 | 含义 |
|---|---|
| **可下载** | 从别处拿来，像开源 skill |
| **可翻译** | 拿来之后翻译一遍 —— **翻的就是这份 md 的文字**，翻成本地语言与本地叫法 |
| **可跨 agent 调用** | 别的 agent 装进扩展根（热载入）→ 调 8xxx 取回这份 md → 照做 |
| **可自定义** | 开发时自己写一份 md，快速复用 |

**与模块的边界 —— 这是三条路的岔口**：

| | 本体 | 谁执行 |
|---|---|---|
| **技能** 8xxx | **一份 md** | 没人执行。agent 读完自己决定怎么调 |
| **模块** 7xxx | **流程**：引用能力编号 + 顺序 + 数据流转 | 机器执行 |
| **支持库** 1xxx–6xxx | 原子能力 | 机器执行 |

⇒ **技能不运行代码。** 要真跑代码，就得**基于底座的能力去封装**成模块或支持库 —— 只有那条路有实现。
技能里出现的代码片段只是**示例**，不是可执行件。

## 四 底座侧的三个保证

1. **底座不认识任何扩展**——底座里不许出现任何扩展的名字、路径或特例分支。
2. **扩展缺了底座照跑**——载入失败只是该能力不可用（未命中返回空），不是启动失败。
3. **新旧互不崩**——新扩展配旧底座、旧扩展配新底座，都不许崩；不兼容时**拒绝载入并说明原因**，不许带伤继续（宪法第 6 条）。

## 五 两个仓的分工

| | 底座仓 | 扩展仓 |
|---|---|---|
| 内容 | 契约 · 内核 · 适配 · 接口面 · 构建验证 · 工具 · 文档 | 扩展本体（声明 + 实现 + 说明） |
| 依赖 | **不依赖任何扩展** | 只依赖底座公布的契约（只读） |
| 维护节奏 | 稳定优先，只增不改 | 随时新增，热载入生效 |
| 谁能改 | 底座维护者 | 扩展作者 |

**升级关系**：底座升版本 → 扩展按自己声明里的「要求底座版本」自行判断能否继续用；不满足就拒绝载入并报明原因。**底座不为任何扩展保留兼容分支。**

## 六 待裁与待实测

1. **扩展根的位置与组织**：一个扩展一目录，还是按类分层。未裁。
2. **声明是文件还是经声明面写入**：与 `对外接口面/声明编写面/` 的关系需定死（倾向：面是唯一写入口，文件是落盘形态）。
3. **热卸载的引用计数由谁维护**：内核维护还是扩展自报。未裁。
4. **扩展的签名与来源校验**：要不要、要到什么程度。未裁。
5. **占位项的粒度**：一个编号一个占位，还是一段一个。未裁。
6. **待实测**：热载入与热卸载各一次现场验证——载入后新编号即时可调；卸载后编号变占位、资源回收干净、其他扩展不受影响。
