# 并行开发与工作区（怎么让「好开发」也有机器保证）

上级：系统工程平台 V1 ／ 落点：`项目文档/设计文档/并行开发与工作区.md`
相关：`开发规范.md`（一个循环 · 提交纪律）· `判据的可信性.md`（半成品红怎么归因）· `全局连接器与网关.md`（拓扑）· `README.md` 第十二节（交付纪律）

**本文解决一个问题**：代码要好维护，**也要好开发**。十几路并行时「抢」不是调度没排好，是**结构问题**。

---

## 一 诊断：三条争用，其中一条**实测不成立**

**构建锁争用不是真因**（实测）：

| 量什么 | 读数 |
|---|---|
| 单腿冷构建（`cargo build --workspace`，清空 target） | **0.32 秒** |
| 同一个 target-dir 里并发两个 cargo | **0.36 秒**（1.11×） |
| 两条腿各自的 target-dir 里并发 | **0.37 秒**（1.15×） |
| 锁**是否真的存在** | 存在。同 target-dir 那次两个进程都打出 `Blocking waiting for file lock on artifact directory` |

⇒ 锁真的在，**但代价约 0.04 秒**。这个仓是 12 个 crate、零第三方依赖、约 3 千行，`jobs = 32` 下一次构建本来就只有 0.32 秒，**锁不是瓶颈**。我把「机制存在」当成了「机制是瓶颈」——这正是 `判据的可信性.md` 要防的那类错：**没有量就下结论**。

**三条争用**（按实测代价从大到小）：

| # | 争用 | 机制 | 实测症状 | 代价 |
|---|---|---|---|---|
| 1 | **共享可变工作区** | 所有腿写**同一个**工作区 ⇒ 任一条腿的半成品让**全员**红；且任一条腿在写就**不能提交** | 实测：主树一度因 `对外接口面/调用接口面/src/lib.rs` 语法错 + `运行内核/调用调度` 的 `crate::配额账本` 未解析 ⇒ **全仓 12 个 crate 一起红**（后由各腿自己修好，现 0.44 秒全绿）。另：10 路成果一度全压在工作区里没进版本库 | **最大**。它同时废掉「全仓绿」这句话（绿不绿取决于谁在写）与「随时可提交」 |
| 2 | **文件争用** | 多条腿写**同一个文件** | 实测 4 例：`契约声明/src/lib.rs`（生成器腿 + 我补 `crate::`）· `编译器支持库/src/容器.rs`（一腿修 clippy + 一腿拆成子文件夹）· 编译器扩展 `src/lib.rs`（三腿都要加 `mod` 行）· 运行内核三件 | 大。**静默覆盖**——不报错，事后才发现丢了别人的改动 |
| 3 | **构建锁争用** | cargo 对目标目录加锁 | 见上表：锁存在，代价 0.04 秒 | **小到可忽略**（但保留机制一，它顺手把这条也归零，且防将来 crate 变大后回潮） |

**结论**：腿数加得越多净收益越接近零，原因是第 1、2 条——**共享可变状态**。

## 一之二 这次量测本身：一条可复跑的量法 + 两个反向样本

**量法**（`/tmp/锁实测2.py`，不进仓库）：固定 `CARGO_HOME` 与 `CARGO_TARGET_DIR` 两个变量中的**一个**，只让另一个变，用 `time.monotonic()` 计时，并 grep 日志里的 `Blocking waiting for file lock on …` 取证。

**两个反向样本**（第一版就是这么量错的，留着证明上面那条量法是必要的）：
1. **没 source `构建环境/进入.sh`** ⇒ `CARGO_HOME` 落到共享的 `~/.cargo`。于是「两条腿各自 target-dir」那一组反而报出 2/2 次锁等待 —— 那报的是**包缓存锁**（`package cache`），不是目标目录锁。**两种锁混成了一个结论。**
2. **用 `date +%s` 计时** ⇒ 精度只有 1 秒，而构建本身只有 0.3 秒，读数全是 `0` 和 `1`，方向都看不出来。

**教训**：量「锁」必须①把两种锁（`package cache` / `artifact directory`）分开取证 ②计时精度要**远小于**被测时长。**读数自相矛盾时，先怀疑量法，不要先怀疑机制。**

**注**：`.cargo/config.toml` 里 `target-dir` 是**相对**路径，但 `构建环境/进入.sh` 又把它导出成**绝对**路径（`$ROOT/构建环境/构建缓存`）。所以隔离成立的前提是**每条腿 source 自己那棵树里的 进入.sh**（此时 `ROOT` = 该工作树 ⇒ `CARGO_HOME` 与 target 都落在该树自己目录下）。若在工作树里 source 了主树的 进入.sh，两条腿就又会共用主树的 target 目录——**这是本机制唯一的用法陷阱**。

## 二 为什么「按文件所有权切开」不够

我这一轮一直在做这件事（每份任务书都写「只改你被指派的文件」），但**实测仍然撞了 4 次**。三个原因：

1. **腿必须碰共享文件**：加一个模块要动 `lib.rs` 的 `mod` 行；改契约层要动被多腿依赖的文件。**所有权切不开共享的接缝。**
2. **收口方的修复会与在飞的腿撞**：我为了解全仓阻塞补了一个 `crate::` 前缀，而那条腿还在写同一个文件。
3. **所有权靠人写、不靠机制**：漏写一个路径就撞。**靠人记得 = 迟早会漏。**

**所以：靠纪律切不开的，要靠机制切开。**

---

## 三 解法：两层机制 + 一条纪律

### 机制一：一腿一工作树（`git worktree` + 独立构建缓存 + **落在仓外**）

```text
系统工程平台V1/                仓库本体
系统工程平台V1.工作树/          ★ 与仓库同级 —— **在仓外**
    └─ <腿名>/                 每条腿一份完整检出（独立 target 目录）
```

**★ 为什么必须落仓外**（这是实测逼出来的，不是随手选的）：

我第一版放在仓内（`.工作树/`）。后果实测到了：**全仓扫描会把那份检出当成真命中** —— 验证器常量表检查的 13 条命中里 **8 条来自 `.工作树/trial1/**` 那份收口前的旧拷贝**，里面还有我从没写过的旧值（`单项超时毫秒: u64 = 30_000`）。**陈旧副本长得跟真的一模一样** ⇒ 假红假绿都判不准。

两种修法：

| 修法 | 性质 | 评价 |
|---|---|---|
| 给每个全仓扫描面加跳过项 | **打补丁** | 仓内现在有两个扫描面（`构建装配/一键验证/一键验证.py::跳过目录`、`测试验证/契约一致性/扫实现.py::建夹具集`），明天第三个忘了就又中。**「靠人记得」= 迟早漏**，这正是本文要消灭的东西 |
| **工作树落仓外** | **结构性** | 仓库里不再有「自己的副本」⇒ 任何遍历（`os.walk` · `rglob` · 终端的 `grep -r` · 编辑器索引）**天然看不见它**，不需要任何扫描面知道它的存在 |

**实测验收**：改到仓外后，仓内 `find . -name '*工作树*'` 命中 **0**（只有工具脚本自己），`grep -rn 30_000` 命中 **0**（那条陈旧值随副本一起消失），工作树内 `cargo check` 仍正常（0.06 秒）。

**注**：`.gitignore` 里那条 `.工作树/` 留作兜底（防有人在仓内手建一个），并在注释里写明「按设计落在仓外」——**不是**这条机制需要它。

**实测可行**（本会话取数）：

| 项 | 读数 | 判断 |
|---|---|---|
| 单腿构建缓存 | **403 MB** | 10 腿 ≈ 4 GB |
| 磁盘可用 | **1.4 TiB** | 富余三个数量级 |
| 仓库本体（不含产物） | 很小（产物占了 406 MB 里的绝大部分） | 检出成本可忽略 |

**效果**（按 §一 的代价排序）：
- **共享可变工作区 ⇒ 归零**（最重要的一条）：半成品只存在于该腿自己的工作树里，**共享工作区永远是绿的** ⇒ 「全仓绿」这句话才**重新有意义**（现在它没意义：绿不绿取决于谁正在写）
- 文件争用 ⇒ **归零**（各自检出，不可能覆盖别人的改动）
- 提交点争用 ⇒ **归零**（共享工作区不再被任何腿写 ⇒ 随时可提交）
- 构建锁争用 ⇒ 归零（但按实测它本来就只值 0.04 秒，**这条是附带收益，不是理由**）
- 合并冲突 ⇒ **必现**（好事：冲突出现在合并那一刻，而不是静默覆盖）

**代价**：每条腿首次构建是冷的。**已实测**：冷构建 `cargo build --workspace` = **0.32 秒**（12 个 crate · 零第三方依赖）。构建缓存每腿 **403 MB**，磁盘可用 **1.4 TiB** ⇒ 10 腿约 4 GB。**两条代价都小到可忽略。**

**★ 唯一用法陷阱**：必须在工作树里 source **它自己**的 `构建环境/进入.sh`。若 source 了主树那份，`CARGO_TARGET_DIR` 会被导成主树的绝对路径，两条腿又共用同一个 target 目录（`进入.sh` 导的是绝对路径，会盖掉 `.cargo/config.toml` 里的相对值）。

### 机制二：认领机制（**做进平台，不是靠纪律**）

工作树解决了「写的时候不撞」，但没解决「**两条腿认领了同一件事**」。那需要一个**认领机制**：

```text
认领(路径集, 腿标识) -> 成功 | 冲突(哪几条路径被谁占)
收工释放(腿标识)
```

**这正是旧版「开工即占」要解决的问题，也是 V1 必须自带的能力。** 而且它天然属于 V1 自己的架构：

- 它是一个**能力**（编号 · 参数表 · 返回 · 可抛错误码，走 V1 自己的契约）
- 它的状态是**显式持有的句柄**（租约），不落进程级全局（宪法）
- 它的失败是**结构化错误码**（冲突时报「哪条路径被谁占」），不是一句文字
- **原子性**：路径集里任一条被占 ⇒ 整体失败（不半占）

**⇒ 这就是「好开发」的机器保证**：撞车由平台**拒绝**，不由人记得。

### 纪律三：腿数上限 + 一批一收

并行不是越多越好。**并行的净价值 = 腿数 × 单腿吞吐 − 争用损失 − 人的注意力成本**。

前两项由机制一、二压到接近零之后，**瓶颈变成第三项：人的注意力**。每条腿回来都要读回执、判对错、合并——**同时飞的腿数 ≤ 能逐条读完回执的数**。

本会话的经验值：**5–7 条是舒适区；10 条开始漏细节**（我自己就有多次「读到半成品就下结论」）。

**★ 平台并发上限（实测 2026-09-27，这是硬约束不是风格偏好）**：同时飞的子代理**上限约 6–7 条**。超过之后，**后启动的腿被硬杀**（报 `Concurrency limit exceeded for account`），而且**杀的是正在跑的那条，不是排队等**。实测：一次放 12 条 ⇒ **5 条被杀**，其中一条已经做完 90%（`契约声明/src/lib.rs` 502→106 的成果差点白做）。续跑两条想把进度补回来 ⇒ 立刻又杀掉一条。⇒ **超订的代价是整条腿重跑，不是「慢一点」**。
**被杀腿的改动仍留在它自己的工作树里**（一腿一树在这里又赚了一次），可用 `SendMessage` 带上下文**原样续跑**，不必从零重做。

**收口节奏（2026-09-27 改）**：一批落地 → **提交** → **一次性修完红**。原写「腿全落地 → **全绿** → 提交」，那条要求每条腿自己追绿，实测效率太低 ⇒ 见 `项目文档/决策记录/2026-09-27_短期红可接受与反漂移选型.md`。**「一批一收」不变**：不收口的批次不许再叠新腿。

## 四 判据（可数，进元判据）

| # | 判据 | 怎么数 |
|---|---|---|
| 1 | **零文件争用**：任两条腿的认领路径集交集为空 | 认领记录两两求交 |
| 2 | **零构建锁等待**：每条腿的 target 目录唯一 | 数 `CARGO_TARGET_DIR` 的取值；日志里 grep `Blocking waiting for file lock` 应为 0 条 |
| 3 | **冲突必现**：认领过的路径在合并时若冲突 ⇒ 报「认领机制失效」 | 合并时比对认领记录 |
| 4 | **共享工作区永远是绿的**：任何「半成品红」都只应出现在**该腿自己的工作树**里 | 红按 `判据的可信性.md` 归因；出现「缺件或半成品」⇒ 违规 |
| 5 | **同时飞的腿数 ≤ 上限** | 数活跃腿 |

第 4 条是这套方案**最重要的产物**：**共享工作区永远绿 ⇒ 「全仓绿」这句话才有意义**。现在它没有意义，因为红可能只是别人写了一半。

## 五 明确不做

| 不做 | 为什么 |
|---|---|
| 不做「多腿共享一个 target 目录」 | 不因为它慢（实测只差 0.04 秒），而是因为**它会让「每条腿独立」这条判据失去落点**：target 一共享，就得再引一套「谁的缓存是干净的」的规矩。**能靠机制免掉的共享，就不要共享。** |
| 不做「靠人记得谁在改什么」 | 靠人记得 = 迟早漏；本会话实测漏了 4 次 |
| 不做「不认领就开工」 | 无认领 ⇒ 撞车是静默的（各自以为独占） |
| 不做「无限并行」 | 瓶颈从机器转移到人的注意力；10 条腿开始漏细节 |
| 不做「边写边提交」 | 提交是共享可变状态的写点；一批一收才可解释 |
| 不用「合并时手工解冲突」当常规手段 | 冲突应当**罕见且必现**；常见冲突说明认领粒度错了 |
