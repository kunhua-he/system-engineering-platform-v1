### 问题 2（★ 阻塞）：任务书指名的输出路径与 V1 声明生成器冲突

- **现象**：任务书 07 要求产出 `契约声明/能力声明/外部_<模块名>.json`。实测把该文件放进去，**闸 0 从全绿变红**（46 通过 / 0 失败 → 42 通过 / 4 失败）：
  - 判据 ①（编号与文件名一致）：`文件名 外部_数值计算支持库.json 不是编号（§一：文件名 = 编号，如 0001.json）`；
  - 判据 ⑤（参数类型都在类型表里）· ⑥（返回类型在类型表里）· ⑦（可抛错误码都在错误码表登记）：因该文件用的是任务书 01 的**外层包壳格式**（`{模块, 号段, 能力列表:[...]}`），而 V1 要的是**扁平格式**（见 `契约声明/能力声明/0000.json`：`编号/名称/参数表/返回类型/可抛错误码` 直接在顶层）⇒ 三条判据都读不到字段；
  - 闸 2 ③a：`这份能力声明没有可用的 编号（缺字段或不是整数）⇒ 无法与实现对照`。
- **复现**：`cp 构建装配/翻译器/产物/任务书格式/外部_数值计算支持库.json 契约声明/能力声明/ && python3 构建装配/一键验证/闸0.py`（删掉该文件即回到全绿，已实测）。
- **原因**：两条 —— ① `契约声明/能力声明/*.json` 的**文件名就是编号**（`构建装配/形态装配/生成声明/读子表.py` 硬规则）；② 任务书 01 定的**外层包壳格式**与 V1 实际的**扁平格式**不是一套。该目录装的是**底座自身**的命令，不是扩展的。
- **正确落点**：**扩展自身目录里的 `能力声明/`** —— 唯一现成先例是 `扩展根目录/原子支持库/编译器支持库/`（`包声明.json` + `能力声明/1101.json` …）。
- **修正**：产物改落 `扩展根目录/原子支持库/数值计算支持库/`（见问题 3 的进一步结论）。
- **状态**：已定位并绕开；**任务书 07 与 01 的该路径必须改**。

### 问题 3（★ 阻塞）：扩展声明根没有实现单元 ⇒ 闸 2 判「未判」

- **现象**：把产物落进 `扩展根目录/原子支持库/数值计算支持库/` 后，闸 2（`扫实现.py`）③a「声明→实现·能力编号」**未判**：
  > 判不了：声明根 `扩展根目录/原子支持库/数值计算支持库` 找不到对应的实现单元 … ⇒ 声明没有实现面可比
- **原因**：`扫实现/比对.py` 按**目录**把声明根映射到实现单元；没有 Rust crate 就没有单元。`扫实现.py` 的退出码是「失败 = 0 **且** 未判 = 0」才 0 ⇒ 未判即红 ⇒ 闸 0 红。**且仓内无任何「声明先行、实现后补」的登记口子**。
- **影响**：★ **纯翻译产物无法独立过闸** —— 批量接入（小队6）若直接把 148 个模块的声明落进 `扩展根目录/`，闸 0 会因 148 个未判而全红。
- **修正（本腿采用）**：默认落**暂存区** `构建装配/翻译器/产物/`（不在闸 1/闸 2 的扫描范围内），上架动作与实现单元落地绑定。
- **候选解法（需裁决）**：① 翻译器同时生成实现 crate 骨架；② 给闸 2 加「已登记的待实现声明根」白名单；③ 批量接入与实现实现同步进行。
- **状态**：已绕开；**需裁一个长期方案**。

### 问题 4：号段分配表口径与现架构冲突

- **现象**：任务书 02 与总览写「号段改为 **10000–999999**，每模块 10000 号」。而 `契约声明/号段图.json` 与 `契约声明/常量表.json` 定的是「号段类宽度 1000 · 号段类个数 10」⇒ **能力号全宽 0–9999**，10000 起越界。
- **修正**：本腿的 `号段分配表.json` 按 `号段图.json` 口径写（1000–1999 = 核心支持库），不按任务书 02 写。
- **状态**：已按权威源修正；**任务书 02 的号段口径需作废重写**。

### 问题 5（★ 阻塞）：判据 ㊻ 与前端控件 id 撞号

- **现象**：能力号最初取自然顺延的 **1200–1208**（编译器支持库占 1100–1199）。落盘后闸 1 判据 ㊻「底座不硬写能力号」当场红 5 条：
  > 底座里硬写已声明能力号 `1200`（1 处）… `1207`（2 处）｜ `前端呈现/网页应用/对话框表.js`
- **原因**：㊻ 的检测表 = 全部「已声明能力号 ≥ 1000」（`判据_能力号.py::已声明能力号`），扫描面 = 底座代码面生产区文本。`对话框表.js` 把**控件 id** 写成 1200/1201/1206/1207/1208（该件共 184 个控件 id）—— **控件 id 与能力号是两个号空间，但判据按数字对撞**。
- **为什么不能靠基线消**：`硬写能力号基线` **只许减**（`冻结基线.py` 文件头：任何新增键或涨了一律拒写）⇒ 无法把新撞的号登记进去。
- **实测口径**：1000–1999 里有 **152 个号**已被控件 id 等占用；连续 9 个空闲的起点只有 1253 · 1276 · 1281 …（全仓 178 个底座代码件实测）。
- **修正**：本模块改取 **1253–1261**（最靠前的空闲段）。
- **影响**：★ **每个模块的号段都必须逐段核 ㊻**，否则一上架就红。这是小队2 号段分配表的硬约束。
- **状态**：已绕开；**约束需写进小队2 的分配规则**。

### 问题 6：类型系统缺口 —— 列表型 / 结果型 在 V1 无原生标签

- **现象**：老项目用 `列表型`（参数）与 `结果型`（返回）。V1 的 `契约声明/类型声明/` 只有 0 空 · 1 整数 · 2 双精度 · 3 逻辑型 · 4 文本 · 5 字节集 · 6 句柄 · 7 任务句柄 · 4294967295 错误。
- **修正**：暂按**字节集（5）**承载（与编译器支持库「词法分析」返回「记号流边界编码（字节集）」同一做法）。
- **代价**：**保真损失 14 处**（5 个参数 + 9 个返回类型），已逐条记进 `翻译来源.json` 的 `保真损失`。
- **状态**：有损绕开；**「结构体/列表过边界怎么编」需专项裁决**（否则每个模块都会丢这一层语义）。

### 问题 7：默认值槽只装 u64 ⇒ 文本默认值无法承载

- **现象**：`取整` 的 `方式` 参数默认值是文本 `"四舍五入"`。V1 默认值槽形状是 `{类型标签, 值}`，而 `值` 被 `读子表.py` 按**整数**取（范围 0–0xFFFFFFFFFFFFFFFF）⇒ 文本装不进去。
- **修正**：丢默认值（写 `{类型标签:4, 值:0}`），并记进保真损失（**1 处**）。
- **状态**：有损绕开；**需裁「文本/浮点默认值怎么落声明」**。

### 问题 8：rglob 先命中制品仓库，且全走 196451 件超顶

- **现象**：首版 `定位模块` 用 `rglob("包声明.json")`，翻译出的模块路径是
  `工程缓存/制品仓库/7d99bca6…/平台客户端/支持库/后端/数值计算支持库` —— **译的是构建副本，不是源码**。同时壳墙钟报 **9359 ms > 4800 ms 硬顶**。
- **原因**：老项目 `工程缓存/制品仓库/` 下有 196451 件 py（含全部源码的副本），`rglob` 会全走一遍。
- **修正**：改 `os.walk` **边遍历边剪枝**（进目录前就把生成式目录从子目录表剪掉），并排除 `工程缓存/制品仓库/__pycache__/测试中心/示例项目/开发文档/.git`；同名多份取**路径最浅**的。
- **读数**：墙钟 **9359 ms → 177 ms**；定位结果改为 `支持库/后端/数值计算支持库`（正确）。
- **状态**：已解决。★ **后续模块的翻译器必须继承这两条**（剪枝 + 取最浅）。

### 问题 9：命名登记闸 —— 新写一个工具要登记约 50 个名

- **现象**：首版翻译器一落盘，第 ⑤ 道闸（命名登记）列出 37 个未登记名；拆包后又报 5 个。**且 `段` · `选项` · `项` 虽在 `命名登记` 表里，但状态是「待改名」（禁止形状）⇒ 不可复用，只能另起新名**。
- **修正**：共登记 50 个名（`信息核心.py 登记 --名字 X --语义 Y --模式 Z --来源 新定义`）；禁止形状的改名绕开（段→版本段 · 选项→命令行选项 · 项→报告条目）。
- **顺带发现**：闸的错误提示写「`信息核心.py 登记 <名>`」，而该子命令**只接受具名参数**（`--名字/--语义/--模式/--来源`），按提示的写法跑会只打用法文本。**提示与实现不一致**。

### 问题 10：入口规范 —— 首版 368 行当场红

- **现象**：首版把实现写在 `老项目模块翻译.py`（带 `__main__` ⇒ 算入口）。闸 1 判据 ⑲ 两条红：`368 行 > 上限 120 行（入口文件）` · `入口文件里有 12 处实现`；㉔ 又红「能跑完的入口却没带壳」。
- **修正**：拆成「壳 + 包」——`老项目模块翻译.py` 退回路由（无函数定义，只 `import` + `自门禁`），实现移进 `构建装配/翻译器/老项目翻译/`（`读源` · `类型映射` · `声明构造` · `翻译流程` · `命令行`，均 < 200 行）。
- **状态**：已解决。

### 问题 11：扩展声明无法用 Python 声明生成器校验

- **现象**：拿本仓的 `读平台声明` 校本扩展的 `包声明.json`，当场 `生成失败`：
  > `扩展根目录/原子支持库/数值计算支持库/包声明.json 的「通知号段」是空表`
- **原因**：`读平台声明` 是给**底座**声明写的（要求非空通知号段、要同目录有 `号段图.json`/`常量表.json`/`作废号表.json`）。★ 但**唯一现成扩展 `编译器支持库` 的 `通知号段` 也是 `[]`** ⇒ 这是**存量缺口**，不是本腿引入的。
- **后果**：扩展契约**没有 Python 侧校验路**，只能靠 Rust 装载侧。本腿只能用 `读能力声明` / `读错误码表`（这两个扩展适用）做验证。
- **状态**：已绕开；**缺口如实登记**。

### 问题 12：文档账本 —— 翻译器目录的 md 全部未入账

- **现象**：闸 1 判据 ㊶ 报 `构建装配/翻译器/README.md` 与 `任务书/01…07 + README` 共 8 份 md「不在文档账本里」。**这是主干存量**（主干闸 0 的唯一失败项就是它）。
- **修正**：在 `项目文档/文档账本.json` 的 `按路径定档` 加一条前缀规则（`构建装配/翻译器/` → 临时文档），一次性清掉 8 份存量 + 本报告本身。
- **状态**：已解决（★ 该件被 7 条腿同时认领，合并期需语义合并）。

### 问题 13：生成物必须自带溯源标，否则记不进账

- **现象**：`v1_task` 功能=5（生成物记账）拒记，报：`生成器这次写过的件里，有没自称是本生成器产物的 ⇒ 一件都不记`。
- **口径**：每份生成物必须自带一行「生成物 · 禁手改 · 生成器：<入口相对路径>」（判据 ⑩ 头标口径；注释形与 JSON 值都认）。
- **修正**：产物新增顶层字段 `生成说明`（“生成物，禁手改。生成器：构建装配/翻译器/老项目模块翻译.py”）。
- **副产物**：多一个字段后，`读能力声明` / `读错误码表` **仍正常消费**（两读器只取具名键，忽略多余键）—— 已实测复验。
- **待确认**：任务书 01 定的能力声明格式没有这个字段。若后续把 V1 声明形状当**冻结面**看，则“生成物标怎么落进 JSON”需裁（可选：改用旁挂的 `指纹.json`，或把标写进已有的 `说明` 字段）。
- **状态**：已解决（以额外字段实现）；**格式口径待裁**。

## 五、经验总结

### 5.1 翻译器改进建议（相对小队5 的正式版）

本腿的 `老项目模块翻译.py` 是**最小可跑版**，与小队5 的正式版预期差异：

1. **只支持 JSON 源**（`包声明.json` + `能力契约/参数契约.json`）。任务书 05 要求的 AST 回退路（补默认值/必填）本腿未做。
2. **号段按表查**，表由本腿最小实现；正式版应读小队2 的完整分配表，并**逐段核判据 ㊻**（见问题 5）。
3. **类型映射是硬表**（11 项）。正式版需覆盖全仓出现的所有老项目类型名，并对未知类型给出**可执行的报错**（本腿的做法：fail-closed 拒译，不静默丢）。
4. **未生成实现骨架**。若采纳问题 3 的解法①，正式版要一并出 Rust crate 骨架。

### 5.2 翻译规范补充（给小队1）

1. **落点是扩展自身目录**，不是 `契约声明/能力声明/`（问题 2 有实测证据）。
2. **文件名 = 编号**（十进制），且 `编号` 字段必须等于文件名。
3. **能力号段必须避开底座代码里的字面数字**（问题 5）—— 这条不写进规范，每个模块都会撞。
4. **有损映射必须留痕**（本腿落 `翻译来源.json.保真损失`），不许静默降级。
5. **源件摘要（sha256）必须落**，否则无从判「译的是哪一版源」。

### 5.3 命名修复规则更新（给小队4）

1. 本模块**零命中** —— 说明老项目 支持库 层的命名已相当规范，修复映射的收益集中在别的层。
2. ★ **禁止形状的债名（`段` · `选项` · `项` 等，状态=待改名）不可在新代码里复用** —— 写新工具时会撞上，需改名（本腿实测 3 处）。这条应写进小队4 的规则。
