# 编译器支持库 · 设计说明

上级：`扩展根目录/原子支持库/` ／ 号段：1101–1199（支持库）／ 形态：**后端能力**（前端是纯 UI，不在本扩展里）

**为什么先做它**：一个编译器会把内核的每一件事真用一遍——类型表（每个字面量的类型标签）· 命令表（每条语句解析成哪个能力编号）· 常量表（每个常量引用）· 数据槽（把值传进能力）· 错误段位（词法/语法/语义错误都要是结构化码）· 统一注册表（按号取命令）· 扩展装载（本扩展自身按契约热载入）。

**所以：编译器跑通 = 内核每一层都被真调用过一遍。它是内核的验收器。**

## 一 前后端切开（硬判据）

| | 在哪 | 干什么 |
|---|---|---|
| **后端**（本扩展） | `扩展根目录/原子支持库/编译器支持库/` | 词法 · 语法 · 语义 · 生成 · 反解 · 诊断 |
| **前端**（纯 UI） | `前端呈现/网页应用/` | 取源码文本 → 调能力 → 显示产物与诊断 → 下载 |

**判据**：前端里出现任何一个解析或生成函数，即为违规。前端只经 `对外接口面/调用接口面/` 说话。

## 二 能力清单

| 号 | 能力 | 输入 → 输出 |
|---|---|---|
| 1101 | 词法分析 | 源码文本 → 记号流 |
| 1102 | 语法分析 | 记号流 → 语法树 |
| 1103 | 语义分析 | 语法树 → 带类型的中间表示（查类型表 · 命令表 · 常量表） |
| 1104 | 生成容器 | 中间表示 → 容器字节（段头 + 段类型号） |
| 1105 | 反解容器 | 容器字节 → 中间表示 |
| 1106 | 编译 | 组合：1101 → 1102 → 1103 → 1104 |
| 1107 | 诊断 | 错误段位 → 中文说明 + 位置 |

每个能力一个号，一条声明，落在 `能力契约/`。

## 三 1:1 复刻的口径（可验证的那一条）

复刻的是**语言语义与产物形状**，不是参照实现的代码。

**验收判据（唯一硬判据）**：**往返一致**——拿现成语料里的容器文件，`反解容器` → 中间表示 → `生成容器`，产物必须与原文**逐字节相同**。

为什么用这条而不用「与参照编译器产出对比」：参照编译器是黑盒、只许只读解析不许运行，没法拿它当基准。而**往返一致可以在现成语料上批量验证**，且它证明的东西更硬——它同时证明了反解与生成两边都把格式吃透了。

**落地顺序因此是**：先做 1105（反解），因为只有它能立刻被语料验证；再做 1101/1102/1103/1104；最后做 1106/1107 与纯 UI 前端。

## 四 参照物与取证来源

格式与语义的取证在参照语料与既有调研件里，**只读**：

- 容器格式：段头 44 字节 + 段类型号；段名异或混淆；段类型 1–15 与 255 的含义
- 语言面：命令表（688 条）· 数据类型表（51 个）· 常量表（335 条）
- 调研落点：旧仓 `工程缓存/易语言架构/架构调研/｜-易程序容器格式.md` 等分片（**只读，不改**）

---

## 五 硬约束

1. **零第三方依赖**：与底座同口径，只用 `std`。
2. **失败是结构化错误段位**，不是字符串、不是 panic。词法/语法/语义错误各自占用自己的段位段。
3. **不许绕过内核**：查类型/命令/常量一律经 `统一注册表`，不许在本扩展里另存一份表。
4. **前端零逻辑**：见第一节判据。
5. **产物形状冻结**：容器段头与段类型号是冻结项，改动必须走 `契约声明/冻结登记.json`。
