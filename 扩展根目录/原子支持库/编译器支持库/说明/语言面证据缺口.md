## 一 最重的一条（原判已更正一半）：容器**能**承载源文本，语言面链仍缺独立基准

设计件把五个能力排成一条链（`1105 反解 → 1101 词法 → 1102 语法 → 1103 语义 → 1104 生成`），理由是「先做 1105，因为它能立刻被现成语料验证」。**实测这条理由对语言面不成立**：1105 反解出的中间表示与语言面的输入不是同一样东西。原用来支撑它的那句「容器里没有源文本」**已被推翻** —— 容器格式**可以**承载源码文本（`t9 编辑信息段2` 与 `t4 程序资源段`）。逐条复核见 `说明/真文本覆盖.md §六.1`，本节不复述其数。

**★ 已裁定**（`项目文档/设计文档/程序文本格式.md`）：原生格式不用 `.e`，改用**通用可读文本**（`.程序文本`），由我们自身定义 ⇒ 「文本 → 结构 → 文本」的基准是我们自身，这个死结随之消失。`.e` 降为**导入导出格式**，判据仍是容器逐字节一致。

---

## 四 `1103 → 1104` 之间缺一层「按表分区的记录流」

容器类型 3 段**不是语法树的直接映射**：它含支持库引用记录、程序集 / 子程序 / DLL 命令 / 常量等**按表分区**的记录流，语句是**字节码**。设计件把 1103 与 1104 直接相连，但容器里的顺序**按表分区、不按语法树先序**。

⇒ 1103 的输出**不能**被定义成「语法树 + 类型标注」；中间必须有一层**记录流形状**。

**★ 现状（口径已更正）**：这一层**已实现并冻结** —— 形状见 `说明/记录流形状.md`，实现见 `src/记录流/`。本节原「建议立成独立冻结腿」的说法**已过期**。
