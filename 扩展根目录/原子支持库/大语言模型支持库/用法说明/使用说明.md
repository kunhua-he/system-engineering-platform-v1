# 大语言模型支持库

只做 chat_completions 协议的连接登记与流式生成任务；不做协议翻译、不重试、不落盘。

## 调用顺序

1. `2501 连接模型(模型, 服务器地址, 接口密钥, 协议)` → 句柄。
   服务器地址可给 `http://host:port`、`http://host:port/v1` 或完整的 `…/chat/completions`。
2. `2502 提交生成任务(句柄, 消息列表, 系统提示词, 温度, 最大令牌数, 工具, 响应格式, 附加请求头)` → 任务句柄。
   提交立即返回；不等模型，不占同步调用预算。
3. 轮询 `2503 读取生成任务(任务句柄)`：`内容` 是累计全文，`已完成` 为真且 `资源在途` 为假时收口。
4. `2505 释放生成任务(任务句柄)`；线程未退完返回假，稍后重试。
5. `2506 释放句柄(句柄)`。

## 边界

- 连接与流内停顿各五秒上限；模型整体生成时长不受这五秒限制，但上游若超过五秒不吐任何字节会明确失败。
- 句柄至 64 个、任务至 64 个，超出返回 2506 资源受限。
- 端点由调用方配置，属运维指定的服务地址，不套用面向任意网址的出站策略；不继承环境代理。
- 任务与句柄只在当前扩展实例内有效，不承诺跨重启；卸载先拒新任务并置取消，线程未退完报延迟释放。

## 模型服务生命周期（2512-2515）—— 拉起模型的唯一入口

**只有经这四口起的模型进程才进底座的服务表**；调用方直接 `Command::spawn` / 直接敲 `llama-server`
起的进程不归任何人管，空闲回收够不着，会变成白占内存的孤儿（2026-11-04 实测过 22 小时）。

1. `2512 拉起模型服务(模型引用, 可执行文件, 启动参数, 监听端口, 就绪路径)` → 服务句柄。
   `启动参数` 是一个字符串、按空格切成 argv（路径里有空格时不要用这一口，改用带引号的包装脚本）。
   端口上**已有服务在听就拒绝**（25010）—— 这是孤儿的主要来源，必须先释放再拉。
2. `2515 等待模型就绪(服务句柄, 超时毫秒)` → 逻辑型。
   **就绪 = 端口在听 + 就绪路径回 200 + 服务若有 `/health` 则它也必须是 200**。
   只看端口或只看 `/v1/models` 不够：llama-server 在模型还没加载完时 `/v1/models` 就回 200，
   但 `/v1/chat/completions` 直接 **503**（「显示已就绪、一问就挂」，2026-11-04 实测）。
   `/health` 才是真判据：加载中 503、加载完 200。
   超时回**假**；进程在就绪前退出回 `2509 拉起失败`（不把「起不来」当「还没起来」）。
   单次等待封顶 **3 秒**：传 5000 会先撞内核调用预算，报成内核的 `4 超时`。模型加载慢就**循环调用**。
3. `2514 取模型服务状态(服务句柄)` → JSON 文本：
   `服务句柄 / 进程号 / 监听端口 / 存活 / 端口就绪 / 运行秒 / CPU毫秒 / 就绪路径 / 状态`。
   `CPU毫秒` 读不到给 `null`（不猜 0）；`状态` 三态：`启动中` / `就绪` / `已退出`。
4. `2513 释放模型服务(服务句柄)` → 逻辑型。
   先 SIGTERM、最多等 5 秒、仍在再 SIGKILL；**真 = 已确认进程不在**（不是「信号已发」），
   假 = 进程仍在跑、条目保留可重试。

判「是不是真在工作」的口径：连查两次 `CPU毫秒`，增量为 0 且 `端口就绪` 为真 ⇒ 空闲（可让位）；
增量在涨 ⇒ 在工作；`存活` 真但端口不就绪 ⇒ 启动中或卡住。

边界：不代理推理请求（请求仍走 2501/2502）；不猜端口；不按进程名或端口盲杀，释放只认本表登记的进程号。

## 传参怎么写（三种写法，实测结果）

| 写法 | 结果 |
|---|---|
| `{"参数名": 裸值}` | **200 成功** —— 底座按契约声明的类型自动装箱，最省事 |
| `{"参数名": {"类型标签":N,"值":V}}` | **200 成功** —— 显式给类型，类型不符会被拒 |
| `[{...}, {...}]` 数组 | **400 拒绝** —— `命名值 必须是对象` |

结论：**一律用对象 + 裸值**。句柄传 `{"服务句柄": 900001}` 就行，不必包 `{"类型标签":6,...}`。
类型标签含义（底座内置、公布后永不改写）：`0 空 · 1 整数 · 2 双精度 · 3 逻辑型 · 4 文本 · 5 字节集 · 6 句柄`。

## 缓存前缀约定（吃满 prompt cache 的唯一写法）

llama-server 的 prompt cache 默认就开，**但只按「从头开始的最长公共前缀」命中**。
实测（同一段 652 token 前缀连发三次）：

| 次 | 耗时 | prompt token | 命中缓存 |
|---|---|---|---|
| 1 | 0.67s | 652 | 0 |
| 2 | 0.44s | 652 | **646（99%）** |
| 3 | 0.44s | 652 | **646** |

所以消息必须这样摆，**顺序错了就一次都不命中**：

1. **`系统提示词`（2502 的第 3 个参数）** = 所有**长期不变**的东西：身份、产品资料、规则、口径。越长越划算。
2. **`消息列表`** = 历史轮次 + 当前问题，**只追加、不改写**。
3. **当前问题放最末一条**。

三条铁律：

- **禁止把会变的东西放最前面**：时间戳、「今天是几号」、随机请求 ID、递增序号，放进去就把整段缓存废掉。
- **禁止回头改历史**：往历史中间插一句、改一个字，前缀就断了，后面全部重算。
- **禁止每轮重排**：同一段资料每次换个顺序拼，等于每次都 miss。

要注入「会变」的信息（当前时间、本次参数），放到**当前问题那一条里**，不要动前面。
