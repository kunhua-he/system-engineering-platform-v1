# 契约声明 · 数据格式

上级：系统工程平台 V1 ／ 落点：`契约声明/格式说明.md`
相关：`README.md` 第五节（唯一事实源）· `代码形态分工.md`（声明用 JSON）· `内核落点.md`（Rust 常量由它生成）· `验证流程图.md`（验证面读什么）

**唯一事实源**：本目录下的 JSON 是声明的唯一来源。编译进扩展的 Rust 常量是**生成物**，禁手改。

## 一 目录布局

```text
契约声明/
├─ 格式说明.md            本文件
├─ 平台声明.json           **底座自己**的声明：格式号 · 标识串 · 版本 · 要求宿主/内核版本 · 名称 · 说明 · 能力号段 · 通知号段 · 错误段位表
├─ 号段图.json             **全平台**的编号布局：能力号段 · 通知号段 · 资源号段 · 错误码段位图（与「声明自己占哪几段」不是一回事，见第二节）
├─ 常量表.json             全平台常量的**唯一定义处**（判据：同一个字面量出现 ≥2 次即违规，必须改成引用本表）
├─ 类型声明/               一个类型一份 JSON（文件名 = 类型标签，如 0001.json）
├─ 能力声明/               一条能力一份 JSON（文件名 = 能力编号，如 1001.json）
├─ 命令类别/               一个命令类别一份 JSON（文件名 = 类别号，如 0000.json）—— `命令信息.类别` 的「号 → 名」表，见 §三·五
├─ 错误码表/               一个错误码一份 JSON（文件名 = 码，如 2043.json）
├─ 通知号段/               一个通知号一份 JSON（文件名 = 通知号，如 2000.json）
├─ 作废号表.json           已作废的编号（只增不改；编号永不回收）
└─ 冻结登记.json           冻结项清单 + 旁路登记
```

**一个号一个文件**是刻意的：编号冲突变成文件名冲突，**在文件系统层面就撞车**，不需要等验证面跑。

### ★ 本目录只装**底座自己的**声明

这一条踩过：目录名叫「契约声明」，容易被当成「全平台的声明都放这儿」。不是。

| 谁的声明 | 放哪 | 谁写 |
|---|---|---|
| **底座自己**（内核自有 `0xxx`） | **本目录** | `对外接口面/声明编写面/` |
| **扩展**（支持库 `1xxx–6xxx` · 模块 `7xxx` · 技能 `8xxx`） | **扩展自己的目录里** | 扩展作者，按 `扩展装载/开发标准/` |

为什么必须这样分：README 的三条硬边界第一条是「**底座不认识任何扩展**——底座里不许出现任何扩展的名字、路径或特例分支」。若把扩展的能力声明堆进本目录，底座就「认识」它们了：本目录的内容会被编译进底座制品，等于每次加一个扩展都要重发底座。

所以 `能力声明/` 里装的是**底座自己的** `0xxx` 命令（底座在 `平台声明.json` 里申报的占用就是 `能力号段=[{起:0,止:999}]`，`错误段位表=[0, 9]`），不是扩展的 1101–1107。`9xxx` 归**接口面与构建验证**那一层（见 `号段图.json` 的归属），**不是底座的命令** —— 别把它当成底座的能力号；底座在错误码上**代它占段位 9**（9001–9007，接口面业务层失败的码，见 `决策记录/2026-09-27_段位9错误码表.md`）。扩展的那份声明在它自己的目录里，由 `扩展装载/` 在载入时读。

## 二 平台声明（`平台声明.json`）

```json
{
  "声明格式号": 20000101,
  "标识串": "d09f2340818511d396f6aaf844c7e325",
  "实现版本":  { "主": 0, "次": 1, "修订": 0, "构建": 1 },
  "要求宿主版本": { "主": 0, "次": 1, "修订": 0, "构建": 0 },
  "要求内核版本": { "主": 0, "次": 1, "修订": 0, "构建": 0 },
  "名称": "系统工程平台 V1 底座",
  "说明": "底座自带的内核能力；其余能力由扩展提供，按契约热载入",
  "目标字宽": 64,
  "能力号段": [ { "起": 0,    "止": 999  } ],
  "通知号段": [ { "起": 2000, "止": 2999 } ],
  "错误段位表": [0, 9]
}
```

三个键名与 `平台信息` 的三个旁路字段**逐字对应**（`能力号段` / `通知号段` / `错误段位表`），生成器不做改名——改名就是又造一个「同一事实两个名字」的漂移点。

### ★ `能力号段` 在这两个地方不是一回事（这一条踩过）

| 在哪 | 是什么 | 例 |
|---|---|---|
| `平台声明.json` 的 `能力号段` | **本声明自己占哪几段** | 底座占 `[(0,999)]` |
| `号段图.json` 的 `能力号段` | **全平台的布局**：每一段归谁 | 5 段（内核自有 / 支持库 / 模块 / 技能 / 接口面） |

两者同名不同义，**必须分开**。曾把全平台那张 5 段的图当成「本声明占用」塞进底座声明——生成物于是声称底座占了 5 段（含支持库那一段），而底座其实只占 `0xxx`。这是「同一事实两个来源」的另一种形态：**同名不同义**。

`号段图.json` 是**平台的**，不是任何一份声明的：所以它既不是底座声明的字段，也不进 `平台信息`。

**`声明格式号` 是格式的身份证，不是版本号**：格式不变，它永远不变。

**★ 两张号段表必须分开**（`能力号段` / `通知号段`）：能力编号与通知号是**两个独立命名空间**，各有自己的 0–9999 与 1–2999 区间。合成一张表会把通知号 2000 判成「落在支持库 1000–6999 里」——这个错我自己的预检当场抓到过。

**`错误段位表` 里是「段位」不是「码」**：段位 = 码的首位十进制数字，也即能力号段的首位（号段即归属）。底座占段位 0（码 1..999）。

## 三 能力声明（`能力声明/<编号>.json`）

```json
{
  "编号": 1001,
  "名称": "取系统时间",
  "说明": "返回当前系统时间，单位为毫秒",
  "类别": 1,
  "状态位": 0,
  "返回类型": 1,
  "用户级别": 0,
  "参数表": [
    { "名称": "时区偏移分钟", "说明": "0 表示本机时区", "类型标签": 1, "状态位": 0, "默认值": { "类型标签": 1, "值": 0 } }
  ],
  "可抛错误码": [1001, 1002]
}
```

规则：

| 字段 | 规则 |
|---|---|
| `编号` | 必须与文件名一致；必须在 `能力号段` 里属于自己那一层；**不许出现在 `作废号表.json` 的 `能力` 空间（`号空间: "能力"`）里**（§七：作废只封同空间的号） |
| `参数表` | **行序即契约**。一旦公布不许重排、不许插入（要加只能新增旁路字段） |
| `参数表[].类型标签` | 必须能在 `类型声明/` 里查到 |
| `返回类型` | 同上；`0` 表示无返回值 |
| `可抛错误码` | 每一项都必须能在 `错误码表/` 里查到，**未登记的不许声明** |

## 三·五 命令类别（`命令类别/<类别号>.json`）

```json
{
  "类别号": 0,
  "名称": "……",
  "说明": "……"
}
```

**为什么有这一节**：`命令信息` 有 `类别: u16`，而顶层原先**没有**「类别号 → 类别名」的表
⇒ 这个号在运行期**永远解不出名字**。参照实现在 `LIB_INFO +0x5C/+0x60` 有一对（计数 + 串块；
字节级实测见 `项目文档/设计文档/接缝实测.md` §二/§三 —— `shellEx` 的 4 条类别串
`['提示工具','拖放功能','热键功能','系统功能']` 与命令 `cat=1..4` 正好一一对应）。
本目录补上这一对（**补的是我方自有的表，不是复刻它的结构**：它的表是「连续 NUL 结尾串块 +
双 NUL 结束」，我方是 `#[repr(C)]` 项表 + NUL 结尾串）。

| 字段 | 规则 |
|---|---|
| `类别号` | 必须与文件名一致（文件名即类别号）；同一份声明里不许重号（生成器 fail-closed） |
| `名称` / `说明` | 非空串；进生成物的 `命令类别表`，由 `v1_contract::取命令类别名(类别号)` 查（查不到返回空指针） |

### ★ 值域与含义**尚未裁** —— 生成器**不替它编一个值域**

既有件里**没有**权威的「类别号 → 含义」定义：参照实现的类别表是**每个库自己的**
（`shellEx` 的 4 条是它自己的分类，不是全平台值域），我方 `命令信息.类别` 现在全是 `0`
但**没有任何一处写出 `0` 叫什么**。⇒ 按「不发明」的口径，本表**允许为空**
（`契约声明/命令类别/` 下只有 `.gitkeep`）：

- **空表 = 「表在（机制已通），值域待裁」**，不是漏写 —— 生成物里 `命令类别表` 仍然存在
  （`[v1_contract::命令类别信息; 0]`），`取命令类别名` 仍然在，机制已通。
- 生成器**不 fail-closed**：它把「`能力声明` 里用到、而 `命令类别/` 没登记的类别」报成**提醒**
  （走 stderr，不卡生成），并注明口径待裁。**拿一条未定的口径去卡生成 = 让一条待裁冻住整份生成物。**
- 值域定了之后：把条目按 `类别号.json` 落进 `命令类别/`，重跑生成器即得常量与可查的表，
  那条提醒自然归零。见 §十 待裁。

## 四 类型声明（`类型声明/<标签>.json`）

```json
{
  "类型标签": 1,
  "名称": "整数",
  "说明": "64 位有符号整数",
  "状态位": 0,
  "元素表": [],
  "属性表": [],
  "事件表": [],
  "命令号表": []
}
```

**类型标签是槽内携带的那个数**——它是多语言兼容的锚点，所以标签一旦公布，含义永不改写。
它自成一个**号空间**（第五个：`号空间: "类型"`，见 §七）——与能力号 / 通知号 / 错误码 / 资源号
**互不相通**（`字段名册与引用方式.md` §五：「类型标签 … 与上面四个不通」）：同一个数字在五个空间
里是五个东西（类型标签 `0` 与能力号 `0` 无关）。

### ★ `0` 是保留标签「空」，扩展不许复用

底座自己就是那张内置标签注册表：`0` 空 · `1–6` 整数/双精度/逻辑/文本/字节集/句柄 · `4294967295` 错误。

**任何非底座声明都不许再登记这些标签**——包括 `0`。规则对**所有声明一视同仁**，`0` 只是其中一个实例。

**不许做成「底座例外」**：例外会繁殖。真正的规则是「**不许复用已登记的标签**」，它对 `0` 与 `1–6`、`4294967295` 是同一条。装载入口原先那个 `类型标签未显式`（把 `0` 当「没填」）已删——它判不到：「没填」与「填了 0」在运行期不可区分（JSON 里 `类型标签` 是必填键，缺键由验证面抓），留着就是一条永远判不准的判据。

扩展的类型从 `100` 起。

## 五 错误码表（`错误码表/<码>.json`）

**段位 0（内核自有，码 1–999）已定义全表**，共 **31** 条（0016 已作废删档；判据 ⑦ 盯着「码表 ↔ 段位表 ↔ 生成物」三方一致），覆盖判定六步 + 建表 + 调度三处会抛的每一个失败。段位 9（接口面与构建验证）已开 **9001–9007** 共 7 条。段位 1–8 的归属见 `号段图.json` 的 `错误码段位图`，**谁用谁立，不预先填满**。

**建表阶段的失败与判定阶段的失败共用同一套码**（同一个失败不因为报在哪个阶段而换码）：`项表为空`=18 · `函数表项数不符`=19 · `类型表自相矛盾`=20 · `常量表自相矛盾`=21 · 而建表侧的 `格式号不匹配`/`标识串重复`/`号段冲突` 复用 6/7/8。

```json
{
  "码": 2043,
  "名称": "文件不存在",
  "说明": "目标路径不存在或不可访问",
  "段位": 2,
  "可重试": false,
  "可自愈": false,
  "需人工": true
}
```

**`码` 与 `段位` 不是一回事**（这一条踩过：字段名曾叫「段位」却存着整个码，是典型的「同名不同义」）：
- `码` = 完整的 4 位号，**就是文件名**，全局唯一、永不回收
- `段位` = 码的首位十进制数字（0–9），也即能力号段的首位（号段即归属）
- 编法：`<段位 1 位><序 3 位>`，例 `2043` = 段位 2 的第 43 号；段位 `0` = 内核自有

### 登记项分两类（这一条踩过：曾把两类混成「四项」）

| 类 | 字段 | 说明 |
|---|---|---|
| **业务登记项**（3 项，人必须给） | `可重试` · `可自愈` · `需人工` | 「失败可编程处理」的全部依据。**验证面猜不出来**——这是业务判断 |
| **冗余登记项**（1 项，可从 `码` 导出，但故意写出来） | `段位` | `段位 == 码 // 1000`。写出来是为了**让验证面交叉比对抓错**：写错了当场判红，而不是默默按错的用 |

**未登记的错误码不许抛出。** 这三项业务判断必须**到得了运行期**——所以 `平台信息` 里有 `错误码表: 表段<错误码信息>`（见 `契约声明/src/lib.rs`），调用方拿到 `码` 之后能查到这三项。**只写进注释就等于没写。**

## 六 通知号段（`通知号段/<通知号>.json`）

```json
{
  "通知号": 2015,
  "名称": "延迟释放应答",
  "说明": "扩展返回它表示自己需要被延迟释放",
  "方向": "上行",
  "参数": ["无", "无"]
}
```

**`方向` 只取 `下行` / `上行` 两个值**——它是**协议方向**，不是号段名。

号段由**通知号本身**决定：`1–999` 下行 · `1000–1999` 上行 · `2000–2999` 生命周期段。
生命周期段里**两个方向都会出现**（装载/卸载/退出是下行，延迟释放应答是上行），所以它不能当成 `方向` 的第三个取值——那样磁盘上 `2000..2003.json`（方向 `下行`）会被整批判成违规。

## 七 作废号表（`作废号表.json`）

```json
{
  "说明": "编号永不回收。删掉的能力，号进这里，含义永不改写",
  "作废": [
    { "编号": 1002, "原名称": "旧取时间", "作废于": "2026-09-26", "原因": "被 1001 取代",
      "号空间": "能力" }
  ]
}
```

作废行是**五键**：`编号` · `原名称` · `作废于` · `原因` · `号空间`。

**`号空间` 是「这个号在哪个空间里作废」的唯一依据**，值域**五个**：`能力` / `类型` / `通知` /
`错误码` / `资源`。前四个是号段空间（`号段图.json` 的「四个号空间互不相通」：能力号 · 通知号 ·
错误码 · 资源号）；**第五个 `类型` 是类型标签空间**——它是独立空间（`字段名册与引用方式.md` §五：
类型标签「与上面四个不通」），只是不属号段制（`u32` 全域，无号段可依，见 §十 待裁第 3 条），
故 `号段图.json` 里没有它，值域也不能漏它（漏了 ⇒ `类型声明/` 掉出检查 3 的覆盖）。
**作废只封同空间的号** —— 数字相同不算同号（能力号 `16` 与错误码 `16` 只是数字上撞了同一个数，
不是同一个号；类型标签 `0` 与能力号 `0` 同理）。
缺了 `号空间`，这个号会被五个空间**一起**排除 ⇒ 那正是实测的假冲突：错误码 `16` 进作废表，
底座 `能力号段 0–999` 含 `16` ⇒ 底座自己载不进来（`号段冲突{起:0,止:999}` · 31 条红）。
故生成器与判据面对缺 `号空间` / 值不在值域的行一律 **fail-closed**。

## 八 生成关系（JSON → Rust 常量）

```text
契约声明/*.json  ──生成器（Python，仅标准库）──→  契约声明/src/声明数据.rs
                                                      ↑ 生成物，禁手改
```

生成器落点：`构建装配/形态装配/`（「读契约 + 收能力 → 出形态」就是它的职责）。
产物头必须标：生成物声明 · 源文件清单 · **源文件指纹** · 生成器路径。生成器须带 `--检查` 模式（重新生成并与落盘件逐字节比对）——这就是四道闸里的**生成物指纹闸**。

### 源与落点（全部从「声明根」派生）

```text
<声明根>/平台声明.json（扩展那份叫 包声明.json，同形状，二者取其一）
<声明根>/号段图.json · <声明根>/常量表.json · <声明根>/作废号表.json
<声明根>/类型声明/*.json · <声明根>/能力声明/*.json · <声明根>/错误码表/*.json · <声明根>/通知号段/*.json
<声明根>/命令类别/*.json   ← 可缺 / 可空（值域待裁，见 §三·五）；缺 = 空表，不是 fail-closed
        │
        └── 生成器（Python，仅标准库）──→  <声明根>/src/声明数据.rs   ← 生成物，禁手改
```

**`能力声明/*.json` 是命令编号（`命令信息.编号`）的源**：生成器逐条出 `能力编号_<编号>` 常量，
实现侧命令表的 `编号` 字段引用它（`命令信息.编号` 是显式字段，**不是**表内下标）。
命令的名称 / 说明 / 参数表 / 可抛错误码由实现侧手写（JSON 侧另有源），两者是否一致
由「声明 ↔ 实现」那组判据（③a–③d）盯着；函数表（执行函数）是代码，同样由实现侧手写，
与命令表一一对应。

**声明根**是可传的参数（默认 `契约声明`）：`python 构建装配/形态装配/生成声明.py --声明根 <目录>`。只认**仓内相对路径** —— 绝对路径会让产物带上机器相关前缀、破坏确定性，故解析到仓外即 fail-closed。根下面有什么、叫什么，是**声明的形状**，不随根变；换根 = 换一份声明，加字段 = 改形状（后者要走 `冻结登记.json`）。

### `常量表.json` 怎么进生成物（判据按**名**，不按值）

`常量表.json` 自称「全平台常量的唯一定义处」。一份没有任何读方的声明等于零，故生成器**逐条**给它落点，一条不漏：

1. **值另有源的条目**（`声明格式号` · `目标字宽` ← `平台声明.json`；`号段类宽度` · `号段类个数` ← `号段图.json` 推导）：生成物**只做交叉比对**，常量出在对应小节；两源不一致即 fail-closed。
2. **本表即唯一源的条目**：逐条出定宽整数常量（`位宽` → `u16`/`u32`/`u64`），每条上方带它的「依据」（源 = 本表那条）。
3. **`值` = `null` 的条目**（未定数）：**显式跳过**，并把名字写进生成物的 `未定数常量` 表 —— 不是静默跳过（静默跳过 = 一份没有任何效果的声明，最坏）。定数后把值填进本表、重跑生成器即得常量。

判据（本表 `判据` 键）：① 同一个常量名不许在别处再定义（实现侧必须引用本表生成的常量）② 本表每条常量在生成物里要么有对应常量、要么有显式的「未定数」标注。

### `号段图.json` 推出的三样

- `号段类宽度` = `能力号段` 全部段边界（每段的 `起` 与 `止 + 1`）的**最大公约数**（本例 `{0,1000,7000,8000,9000,10000}` ⇒ 1000）；`号段类个数` = `(最大止 + 1) ÷ 号段类宽度` = 段位上界 + 1（本例 10）。**推不出来（gcd ≤ 1，即出现不等宽/未对齐的段）即 fail-closed**，不写「大概对」的推导。
- 通知号的三个号段（`下行` · `上行` · `生命周期`）：按 `通知号段` 的 `归属` 前缀取，出成生成物里的 `通知号段` 模块；`v1_contract::通知号段` 就是 `pub use` 它。
- 占用段的 `归属` 注释 + 「占用 ⊆ 布局」校验（不满足即 fail-closed）。

`号段图.json` 是**全平台布局**，**不进** `平台信息`，故生成物里不产出任何「全平台号段图」常量（留一份就是第二个来源）。

**判据**：**手写 = 声明数据字段的值不是 `声明数据::…`**（不是「构造点存在即违规」）。

**为什么要把定义写死**：`static 底座存储: 静态声明 = 静态声明(平台信息 { … })` 这个**构造点必须存在**——装载入口自己就是消费方，它得有个静态实例才能导出符号。收口之后这个构造点保留，只把**字段值**换成 `声明数据::…`。所以「手写」只能按**值**判，不能按**构造点**判；按构造点判会让这条判据永远红。

连带：**测试夹具**（`#[cfg(test)]` 内的合成声明）不算底座声明，但另受两条更严的条件约束——①必须在 `#[cfg(test)]` 内 ②不许被生产代码引用。

## 九 验证面查什么（闸 2 的声明侧）

| # | 检查 | 依据 |
|---|---|---|
| 1 | 编号与文件名一致 | 文件名即编号 |
| 2 | 编号不重复 | 文件名天然唯一，另查 JSON 内字段与文件名一致 |
| 3 | 编号不在作废号表里 | `作废号表.json` |
| 4 | 编号落在自己那一层号段内 | `号段图.json` 的 `能力号段`（布局）；另查 `平台声明.json` 的 `能力号段`（占用）⊆ 布局 |
| 5 | 参数类型都在类型表里 | `类型声明/` |
| 6 | 返回类型在类型表里（或为 0） | 同上 |
| 7 | `可抛错误码` 每一项都在错误码表登记，三项业务登记项齐全，且冗余登记项 `段位 == 码 // 1000` | `错误码表/` |
| 8 | 通知号落在对应方向的号段内 | `通知号段/` |
| 9 | 冻结登记三键齐全 · 落点存在且是**单个**落点 · 日期成形 | 冻结登记 |
| 10 | 生成物与 JSON 一致（指纹比对） | 生成关系 |

这十项全部是**纯数据比对**，不编译、不启动、不跑用例——所以秒级。
