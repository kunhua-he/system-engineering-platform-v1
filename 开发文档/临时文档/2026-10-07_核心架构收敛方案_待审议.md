## 一、执行摘要

**结论：保留 V1，不建议再次重写；先补齐运行闭环，再冻结公共机制，最后扩大扩展接入。**

V1 已具备值得保留的基础：契约与实现分离、号段寻址、定长数据槽、显式实例状态、单一适配器、结构化错误和秒级静态门禁。当前主要问题不是目录不够细，而是部分机制尚未形成完整保障：契约表达与生成、执行隔离、生命周期、Agent 重试语义以及可复现的发布证据。

建议按以下顺序收敛：

1. 对齐规则与验证基线，避免把缺材料、未覆盖或严格检查失败误读成成熟。
2. 补齐类型、默认值、扩展声明生成与统一边界校验。
3. 在既有适配器落点完成子进程与 IPC，隔离扩展故障。
4. 收紧装载引用、在途调用、卸载、重启和任务句柄失效规则。
5. 建立由契约驱动的 Agent 搜索、取契约与调用体验。
6. 用代表性老能力验证稳定边界，再冻结并批量接入。

**最终目标不是让所有实现永远不变，而是让新增能力与业务策略不再迫使底座变化。**

阅读建议：不熟悉架构时先看第三十节的白话结论和第三十一节的推荐取舍，再看第三十五节的施工包与第三十八节的交付判断。技术审议看第十八至二十六节及第三十二至三十六节。第二十节保留60个基础事项，第三十四节补充12个细化事项，共72项；不是72个已复现缺陷，也不是72项都要同时开工。已确认、待验证和新增建议分别标识。

## 二、定位、范围与证据口径

### 2.1 平台画像

本方案按“Agent 本机能力调用平台”设计：业务项目与平台独立，Agent 通过统一逻辑入口发现和调用能力。内核仍是编译器式机制底座，不发展成承载业务、任务编排和运营策略的应用服务器。

本轮不以公网多租户、分布式调度或云控制面为前提，不引入 npm、前端框架或第三方 Rust 依赖，不改既定语言分工。

### 2.2 调研范围与限制

- V1：README、实际架构、信息核心中的相关裁决及未完成台账；调用调度、适配器、资源网关口、HTTP 网关、契约生成器及部分测试路径。
- 老项目：定位文档、网关装配与 Agent 薄壳定点对照。旧仓 CodeGraph 索引无法打开，因此不声称完成老项目全量代码审计。
- 已验证：静态门禁、底座工作区测试、编译器支持库独立测试和严格 Clippy。
- 尚未验证：真实子进程隔离、故意崩溃与永久阻塞扩展、所有跨载体兼容组合、长期负载及全部老能力迁移。

## 三、新旧项目的取舍

### 3.1 应继承的能力

- Agent 只需要“搜索能力 → 获取所需契约 → 调用能力”，不需要理解平台内部目录。
- 业务零侵入：不复制底座、不 import 平台内部实现。
- 支持库承担原子能力，模块承担组合流程，技能承担 Agent 使用方式。
- 调用失败可结构化判定，不靠解析自然语言猜测。
- 能力由声明发现，避免在 Agent 上下文中一次塞入全部接口。

### 3.2 不应搬运的结构

老项目网关装配同时涉及参数校验、别名、幂等、限流、审计、任务系统等职责，多个混入类共享宿主状态。拆小文件有助于阅读，但不等于职责耦合消失。

对照依据：老项目 `运行核心/统一网关/网关核心.py` 的职责说明、混入类装配和构造函数；`开发工具/薄壳/薄壳服务.py` 的结果呈现逻辑。

**建议：继承使用体验与必要运行保障，不照搬旧控制面的职责聚合方式，也不直接搬入整套任务系统。**

## 四、收敛原则

1. **冻结公共语义，不冻结半成品。** 类型、所有权和故障语义未闭环之前，不以“几十年不动”作为已实现承诺。
2. **唯一机制不等于单一实例。** 一个权威实现可以有多个显式实例，各实例状态隔离。
3. **无状态协议不等于无状态宿主。** 调用方无需连接管理；宿主仍可持有执行域、装载状态和配额。
4. **载体变化不产生第二套业务语义。** 进程内、IPC 等模式复用契约、校验与错误含义。
5. **机制与策略分离。** 通用调用、超时判定和所有权属于机制；重启预算、业务重试和补偿属于策略。
6. **生成物不是第二个事实源。** 接口描述、绑定和静态声明由声明生成，不手写重复语义。
7. **验证按证据分级。** 静态合规、行为正确、故障隔离与发布可用不能混成一个“绿”。
8. **以改变成本判断成熟。** 能连续新增不同类型扩展而不修改底座，才算边界稳定。

## 五、目标架构与职责归属

```text
Agent / 业务程序 / 网页
          │
          ▼
Agent 薄壳：搜索、取契约、调用
          │
          ▼
唯一逻辑网关：协议转换、请求形状、结果呈现
          │
          ▼
适配器实例＝运行宿主：装载、执行域、进程监督、生命周期、调用上下文
          │
          ▼
稳定内核：注册寻址、数据槽、所有权、通知、调用判定、留痕机制
          │
          ▼
扩展：支持库 / 模块库 / 技能库

契约声明 → 构建与验证 → 不可变制品及派生接口描述 → 宿主装载
```

“运行宿主”是现有适配器的职责描述，不是建议新增内核节点。图表达逻辑调用关系，不改变仓内已定分层依赖。

| 归属 | 负责 | 禁止承载 |
|---|---|---|
| 契约声明 | 编号、类型、调用形状、错误语义、兼容规则 | 部署路径、密钥、业务策略 |
| 运行内核 | 寻址、边界表示、所有权、通知、通用调用判定与留痕机制 | 具体扩展特例、业务工作流、业务补偿 |
| 适配器宿主 | 装载实例、执行载体、进程监督、在途引用与通用调用上下文 | 具体业务任务状态、能力专属流程 |
| 网关和薄壳 | 协议转换、契约发现、结果呈现 | 第二套调度或直接调用扩展的旁路 |
| 支持库、模块、技能 | 能力实现、组合流程、任务结果、业务恢复与幂等 | 绕过底座边界的特权路径 |
| 构建、验证与开发工具 | 生成、检查、打包、取证、仓库维护 | 参与生产运行或成为使用角色的第二入口 |

## 六、契约闭环

### 6.1 已确认的保障差异

通用能力调用路主要检查参数个数，并将逐槽正确性作为调用方约定；资源网关口则有输入、输出逐位形状检查。不能因此声称每个能力都存在错误，但两条路径的平台级保障不一致。

证据位置：`运行内核/调用调度/src/调度核心.rs::调度调用`、`跨语言适配/适配器实现/src/核心实现/适配器定义.rs::调用能力`、`跨语言适配/资源网关口/src/关口/关口主体.rs::派发`。

### 6.2 建议方案

- 在既有调用判定路径内统一检查参数个数、逐位类型和返回类型；错误槽作为结构化失败处理。
- 网关与 IPC 负责合法编码的解析，不各写一套能力语义校验。
- 原生指针有效性不能仅靠类型标签证明；进程内模式须明确可信调用约束，跨进程模式禁止传可解引用的远端指针。
- 保留现有定长槽布局；列表、记录等结构通过新增类型号及明确编码约定承载。
- 结构化载荷明确元素类型、字段形状、大小、嵌套和所有权限制，不以“字节集”掩盖类型语义。
- 文本及浮点默认值由声明和生成器正式支持；涉及冻结字段时采用登记的旁路或兼容版本，不改写旧字段含义。
- 扩展与底座复用生成流程。扩展无通知可合法表达为空，但必填项仍须严格验证。
- 接口描述、绑定和静态声明都从同一声明派生；发布时比对声明与生成物指纹。

### 6.3 验收与既有台账

优先解决台账309“类型系统与默认值”、310“扩展声明生成”，再扩大台账308的批量迁移。

验收：一个含列表、记录、文本默认值及结构化错误的独立扩展，仅写声明与实现即可接入；生成物不手改，类型语义不降级，底座没有扩展特例。

默认值限制证据：`构建装配/形态装配/生成声明/读子表.py::读能力声明`，当前默认值的“值”经整数读取函数消费。

## 七、执行隔离与 IPC

### 7.1 现状与已定分工

当前调度在执行返回后判超时，永久阻塞的执行方不会走到该判断。发布配置为 `panic = "abort"`；进程内执行不能靠工作线程或 `catch_unwind` 获得可靠的崩溃隔离。

证据：`运行内核/调用调度/src/调度核心.rs::调度调用`、根 `Cargo.toml` 的发布配置；相关官方说明见第十七节。

保留已有裁决：进程管理落在适配器；调度负责判定与报码，不承载进程逻辑；跨进程沿用现有契约与调用语义；0034“能力进程崩溃”按既有占号裁决随实际调用方落地，不预先宣称已实现。

### 7.2 六项未定问题的推荐收口

| 问题 | 推荐方案 | 边界 |
|---|---|---|
| 进程池粒度 | 按适配器实例、扩展标识和制品版本划分执行域；初版每域一个工作进程 | 不混装无关扩展；扩展未声明可并发时不擅自并发执行 |
| IPC载体 | 当前本机优先使用 Unix domain socket | 后续 Windows 只替换传输实现，不另造调用语义 |
| 帧与长度 | 帧头明确协议版本、消息类型、请求号、载荷长度；解析先校界限再分配 | 分别限制单帧、整次调用及累计缓冲；不允许无界内存分配 |
| 背压 | 有界队列，容量耗尽时结构化拒绝 | 不静默丢调用，不无限等待；控制消息保留处理能力 |
| 反复崩溃 | 适配器监督层负责退避、重启预算和熔断 | 阈值属于部署配置；业务是否重试由调用与能力保障决定 |
| 重放及引用归属 | 重放装载初始化，不默认恢复业务任务；宿主持有装载引用和在途执行租约 | 初始化重放不等于旧会话恢复；引用随调用结束、进程确认退出等明确事件释放 |

上述六项是完整的推荐方向，不是已经生效的协议。具体字段布局及容量参数在施工前通过专门裁决固化；参数值必须有压测或内存预算依据，不在本文冒充已有实测。

### 7.3 装载、执行与故障处置

- 动态扩展的实际装载与初始化也在工作进程内完成，宿主不先执行未知扩展代码再谈隔离。
- 内部就绪检查验证契约和制品身份，不要求 Agent 额外握手。
- 进程内模式保留给明确接受故障共享的可信场景；面向长期 Agent 使用，建议将进程池作为主要部署形态。改变默认模式须正式审议。
- 卡死回收由适配器的执行监督实现；内核仍保留既有超时判定职责。
- 通道EOF、进程退出和协议错误分别留痕；有必要新增错误码时按号段流程登记，不临时硬编码。
- 杀进程不撤销已经发生的外部副作用；仅重拉进程也不能保证业务恢复。
- 进程隔离不是文件、网络、密钥权限沙箱。没有操作系统级限制时，自描述必须如实说明。

验收：扩展崩溃、永久阻塞、IPC断连、半帧及超长帧均不使网关或其他执行域失去服务；使用确定的检测及回收预算验证，不只检查“最后返回一个错误”。

## 八、状态、所有权与生命周期

### 8.1 状态归属

| 状态 | 持有者 | 重启后的语义 |
|---|---|---|
| 契约和制品身份 | 声明及不可变制品；宿主持有装载引用 | 重新校验后装载 |
| 装载台账、进程、配额域、在途调用 | 适配器实例 | 按该实例的重建规则恢复或清空，不落隐式全局 |
| 任务状态、结果及业务恢复凭据 | 扩展 | 只按扩展声明的恢复能力处理 |
| 任务句柄 | 跨边界不透明值；有效性由生产者保证 | 不可恢复的任务明确失效，不能误命中新任务 |
| 跨边界返回值 | 既有所有权与分配协议规定的持有者 | 进程退出时清理域内资源；外部副作用另行处理 |
| 留痕 | 宿主既有留痕机制及部署选择的保存出口 | 查询能区分记录不存在与已有失败 |

不向内核增加业务任务注册表。任务句柄须避免重启后复用；可使用执行代次、明确有效性校验等机制，但不得破坏已有不透明值契约。

当前 C ABI 每次建立默认边界、配额不跨调用累积，是已记录的有意设计，不作为本轮擅改对象。必须说明嵌入形态与常驻宿主形态的状态范围，不能向调用方承诺实际上不存在的跨调用配额域。

证据：`跨语言适配/适配器实现/src/边界面.rs::默认边界`；数据库中的无状态边界及长活原语裁决。

### 8.2 并发与卸载

当前网关会持有适配器读锁执行请求，而追加装载需要写锁；长执行存在阻塞装载的结构性风险，尚未以压力场景证明影响范围。

证据：`对外接口面/调用接口面/src/网关.rs::造应答`。

建议采用“锁内取得执行引用、锁外执行”的路径。卸载分两步：先停止接收该执行域的新调用，再等待在途引用和延迟释放协商结束。执行引用有效期间不得卸载动态库或销毁其上下文。

生命周期回调也不应在全局状态锁内无限等待。状态转换在锁内完成，外部执行通过明确的超时、租约和回执机制衔接。

验收：调用、取消、装载、卸载和重启交错时，不提前释放、不串实例、不误用旧句柄；未完成卸载能返回明确状态而不是假成功。

## 九、Agent 使用面与重试安全

### 9.1 使用入口

运行薄壳建议保留少量职责：搜索能力、获取所需契约、调用能力。它与现有开发工具MCP的开工、编辑、符号查询和门禁职责分开，不把开发协议塞给使用角色。

命名参数由薄壳按声明映射成现有行序槽表，不改变底层调用形状。搜索目录是声明的派生视图，不新增手写能力清单。

工具描述和错误提示应回答：有什么、需要什么、执行保障是什么、失败后下一步是什么。MCP与HTTP均转入同一调用路径，不获得专属执行权。

### 9.2 结果表达

结构化结果保留成功或失败、值或错误码、追踪标识；长活另提供任务句柄。需要判断重试时，表达执行阶段、结果是否确定和重试前提。

文本说明是可读补充，不能替代机器可判断的结果；`false`、`0`、空列表等可能有契约含义，不做无差别省略。协议错误与能力执行失败分别映射，不将所有错误包装成同一种自然语言失败。

### 9.3 重试与幂等

| 情况 | 建议行为 |
|---|---|
| 执行前拒绝，明确没有进入扩展 | 按既有错误语义及调用方策略决定是否重试 |
| 无副作用或明确提供幂等保障 | 在声明的范围与有效期内允许有界重试 |
| 超时、断线或崩溃，不能确认副作用是否发生 | 返回结果未知，不自动重放 |
| 长活进程重启且任务不支持恢复 | 旧句柄明确失效，禁止假装任务继续 |

幂等请求身份代表调用意图，不是把相同参数哈希后永久去重。具体业务去重、结果持久化、恢复与补偿归扩展；宿主负责传递请求身份和记录通用执行状态，不承诺所有外部副作用“恰好执行一次”。

## 十四、变更控制与回退

| 变更 | 实施控制 | 回退与限制 |
|---|---|---|
| 契约及生成器 | 保持旧号含义；登记新增字段或类型；双向兼容测试 | 保留旧制品；若新输入无法由旧版解释，应明确拒绝而非静默降级 |

## 十五、核心冻结标准

以下条件满足并有对应证据后，才建议将公共机制标为稳定：

1. 新增能力只修改扩展，底座没有能力专属分支或路径。
2. 相同契约在支持的载体下具有一致的调用、校验与错误语义；平台特有故障明确区别。
3. 扩展崩溃、卡死和断连不影响网关及其他执行域。
4. 错误输入在执行前拒绝；错误输出不会静默进入上层。
5. 调用、卸载、取消和重启不误用旧句柄或提前释放资源。
6. 支持范围内的新旧调用方、宿主和制品兼容组合有实际测试。
7. 发布证据可复现，缺材料和未覆盖不能冒充通过。
8. 至少完成第十三节的五类试点，证明不是只对一个演示扩展成立。

冻结对象是公共机制、契约与职责边界；实现仍允许优化和修复。以后主要维护扩展，不代表内核不再承担安全、兼容与缺陷修复责任。

## 十八、增补结论：方案是否足够稳固，还有什么缺失

### 18.1 明确回答

**方向已经可以收敛，但当前代码尚未达到可冻结为成熟核心的程度；本文完善后也仍是候选方案，不是运行稳定性的证明。**

前十七节解决了主要职责边界；增补调研发现，未来支持库、模块和技能真正进入统一调用路时，还需要把“制品能被识别”与“能力能被执行或读取”之间的接缝补完整。

用户提出“先死磕核心，再接真实业务扩展”的顺序合理。但完全不使用扩展样本就冻结核心，无法证明接缝稳定。建议区分：

```text
真实业务接入：旧库大批迁移、业务模块上线、技能规模建设
    → 等核心验收后再做

契约考题：极小支持库、极小模块、极小技能、故障样本
    → 核心施工期必须做，只用于证明接缝，不发展业务
```

当前仓中已有编译器支持库和模块样本，不能简单说“完全没有任何扩展”。准确表述是：**已有验证样本，不代表三类扩展生态已经完成成熟接入。**

### 18.2 本次补查新增的关键缺口

| 事项 | 补查结果 | 对冻结核心的影响 |
|---|---|---|
| 模块执行体来源 | 模块读取器明确只解析、不执行；编译入口接收调用方提供的能力码并装包，不能单凭它证明源码生成了可运行执行体 | 必须证明程序文本如何成为可执行体，不能只完成IPC就宣布模块可运行 |
| 模块格式与执行方式 | 既有裁决把WASM定为打包格式、子进程加IPC定为执行路线 | 子进程和IPC不是WASM执行引擎；两者之间的转换或执行体生成仍须明确 |
| 技能真实取文路径 | 后缀表要求技能段19；目前查看的通用容器解包只接受16、17、18三段；未取得完整的技能注册、按8xxx取文证据 | 必须补齐同一codec对已声明技能形态的支持，并完成真实取文测试 |
| 热升级与热装载 | 当前热装载对已存在身份直接跳过，候选逐个追加；启动装配已有依赖重试排序 | “追加装载成功”不能代替版本切换；热装载的依赖处理也要与启动路径对齐 |
| 支持库解包缓存 | 当前缓存路径由包内指纹段生成，直接写文件；该路径未显式调用已有段指纹校验 | 需验证内容、指纹、缓存键及发布写入一致，防止半写和错误复用 |
| 原生库物理释放 | 当前取扩展声明路径明确让动态库句柄存活到进程结束 | 逻辑卸载不能冒充动态库内存已释放；进程隔离和引用释放须形成闭环 |
| 目标扩展是否接入成功 | 当前热装载响应可在配置缺失或候选剔除时返回顶层成功，另附说明与候选结果 | Agent必须能机器判定指定扩展已就绪，不能只读顶层成功 |

这些是接缝与运行保障问题，不是建议把业务重新塞进内核。证据集中在第二十八节。

### 18.3 不应再遗漏的边界

- 模块依赖哪个支持库版本，调用时是否还是那个版本。
- 同一身份的新版本如何替换旧版本，在途调用何时切换。
- 技能只提供说明，谁批准说明中的危险动作，依赖缺失如何提示。
- 有限队列之外，结果缓冲、任务结果、日志、缓存和子进程数量是否也有上限。
- 调用链追踪、取消传递、结果未知、重复提交与补偿是否能贯穿模块到支持库。
- 扩展自检通过、平台准入通过、部署成功、业务执行成功必须分别判定。

### 20.1 如何读清单

- **已确认缺口**：台账或源码明确缺少该保障；不表示已经复现生产事故。
- **已确认局限**：当前有意设计或实现范围限制，是否改变须审议。
- **待验证**：需要实测或更完整代码取证，不能提前写成缺陷。
- **建议补齐**：为目标架构提出的设计或交付要求，不冒充当前承诺。
- **已有机制／补证据**：机制已经存在，重点是扩大真实覆盖，不重复造实现。
- **P0**：阻断面向三类扩展的核心冻结；**P1**：阻断规模接入或明确保障；**P2**：维护和使用体验完善。优先级属于本方案，不是现行安全漏洞评级。

| F10 | P1／建议补齐 | 冻结后的核心准入、公开面变更影响和责任归属清楚 | L17、L01、L16 | 新业务需求先落扩展，机制变更有兼容证据 |

## 二十一、文本式流程图

以下图中“拒绝”均应留下原因与关联读数；箭头表示责任交接，不是允许新增跨层调用。

### 21.1 核心稳固的顺序

```text
规则与契约口径一致
       ↓
声明能生成、参数能校验、三类制品能正确区分
       ↓
支持库执行域＋模块执行体＋技能取文三条接缝考题
       ↓
IPC、故障隔离、在途引用、卸载、重启、升级
       ↓
发布制品下正向、负向、兼容及回退实测
       ↓
核心候选验收 → 批准冻结公共机制
       ↓
少量真实支持库 → 少量组合模块 → 技能整理
       ↓
保真与依赖规范验证通过 → 批量迁移
```

### 21.2 单次调用与长活

```text
Agent报能力号＋命名参数
       ↓ 薄壳依契约映射，不擅自改值
统一网关解析协议 → 拒绝非法编码或过大请求
       ↓
适配器取执行引用 → 内核判目标、形状和调用预算
       ↓
执行域准入 → 队列已满则明确拒绝
       ↓
短活：返回结果 → 校输出 → 归还引用 → 留痕 → Agent
长活：立即返回任务句柄 → Agent按契约取结果或取消
       ↓
超时／断线：判断执行阶段
       ├─ 明确未执行 → 按保障决定重试
       └─ 可能已执行 → 结果未知，不擅自重放副作用
```

### 21.3 单个扩展接入

```text
选择支持库／模块／技能
       ↓
分配身份与号段 → 写自身声明 → 写本体及说明
       ↓
同源本地自检 → 生成或打包不可变制品
       ↓
隔离的待验位置：平台准入＋真制品考题
       ├─ 失败 → 留报告，当前发布目录不动
       └─ 通过 → 放入声明指定的当前扩展目录
                          ↓
既有扫描与生命周期装载 → 判定依赖和兼容
       ├─ 拒绝 → 目标不可用，其他扩展照跑
       └─ 就绪 → 现有查询路径确认身份、版本、能力
                          ↓
Agent发现并调用 → 无需修改底座
```

### 21.4 发布、升级与回退

```text
构建新制品 → 指纹与兼容验证 → 保存旧制品
       ↓
新执行域候选装载与就绪验证
       ├─ 失败 → 不切换，旧域继续服务
       └─ 通过 → 新调用切向新域
                          ↓
旧域停止接新调用 → 在途排空／任务按声明处置
                          ↓
撤通知与注册引用 → 确认进程退出／安全释放 → 留回执

新域异常 → 判断是否允许回退
       ├─ 无状态或兼容恢复 → 新调用切回旧版本
       └─ 有不可逆副作用／不兼容状态 → 隔离、查询或补偿
          不以“换回文件”冒充业务已恢复
```

### 21.5 执行域崩溃

```text
IPC断开或检测到执行进程退出
       ↓
停止新调用 → 标记在途调用的执行结果确定性
       ↓
结构化失败＋调用链留痕 → 回收句柄、管道及进程资源
       ↓
是否耗尽重启预算？
       ├─ 是 → 熔断，明确不可用，等待部署侧处置
       └─ 否 → 退避 → 重建执行域 → 重放允许的初始化
                                       ↓
                旧任务不自动恢复，旧句柄明确失效
```

## 二十二、三类扩展的接入标准

### 22.1 共用标准

| 要求 | 支持库 | 模块库 | 技能封装库 |
|---|---|---|---|
| 自身包声明与能力声明 | 必须 | 必须 | 必须 |
| 号段 | 沿用1xxx至6xxx | 沿用7xxx | 沿用8xxx |
| 本体 | 原生原子能力 | 程序文本与真实执行体 | `说明.md`；不含可执行实现 |
| 对外行为 | 执行原子操作 | 组合调用已有能力 | 返回技能说明文本 |
| 自身错误码表及指纹 | 沿用必备件要求 | 沿用必备件要求 | 沿用必备件要求 |
| 类型声明 | 沿用支持库必备件要求 | 引用有效契约类型 | 返回文本，引用所需能力 |
| 用法说明 | `说明/使用说明.md` | `说明/使用说明.md` | 本体`说明.md` |
| 制品 | 后缀从权威后缀表读取 | 后缀从权威后缀表读取 | 后缀从权威后缀表读取 |
| 依赖与平台适配 | 显式声明与验证 | 固定所需能力及兼容范围 | 明确所需能力与操作前提 |

不在这里重新写一张独立后缀表。三类容器必须使用同一codec按种类解析；不能让每个扩展自行写解包器。

### 22.2 两种目录角色

```text
创作仓：源声明＋本体＋说明＋测试＋生成物
       ↓ 同源自检与构建
待验位置：不可变候选制品＋绑定身份的验证报告
       ↓ 通过准入
当前发布目录：每个直接子目录恰好一个该种类制品
       ↓ 已有根声明扫描
运行数据根：解包缓存、日志、临时件、必要运行状态

旧制品保留区：不混入当前候选扫描目录
```

上图是目录职责，不是本次创建新目录或改根声明。实际路径通过既有装配与根声明配置；不把新版本的两个制品同时放进“恰好一个制品”的候选目录。

### 22.3 依赖规则

- 必须区分“身份与兼容范围”以及“本次部署实际选择的版本与指纹”。后者是派生部署锁定结果，不是第二份源声明。
- 依赖图必须可排序，循环和缺失不能靠反复试运行掩盖。
- 未声明为可选的依赖缺失时拒绝就绪；可选依赖的降级必须能描述与验证。
- 更新支持库后，依赖模块先做兼容考题；不能默默改用最新版。
- 卸载被依赖扩展时，明确拒绝、排空或同时处置依赖者；不能留悬空函数指针。
- 技能依赖不在时，返回可判的不可用状态或明确的缺能力说明；不得捏造能力号。
- 每个号只有一个有效归属；旧号不能因重发包而换含义。

### 22.4 Agent判断接入成功

```text
本地自检通过
    ≠ 制品已完成构建
    ≠ 平台准入通过
    ≠ 扩展已就绪
    ≠ 这次业务调用成功

接入回执必须能定位：
目标身份 → 实际版本与指纹 → 依赖状态 → 提供能力 → 就绪或拒绝原因
```

沿用既有查询和生命周期路径，不新增未经批准的导入端点。新增可判字段或判定能力应走兼容旁路登记，不直接改写冻结响应字段。

## 二十三、支持库接入：原子能力先行

### 23.1 创作包的结构示意

```text
原子支持库/<库名>/
  包声明.json
  能力声明/<编号>.json
  类型声明/<标签>.json
  错误码表/<码>.json
  Cargo.toml ＋ src/               原生实现与生成的声明面
  说明/使用说明.md
  指纹.json
  测试样本与接入证据               具体位置服从统一模板
```

树表示创作包，不允许手写生成物。新名字、号段和错误按既有登记流程处理。

### 23.2 从开发到使用

```text
一项原子操作 → 定参数、返回、错误、副作用和保障
       ↓
写声明 → 生成静态面 → 实现操作 → 本地自检
       ↓
构建原生执行体 → 统一容器打包 → 平台准入
       ↓
放入当前发布目录 → 在隔离执行域装载与初始化
       ↓
按号调用 → 输出校验 → 统一结果与留痕
```

第三方、文件和网络边界留在支持库；业务流程组合进入模块。底座不得依赖具体库的名字或SDK。第三方依赖许可与环境要求须按扩展规范审议，不自动获得进入底座依赖的资格。

第一批真实支持库建议选择无副作用计算与可控文件操作两类，先证明类型与副作用边界，再碰复杂外部服务。已有编译器支持库作为机制考题使用，不证明其他支持库天然合格。

## 二十四、模块接入：先证明“代码真正执行”

### 24.1 最大的未闭环事项

现有`模块制品.rs::取模块接口说明`只解析接口；编译器`执行入口.rs::编译执行`接收能力码字节并装包。**接口段能读、语义分析通过、码段有指纹，都不能证明程序文本已经生成对应执行行为。**

既有裁决不引入第三方WASM运行时，保留子进程加IPC路线。需要补的是该路线使用的执行体从哪里来，而不是重新把进程管理放进内核。

### 24.2 推荐待审议方案

推荐由编译器扩展与构建侧将同一程序文本生成本机执行体，宿主只装配和运行它；模块调用支持库时走宿主已有能力调用语义。保留已承诺的WASM打包形态，但不得私下改变原码段含义。

执行描述、平台身份、源码与执行体关联证据如何进入制品，必须先查冻结登记，采用已允许的旁路；没有可用空间时审议格式演进。当前三段codec不允许任意塞第四段，不能用一个未登记的旁车文件偷偷成为执行来源。

这是推荐施工方向，不表示代码生成、执行描述或新容器版本已经完成。若不批准该方案，必须给出满足既定依赖约束的另一条真实执行体路线；只有“有子进程”不能放行模块接入。

### 24.3 完整执行流程

```text
模块程序文本＋自身声明＋锁定依赖
       ↓
词法 → 语法 → 语义与依赖类型检查
       ↓
生成真实执行体 → 绑定源码、平台、声明和指纹证据
       ↓
按批准的统一制品形态打包 → 真制品准入
       ↓
模块工作进程执行组合逻辑
       ↓ 请求调用支持库能力，不直接拿其他库的私有指针
宿主沿既有调用路径判定、转发与关联追踪
       ↓
支持库执行域 → 返回结果 → 模块下一节点或结构化失败
       ↓
模块最终结果 → Agent
```

模块需明确失败节点、已发生副作用、取消传播和补偿范围。补偿不是通用内核自动回滚。节点状态由模块扩展持有，不新增中央业务任务表。

验收必须修改一份模块源码并重新构建，确认真实结果发生相应变化；同时用错误依赖、节点失败、超时及取消证明调用链，不只比接口JSON。

## 二十五、技能池接入：只取文，不自动执行

“技能池”是用户侧集合概念，在本项目落到已声明的技能封装库；不另建第二个技能注册中心或下载服务。

### 25.1 技能结构示意

```text
技能封装库/<技能名>/
  包声明.json
  能力声明/<编号>.json             返回类型为文本
  错误码表/<码>.json
  说明.md                         技能本体，不是可执行实现
  指纹.json
  依赖能力与兼容前提               进入已有声明，不另立号表
```

技能本体至少交代目标、前提、所需能力、步骤、成功判据、失败处置、危险动作及资源引用。示例只是说明，技能不得携带真实密钥或把示例自动提升为执行权限。

### 25.2 技能发布与使用

```text
编写说明.md＋依赖声明 → 同源自检
       ↓
统一codec打包接口段、技能本体段和指纹段
       ↓
放入声明指定目录 → 校验并注册取文能力
       ↓
Agent搜索技能 → 调8xxx → 取回说明文本
       ↓
Agent核对依赖与授权 → 逐步调支持库或模块
       ↓
每次动作仍走同一网关，不因技能说明获得特权
```

按已有裁决，不新增URL自动下载口。技能随扩展仓整目录分发；翻译文本可以改说明，但不能随意改编号或能力语义。翻译后仍须验证依赖及示例。

验收：一个真实技能制品可按号取回完整文本，中文编码不损坏，未执行任何示例代码；依赖缺失可判，文本不扩权。未经这条考题，不能把技能目录存在视为技能接入完成。

## 二十六、核心先行的放行门槛

### 26.1 四个状态，不再只说“核心绿了”

| 状态 | 含义 | 可以做什么 | 不可以声称 |
|---|---|---|---|
| 静态合规 | 当前静态门禁通过 | 继续核心施工 | 故障隔离或全部扩展已成熟 |
| 接缝可用 | 三类极小制品能够执行或取文 | 做隔离、升级和兼容考题 | 已适合大规模业务接入 |
| 候选稳固 | 故障、生命周期、发布和回退证据满足目标 | 审议冻结，少量真实试点 | 以后不再需要安全与缺陷维护 |
| 可规模接入 | 多类真实试点按规范成立 | 分批迁移老能力和建设技能集合 | 任意扩展未经准入也可靠 |

### 26.2 冻结前不可跳过的十二条考题

1. **声明生成**：支持库、模块、技能的自身声明均有同源生成或打包流程，无重复手写语义。
2. **类型表达**：标量、列表、记录、文本默认值和边界值不失真。
3. **调用校验**：错输入、错输出、未知号和非法错误槽按同一语义处理。
4. **支持库接缝**：真制品在受控执行域完成装载、调用与释放。
5. **模块执行体**：程序文本变化对应真实执行行为变化，并通过支持库完成组合调用。
6. **技能取文**：段19在同一codec中被正确解析，按号返回文本且不自动执行。
7. **隔离与预算**：崩溃、卡死、畸形帧、队列满和大量输出不拖垮宿主。
8. **生命周期**：在途卸载、延迟释放、取消、重启和旧句柄均有确定结果。
9. **版本与依赖**：启动、热装载、升级及锁定依赖一致，不产生半可用的目标扩展。
10. **缓存与来源边界**：内容校验、受控写入、路径范围和平台身份执行前成立。
11. **结果与权限**：指定目标是否就绪、业务是否成功、结果是否未知均可判；技能不扩大权限。
12. **发布与回退**：发布配置、旧制品兼容、确定性夹具和资源恢复有绑定版本的证据。

这些是候选验收建议，批准后应落到已有判据、案例或发布检查，而不是把全部功能另写进闸0。一个考题不通过，明确停在对应状态；不能以“暂时不用这类扩展”冒充面向三类扩展的核心已经稳固。

### 26.3 核心施工顺序的进一步收紧

```text
先裁接口与执行体来源
       ↓
契约生成、三类codec、类型与号段
       ↓
隔离执行域、IPC与通用校验
       ↓
三类最小接缝考题
       ↓
在途引用、依赖、升级和回退
       ↓
故障样本、权限、资源恢复和发布证据
       ↓
核心候选验收 → 少量真实试点 → 批量迁移
```

业务支持库和模块仍放到后面。施工期仅保留证明机制必要的极小样本，不把样本建设扩大成业务开发。

## 二十七、小事也必须交代清楚的接入回执

每个扩展首次接入或升级时，回执至少可以回答以下问题；字段沿现有报告形态扩展，新增冻结字段走正式登记。

| 类别 | 必须可判的问题 |
|---|---|
| 身份 | 是哪个扩展、哪一类、哪个实现版本、由哪个制品指纹提供 |
| 兼容 | 需要哪版宿主、内核、声明格式、ABI、系统和CPU架构 |
| 能力 | 提供哪些号、哪些类型、哪些错误；有无冲突或作废号 |
| 依赖 | 要求谁、实际选谁、缺谁、为何允许降级或为何拒绝 |
| 构建 | 本体来源、生成器与工具链、生成物是否一致、执行体来自哪里 |
| 副作用 | 可能读写什么、危险动作由谁授权、密钥引用在哪绑定 |
| 运行 | 进程内还是隔离、是否串行、超时与取消保障、可否恢复 |
| 就绪 | 真正装上多少、剔除谁、目标版本是否就绪，而不是只有顶层成功 |
| 观测 | 调用链标识、失败位置、日志脱敏、截断和丢弃计数 |
| 资源 | 返回值归还、任务结果期限、缓存清理、进程及句柄回收 |
| 升级 | 旧版在哪里、在途如何排空、依赖者如何处理、何时切换 |
| 验证 | 本地自检、平台准入、发布考题分别是否执行；哪些缺材料或不覆盖 |

这些回执不能要求Agent填写全部底层细节。声明、生成器和宿主已经知道的内容自动带出；只有作者必须决定的语义才交给作者。

## 二十九、增补参考与最后建议

- WebAssembly核心规范将WASM描述为虚拟指令集，并将调用和环境交互留给嵌入环境；这支持“子进程与IPC并不自动提供WASM执行机制”的区分。来源：`https://webassembly.github.io/spec/core/intro/introduction.html`。不据此要求更换项目已定执行路线。
- Rust标准库的`Child`说明不会因丢弃句柄自动停止或等待子进程，长期运行程序须负责确认退出和资源回收。来源：`https://doc.rust-lang.org/std/process/struct.Child.html`。施工时按项目锁定工具链核验所用API。
- MCP工具规范要求对来自非可信来源的工具注解保持不信任；本文同样不把技能文本和描述当作实际授权。来源：`https://modelcontextprotocol.io/specification/2025-11-25/server/tools`。参考版本不代表要求迁移协议。

**最后建议：坚持核心先行，但将三类扩展的最小契约考题纳入核心验收。先把“支持库能安全执行、模块有真实执行体、技能能可靠取文”证明完整，再冻结公共机制。之后真实接入只走同一份规范，不在底座增加任何具体库、模块或技能的特例。**

本次增补仍是临时待审议文档，不修改既有裁决、不新增能力号、不实施任何进程或平台配置变化。

## 三十、给非技术决策者的结论：核心要稳在什么地方

**我的推荐：不继续扩大核心，也不再次重写；把现有核心做成“可证明的稳定接缝”，再接业务。**

可以把平台理解为一个通用插座：支持库是工具，模块是组合工具的程序，技能是使用说明。插座不应知道每个工具的内部做法，但必须管住接线、供给边界、故障和插拔。

| 你关心的问题 | 本方案给出的答案 |
|---|---|
| 现在是不是架构选错了 | 没有必要因此重写；保留已经形成的声明、编号、边界和分层机制 |
| 现在是否足够成熟 | 当前证据还不够；有些接缝没有真实运行闭环，静态全绿不能替代它 |
| 怎样才算核心稳固 | 新工具接进来不改核心；坏工具不带走宿主；升级不串版本；失败后能正确决定下一步 |
| 后面接库会不会又很痛苦 | 先通过三类极小接入考题，再把同一标准用于真实扩展；不靠给每个库开特例解决问题 |
| 是否需要把未来功能全部做完 | 不需要；现在补公共机制，复杂业务和运营功能明确后置 |
| 完善方案能否保证永远没问题 | 不能；稳固来自实现、测试、可复现证据和后续变更纪律，不来自文档篇幅 |

最重要的区别是：**“实现还可以修”与“接入方需要反复跟着改”不是一回事。** 目标是把变动关在实现和扩展内部，公开语义确需变化时显式演进，不偷偷改变旧能力的含义。

以下章节是前文的施工化细化，不另起一套架构。建议性质不变；批准前不把它写成生效规则或未完成台账中的已派工任务。

## 三十一、推荐取舍：由方案替你收口，而不是把选项都推给你

| 议题 | 推荐的第一版选择 | 明确不做什么 | 性质与边界 |
|---|---|---|---|
| 产品范围 | 单机、Agent优先的能力平台，首先验收当前本机部署 | 不提前做公网多租户、分布式调度或集群控制面 | 沿用本轮范围；支持平台矩阵仍须登记 |
| 内核职责 | 只保留通用机制与公开接缝 | 不吸收业务流程、业务任务中心或每个库的特殊分支 | 遵守既有定位 |
| 使用入口 | 搜索、取契约、调用转入同一逻辑网关 | 不让技能、模块或薄壳拥有私有调用通道 | 沿用唯一入口；无需新增公开端点 |
| 执行形态 | 对需要故障隔离的扩展使用适配器工作进程 | 不把线程隔离当进程隔离，不遇错自动退回进程内 | 默认模式改变须审议；保留合法装配形态 |
| 调度并发 | 初版一个执行域串行；显式证明可并发后再放开 | 不先上复杂调度器，不靠全局锁串行整个系统 | 推荐初版策略，不改底层调用语义 |
| 版本选择 | 候选装载时确定版本及依赖；一次调用链锁定其依赖快照 | 不在每个节点临时选择“最新版本” | 声明格式与旁路字段须核对冻结登记 |
| 原生库装载 | 宿主先读静态制品信息；扩展代码仅在批准的执行域初始化 | 不为获取声明而先在宿主执行未知原生库 | 细化B03，属于核心冻结考题 |
| 模块执行 | 先用极小模块证明程序文本到真实执行体的闭环 | 不把WASM容器、接口解析或IPC当成已完成执行器 | 沿用第二十四节推荐；格式演进须审议 |
| 技能定位 | 取回说明，由Agent按能力契约和授权执行 | 不自动跑技能，不从技能文字推导新增权限 | 遵守既有技能裁决 |
| 重试与恢复 | 默认不重放结果未知的副作用；业务幂等由扩展实现 | 不承诺所有操作恰好一次，不静默复活旧句柄 | 细化第九节，不新增中央业务状态库 |
| 依赖与分发 | 复用现有扩展目录、声明、codec和准入流程 | 不先造包管理平台、插件市场或远程下载服务 | 不改变已有整目录分发规则 |
| 成熟判断 | 通过三类接缝、故障、兼容、回退及真实试点 | 不按文件数量、测试总数或观察天数直接宣布成熟 | 按证据放行，不按口号放行 |

**需要优先审议的技术项**仍集中于：类型与默认值的兼容表达；六项IPC前置问题；模块执行体来源与制品承载；装载和版本切换的一致性；平台支持范围与安全保障边界。其余工作围绕这些结论施工，不反复讨论已经定案的语言和内核定位。

## 三十二、把“接入成功”做实：发布、依赖与调用的一致性

### 32.1 四类身份不能混用

| 身份 | 回答什么 | 使用规则 |
|---|---|---|
| 扩展标识 | 这是哪个扩展 | 跨版本保持身份，不拿目录名代替权威标识 |
| 实现版本与制品指纹 | 实际执行哪份内容 | 同名同版本但不同内容不得静默覆盖；修正版使用明确的新制品身份 |
| 契约身份 | 调用形状和语义依据是什么 | 从声明派生；不能只凭实现版本判断ABI和契约是否兼容 |
| 执行域代次 | 当前进程或实例是哪一次运行 | 重启后改变代次，旧任务和句柄不能碰巧指向新实例 |

这些是逻辑概念，不要求各造一张表或新的公开编号空间。优先复用已有字段；确需增加表达时，按冻结登记与号段规则审议。版本号的比较、预发布版本处理和兼容范围先规定一种口径，再让构建与运行复用，禁止按字符串大小猜版本。

### 32.2 候选区与就绪区之间必须有发布边界

推荐在适配器持有的既有装载状态中形成以下逻辑状态，不强制新增中心服务：

```text
未装载
   ↓ 静态格式、指纹、平台与号段校验
候选：内部可检查，使用角色尚不可调用
   ↓ 确定依赖快照 → 工作进程初始化 → 就绪考题
就绪：声明查询与调用路看到同一代次、同一能力集合
   ↓ 停止接收新调用
排空：旧调用只引用旧制品和旧依赖
   ↓ 回收完成
已退出：旧句柄失效，允许清理无引用缓存

任一步失败 → 留候选失败回执，不发布半成品
```

- 同一扩展的能力、类型、错误码和通知注册作为一个发布单位；不能只公布其中一半。
- 扫描批次可有部分扩展成功，但每个扩展须有明确状态；不存在“所有扩展必须一起成功”的新全局事务。
- 依赖组确需共同切换时，先明确该组的发布单位与回退限制，不能假装跨扩展已经天然原子。
- 更新路由的临界区只切状态和引用，不运行初始化、业务调用或无界等待。
- 发现结果只能展示与当前查询语义相符的状态；“制品存在”“声明合法”“已就绪”必须可区分。

兼容既有唯一入口：查询与生命周期回执由同一路径派生，不另开就绪注册服务。增加机器可判字段时先核对冻结形状。

### 32.3 依赖必须在装载时解析，在调用链内保持一致

```text
候选声明的依赖要求
       ↓
按版本、能力、类型和运行保障检查已有候选与就绪扩展
       ├─ 缺失／冲突／非法循环 → 拒绝目标或按声明允许降级
       └─ 满足 → 记录确定的依赖快照
                     ↓
模块根调用取得执行租约及快照
                     ↓
后续支持库调用沿同一快照寻址，不临时换到新版
                     ↓
调用结束／任务结束 → 释放引用 → 旧域才可最终退出
```

初版拒绝没有明确语义的强依赖循环；不把反复重试装载当成循环依赖解决方案。可选依赖只有在声明说明降级行为时才允许缺失。单次调用链锁定版本不等于永久保留所有旧进程；长活需要另有期限、升级处置和资源预算。

启动与热装载共用同一依赖判定机制，展示层不得自行决定可装载性。卸载被依赖扩展时应说明阻塞者与处置选项，不偷偷将依赖者转到别的版本。

### 32.4 发现与调用之间也有版本竞争

Agent先取契约、随后调用时，扩展可能已经升级。推荐由派生契约视图带出身份或指纹，并通过现有调用上下文在可表达范围内核对。

- 能力号语义不变且调用形状兼容，继续按统一契约校验执行。
- 已取契约不再适用，执行前明确拒绝，并提示重新读取；不自动重排参数或补出新含义。
- 不要求使用角色建立连接、握手或管理执行域；一致性身份属于一次请求的信息。
- 能力不存在与暂时未就绪分别可判，避免Agent把部署失败误读成“没有这项能力”。

这里是建议语义，不是宣布新增协议字段已经实现。缺少可用承载位置时先裁兼容方案，不由薄壳私造字段绕过契约。

## 三十三、安全、资源和故障：不能把“子进程”当作所有保障

### 33.1 明确三个不同保障等级

| 等级 | 能承诺什么 | 不能承诺什么 | 本轮策略 |
|---|---|---|---|
| 可信进程内 | 合法调用形状与可信实现下的统一机制 | 扩展崩溃隔离、恶意代码隔离 | 明确受控适用范围，不作为故障隔离验收替代品 |
| 工作进程隔离 | 经考题证明的崩溃、卡死处置和执行域分离 | 仅凭进程分离就阻止同权限代码读文件、联网或启动其他程序 | 第一版优先做实，并明确权限继承与资源边界 |
| 操作系统沙箱 | 在已实现、已测试的平台上限制指定资源访问 | 任意平台上天然可用、完全消除恶意代码风险 | 尚未证明前，不接纳需要此保障的非可信扩展 |

上述等级是方案说明，不新造边界载体，也不改变既有“进程内／进程池／沙箱”形态裁决。声明写“不能联网”不等于实际禁止了联网；能力只从网关调用，也不代表原生代码无法绕过网关直接访问操作系统。

当前本机可信扩展可先实现故障隔离，但必须把“无法防御同账号恶意代码”写入准入和部署回执。接纳非可信扩展之前，再实施并验证对应平台的沙箱与最小权限；不能先接入再补边界。

### 33.2 第一版也不能省的安全控制

| 控制点 | 推荐动作 | 责任落点 |
|---|---|---|
| 声明检查 | 先从静态制品读声明并校验，初始化只在批准执行域发生 | L02、L06、L08 |
| 子进程启动 | 使用受控执行体路径、参数表、工作目录；不拼接外来文本成shell命令 | L06、L10 |
| 环境与密钥 | 按所需项传环境；秘密只绑定给需要它的扩展，结果与日志脱敏 | L06、L11、L15 |
| 本机入口 | 明确IPC目录与文件权限；HTTP暴露范围和调用来源校验进入部署审议 | L06、L14；未实现认证前不开放远程访问 |
| 能力授权 | 声明表达请求范围，部署侧授予实际权限；危险副作用单独受控 | L01、L06、L11；不靠技能文字授权 |
| 制品来源 | 指纹用于内容一致性；可信来源另由受控目录和发布流程保证 | L02、L09、L10；未来引入签名另行审议 |
| 路径访问 | 校验允许根、符号链接与实际打开对象；不只用字符串前缀判断 | L06、L08、L11 |
| 日志与输出 | 限长、脱敏、标记截断；不可将扩展输出混入IPC控制帧 | L06、L15 |

Rust的`Command`默认继承父进程环境与工作目录，因此“创建了子进程”不是已经最小化环境的证据；建议显式清理后按需注入。资料R01核验的是标准库默认行为，项目是否已收紧须由实现和验收另行证明。

本节是施工建议，不声称当前已经复现密钥泄漏、鉴权绕过或恶意扩展攻击。第一版不承诺公网安全；这不免除本机入口与秘密管理的检查责任。

### 33.3 资源预算要覆盖整个调用链

不能只给单帧设上限：每个值都“合法”，累积起来仍可能超预算。建议在既有配额和调用上下文范围内统一回答以下问题。

| 资源 | 至少明确的限制 | 耗尽时的行为 |
|---|---|---|
| 输入与解码 | 单帧、整次调用、嵌套深度、元素数量、累计分配 | 执行前拒绝，避免先分配再校验 |
| 执行 | 执行域数量、队列数、单域并发、等待与执行预算 | 有界拒绝或结束等待，区别未执行与结果未知 |
| 嵌套调用 | 最大深度、扇出、调用链累计预算 | 不递归等自身；剩余预算不因转发重置 |
| 任务与结果 | 活跃任务数、结果字节、保留期限、查询频率 | 返回明确配额或过期状态，不无界存放 |
| 进程与输出 | 输出累计量、退出等待、子孙进程处置范围 | 不等管道塞死后再读取；确认回收结果 |
| 日志与缓存 | 大小、滚动、保留期限、清理时机、磁盘不足 | 保留可判错误；不删仍被执行租约引用的内容 |

具体数值不能凭文档拍脑袋。W01确定目标硬件和场景，W04、W07测量后登记默认值与硬上限；未配置或非法配置采用明确的安全拒绝或已批准默认值，不出现“0到底是禁用还是无限”的歧义。

截止时间使用同机可比较的单调时间预算；转发只消费剩余量。跨进程超时、取消确认和进程回收是不同状态，**取消请求发出不等于任务已停止，停止也不等于副作用已撤销。**

### 35.3 每次变更的大小与回执

每批只解决一个可验收的行为切片，例如“错误标签在执行前拒绝”或“候选初始化失败不发布”。一个工作包可由多批组成；禁止一批同时改契约、所有扩展、薄壳和发布方式且没有中间回退点。

### 36.1 静态门禁、行为考题与发布考题不混账

```text
改动代码或声明
     ↓
闸0：现有秒级静态检查
     ├─ 失败 → 停在当前变更，不放宽硬顶制造通过
     └─ 通过 → 按现有实测与发布流程执行对应行为考题
                       ↓

                       ↓

```

不为保持静态五秒把故障注入全部塞进闸0，也不拿静态全绿代替行为验收。运行测试的范围和入口遵守README与既有验证裁决；本方案中的验收卡不是另立“选模块验证”公开档。

### 36.2 稳定性观察需要终止条件

建议在W01登记负载模型、目标并发、故障预算和资源容差，在W07执行至少覆盖正常、过载、反复启停与升级交错的考题。报告同时写循环次数、持续时间和资源趋势，不能只写“运行一段时间没报错”。

不以固定几天或固定测试数量证明成熟。观察期内出现影响核心保障的缺陷，修复后重跑关联考题和受影响兼容组合；缺材料就标缺材料。达成事先约定的条件即可结束这轮候选验收，不让“再多观察一下”变成永不收敛的工作。

## 三十七、长期维护：让后续变化有唯一落点

### 37.1 新需求先过四个问题

```text
新需求
  ↓ 是否只需说明“怎么用”？
  是 → 技能；不加执行权
  否 ↓ 是否只是组合已有能力？
     是 → 模块；依赖与失败策略显式声明
     否 ↓ 是否增加一个原子或外部系统能力？
        是 → 支持库；不在底座加库名分支
        否 ↓ 是否至少两类扩展都需要同一跨边界机制，且现有接缝无法表达？
           是 → 提交核心机制演进审议、兼容考题与回退边界
           否 → 继续澄清需求，不为了方便把业务塞进内核
```

“两类扩展都需要”是判断通用性的建议证据，不推翻既有核心准入裁决。安全修复和明确的现有机制缺陷不需要为了凑两个业务案例而延迟处理。

### 37.2 变更分类与维护成本控制

| 变更 | 默认落点 | 要求 |
|---|---|---|
| 技能步骤、业务策略或模块流程 | 对应扩展 | 依赖与授权不漂移；不变更底座 |
| 原子能力或外部接口适配 | 支持库 | 按号段、契约、准入与副作用标准接入 |
| 内部算法优化 | 既有实现 | 公共语义不变，重跑相关行为与回归证据 |
| 公开类型、ABI、容器或错误语义变化 | 契约及既有接缝 | 先审议，明确兼容或拒绝范围，不静默改旧号含义 |
| 运行配置变化 | 既有装配与部署位置 | 校验配置，记录生效快照与保障差异；配置不是能力事实源 |
| 安全与边界缺陷 | 实际责任层 | 复现、修复、回归；必要时停止相关制品准入，不降级掩盖 |

后续维护应主要是扩展实现和制品发布，但不会变成“核心永远不维护”。平台工具链升级、兼容缺陷和安全修复仍要有责任人或责任Agent，验收不能由实施者的一句“已完成”代替。

### 37.3 规则、方案和任务各归各位

- **当前架构**仍在`开发文档/实际架构.md`，本方案不改写当前事实。
- **生效裁决与规则**仍在信息核心库；本文被批准的内容通过既有命令入库并记账，不手改数据库。
- **实际派工与未完成事项**只在既有`未完成.json`；A至G、W与T编号不是第二个任务台账。
- **接入说明与生成范例**由已有声明和规范派生；不再手写一份平行号段表、类型表或错误表。
- **本文转正**时按文档治理更新账本，批准部分入库，临时草案归档或移除；不得把已批准正文永久留成第二权威设计源。

本轮不执行转正、不新增DB条款、不调整实际架构，避免“补方案”悄悄变成“已经批准新规则”。

| 正式制品、部署配置及发布证据 | 保留一致版本与上一可用制品 | 只备份源码不一定能恢复实际部署状态 |
| 信息核心源表与任务源件 | 通过受控一致快照恢复，再核对派生件 | 不复制正在写入的单个SQLite主文件冒充完整快照 |
| 扩展业务状态与外部副作用 | 按扩展声明备份、查询、恢复或补偿 | 恢复平台文件不会撤销外部已发生的操作 |

第一版先做一次受控恢复演练，记录哪些能恢复、哪些只能重建、哪些明确不支持。是否增加自动备份产品不在核心冻结范围。
