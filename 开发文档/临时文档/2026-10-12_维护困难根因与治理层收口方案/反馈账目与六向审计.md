## 十四 反馈账目里值得看的东西（本轮新增）

数据源：`<运行数据根>/数据库/开工账本.db`（只读）。

### 14.1 它是什么

```text
反馈来源 947 · 反馈条目 4735 · 反馈判词 4663 · 反馈证据 8106 · 反馈批次 1030
反馈关闭 6 · 工具流水 3922 · 开工 841 · 认领 9295 · 改动 23759 · 认领重叠 1555
```

设计上它是一套**完整的「发现 → 判词 → 证据 → 关闭」闭环**，且判词由主策划给、不让提交方自判。
**这套设计是对的**，且比多数项目的手工台账先进。本轮看的是它的**运行时实况**。

### 14.2 实况：只进不出（这是最重要的一条）

```text
判词分布    债务 2351 · 非问题 1978 · 待核 334
判词状态    现行 4657 · 已撤 6
反馈关闭    全表只有 6 条
```

⇒ **登记口活跃、销账口几乎不动**。
台账自身也记了这条（现量原文：未关闭债务 2338 条，关闭记录仅 4 条，销账口不在任何常规流程）。

**这造成一个连锁后果**（实测）：

```text
「现行」判词里，指向的台账目标**已经不存在**的，有 123 条：
  目标 312(54) · 330(21) · 320(12) · 327(11) · 317(8) · 334(6)
  322(5) · 329(2) · 316(2) · 326(1) · 331(1)
这 11 个目标号已从 未完成.json 里删除（条目修好即删），
而判词仍标「现行」⇒ 指向了一个已消失的目标
```

⇒ 于是出现**两份对不上的账**：台账说「已修完、已删」；反馈库说「现行债务」。
新会话若查反馈库，会去修**已经不存在的东西**。

### 14.3 值得直接借用的做法（正面）

```text
① 判词三分：债务 / 非问题 / 待核
   —— 明确把「不是缺陷」也登记下来，防后人误修。本项目已在用，值得保住。

② 判词带「关联种类 + 关联目标」
   —— 债务必须关联唯一台账条目或正式开工，不许悬空。设计正确。

③ 来源级幂等（批次表用幂等键）
   —— 同键同文=重放、同键异文=拒，防止重复登记。

④ 判词带「理由」正文
   —— 例如「已补 stat 级刷新兜底，原文…」；这是可追溯的裁决留痕。

⑤ 已撤机制（关联状态=已撤）
   —— 判词写错时可撤回而非删除，保留反向对照。
```

### 14.4 值得警惕的做法（负面）

```text
① 关闭口不纳入常规流程 ⇒ 债务只进不出（见 14.2）

② 关联目标无「台账条目消失」的联动
   —— 台账条目删了，判词不会自动失效，仍标「现行」

③ 判词量与台账量级不匹配
   —— 判词 4663 条 vs 台账现行约一百余条；一条台账平均背着约 30 条判词，
      说明「判词」实际上是「发现的原始记录」，不是「待办」
      ⇒ 名称与职责不符：叫「判词」，实际承担的是「发现归档」

④ 已撤 6 条里有一条（关联目标已不在台账）暴露了口径漂移：
      「关联目标 323」的判词写着「修改.py 仍不能建目录、shell.py 仍原样交给 /bin/sh」
      —— 而 shell 那条本轮实测**已修**
      ⇒ 撤得对，但说明判词也会滞后于代码
```

### 14.5 对方案的影响

```text
§5.4「当前态只允许一种表达」要加一条：
  反馈库的「现行」必须与台账现行条目**联动校验**；
  台账条目消失 ⇒ 该判词要么转「已关闭」、要么标「目标已消失」，
  不许继续标「现行」
```

## 十六 六向专项审计（本轮新增）

本节按华哥本轮给的六个方向逐项实测。**全部只读**（读码 · 读依赖图 · 读 Git · 读库）。

### 16.1 方向一 · 文件命名

结论：**不用改名，只有一处建议**。

```text
实测：英文开头文件名逐条看过，全是合法形态：
  · 16 个 lib.rs / 1 个 main.rs  —— Cargo 强制，改不了
  · 开发工具/MCP服务/作业执行/命令执行.py    —— 英文名，属「外部协议名」一类
  · 其余是 .json / .sh 配置名

⇒ 结论：不构成「命名混乱」，不建议批量改名。
   ★ 唯一可选：shell.py 若嫌与全中文口径不一致，可改名 ——
     但它是 MCP 工具 v1_shell 的实现件，改名要同步工具面，收益低、风险有，建议不动。
```

### 16.2 方向二 · 代码洁净度

结论：**洁净度是好的，不必清理**。

```text
TODO / FIXME / XXX / HACK 实测：全仓只有 5 处命中，且全是**误报** ——
  3 处是 `\uXXXX` 转义说明（协议文档文字）
  2 处是 `腿/v1-100XXX` 占位形状（示例文本）
⇒ 真 TODO 标记 = 0
```

**但有两条「体量类」洁净问题**（不是乱写，是长得太大）：

```text
① 开发工具/MCP服务/ 一个目录 171 个 .py，其中 53 个是「*样本.py」
   —— 样本与实现同目录，读的人分不出哪个是正式实现
   ★ 归位建议：样本收进 开发工具/MCP服务/样本/（同层子目录，不改名、不改内容）

② 超 400 行源件 12 个（按库条款 §六 的 400 口径），但判据⑲ 现行硬数是 **800**，超 800 = 0 个
   —— 已在台账按「存量基线只许减」口径记账，不是新问题
```

### 16.3 方向三 · 代码咬合度

结论：**底座内部咬合是好的**；只有一处「同源两份」是**有意设计**。

```text
底座内部：各 crate 依赖单向、无反向、无跳层（见 §12.1）—— 咬合健康
```

**实测的「同名实现」全部查清，都不是重复**：

```text
· 编译器支持库 另有 容器/ 目录（装包 · 校验槽 · 反解定义 …）
  —— 查件头：它服务 `.e` 的段类型 1–15/255，是「易语言互操作路」；
     而 契约声明/容器.rs 服务能力包件三段 16/17/18/19。
     契约声明/容器.rs 件头**明写**：「`.e` 互操作路的骨架另算…跨语言/跨层不许硬合」
  ⇒ 这是**有意分层**，不是第二套实现。上一轮怀疑它「重复实现 codec」—— 已查清，**撤回**。

· 编译器支持库/能力包件/装包.rs 有 `装包`
  —— 件头明写：「能力包件容器格式只此一份实现（本件**转调**，不重写）」
     它只把六字段编成接口说明段字节，其余转调契约层
  ⇒ 合规，不是重复。

· 造错误槽 / 造标识 / 转十六进制 / 真假值转线上值 等同名函数
  —— 全在**测试件**里（测试夹具各造各的），不是生产重复。
```

### 16.4 方向四 · GitHub 合并上传

结论：**没有工程化问题，只有「推送延迟」这一条习惯问题**。

```text
远端：origin  git@github.com:kunhua-he/system-engineering-platform-v1.git
状态：本地领先 2 条未推（最新两条合并提交）
      远端最后提交 ce96533e 2026-10-12 08:20
      本地最后提交 3f3f8205 2026-10-12 08:49  ⇒ 延迟约半小时
```

**好的部分**：

```text
· 提交信息质量高：说清「改了什么节点、为什么」，带台账号与承接提交
· 合并口径严格：每批合并都写「隔离集成校验通过」
· 分支模型清晰：只保留 主干 + 短暂命名的 腿/*，合完即删
· 无 .github / 无 CI —— 属有意选择（门禁走本地 pre-commit 钩子 + 闸0）
· 无 PR 流程 —— 单人 + AI 协作，PR 反而增开销，属合理取舍
```

**唯一建议**：主干领先远端时**尽快推**，别攒。
理由：本地一旦出意外（磁盘、误 reset），未推的提交是唯一副本。

### 16.5 方向五 · 是否足够工程化

结论：**远超一般项目；短板不在「工程化程度」，在「工程化的可解释性」**。

```text
强项（实测）
  · 门禁：闸0（声明侧 + 实现侧）+ 判据表现量 + pre-commit 钩子
  · 任务：开工账本 · 工作树隔离 · 路径认领 · 内容指纹 · 四道闸
  · 反馈：发现→判词→证据→关闭 闭环（含幂等、可撤回）
  · 规则：SQLite 单一事实源 + 派生表 + 基线冻结
  · 验证：静态（秒级）+ 行为（案例）+ 发布（验收卡）三级
  · 提交：一条一事、精确路径 add、禁通配

短板（实测）
  · 无 CI（本地门禁依赖跑门禁的那台机器）
  · 反馈关闭口不在常规流程 ⇒ 债务只进不出（§14.2）
  · 「能力是否可用」缺单一机器可读读数口（§三 根因三）
  · 文档口径会漂（工具数 / 判据数写死）
```

⇒ 一句话：**它已经不是「够不够工程化」的问题，而是「工程化产物太多、缺一张统一的状态读数」的问题。**

### 16.6 方向六 · 怎么更快接近老版本、开发支持库与模块库

这是六个方向里**最有价值**的一条。实测现状：

```text
翻译器：开发工具/老项目接入/（7 件 · 约 900 行）
  翻译器主流程 114 · 翻译器实现 190 · 翻译器常量 85
  翻译器生成 287 · 翻译器自测 165 · 老项目模块翻译 43 · 翻译器测试 35
  ★ 注意：上一轮记录的「构建装配/翻译器/」已不在 —— 实际住在 开发工具/老项目接入/

已接入的扩展（扩展根目录）
  原子支持库：编译器支持库 · 数值计算支持库        （2 个）
  组合模块库：数值统计模块                              （1 个）
  技能封装库：取文技能                              （1 个）
```

**实测出的加速瓶颈（按影响排序）**：

```text
① 模块侧「程序文本 → 真执行体」未闭环（最大瓶颈）
   台账自身标：模块执行体的制品承载位置未批准
   ⇒ 就算批量翻译出一万个模块，也跑不起来 ⇒ **这一条不解决，批量迁移没有意义**

② 类型翻译未联合验收
   台账标：列表型参数 · 结果型结构 · 文本默认值 三条未过真实消费者读回
   ⇒ 老项目里最常见的恰恰就是这三类

③ 依赖图与号段分配已有（翻译器常量 / 号段分配表.json）
   ⇒ 这一环已具备，不是瓶颈
```

**建议的加速顺序**（一次做透，不铺开）：

```text
第一步  先打通「一个模块」的真闭环
        程序文本 → 真执行体 → 宿主装载 → 真实调用出结果
        判据：改模块源码，真实行为跟着变（不是只改接口段）

第二步  再打通「三类类型」的翻译闭环
        列表型参数 · 结果型结构 · 文本默认值，各跑一遍真消费者读回

第三步  用前两步的成果跑通「一类老能力」端到端
        翻译 → 生成 → 装载 → 调用 → 结果正确

第四步  才谈批量
        前三步不通，批量只会把不通的东西放大一万倍
```

**为什么这个顺序**：批量翻译的成本是线性的，但**闭环不通时收益是零**。
先把「1 个跑通」做扎实，再放大，比先翻译 1000 个再回头修闭环便宜得多。
