## 二十二 派活与并行：哪些能交子会话（本轮结论）

回答一个问题：**这份方案要落地，哪些活能派出去、能不能并行。**

### 22.1 先看平台自带的并发机制（不用另造）

```text
实测：平台**已经有**成熟的并行开发机制，不要另搞一套。

· 一腿一工作树        开发工具/并行工作树.sh
   实测说明：共享可变工作区会「一条腿的半成品让全员红、任一条腿在写就不能提交」
   ⇒ 一腿一工作树后：共享可变状态归零 · 文件争用归零 · 构建锁争用归零

· 文件租约硬锁        开工即占（整批原子认领）· 同一份文件也能上锁
   撞车有界等待重试即可；谁先拿到谁先改、改完留日志

· 判据池自适应宽度     构建装配/一键验证/一键验证/基础定义/常量_池宽.py
   核数上限 = min(32, 核数)；4 条闸并发时每条只起 8 个，不互抢

⇒ 结论：**并行不是问题，冲突才是。** 派活的关键是「按文件切分」，不是「按主题切分」。
```

```text
② 与他条共享文件（要串行或排批）              126 条

③ 落点跨多目录（最易冲突）                    64 条

```

**文件独占的 16 条**（可立即派，零冲突）：

### 22.3 哪些能派子会话、哪些不能

```text
★ 能派（子会话擅长）
  ① 落点单一、文件独占的条目            —— 上面 16 条 + 同目录内互不重叠的
  ② 只读调研（把某条台账的「现状」核实清楚，不改码）
  ③ 单文件修复（一条命令能验收的）
  ④ 补反向样本（给已有判据补一条反证）

★ 不能派（必须主会话做）
  ① 跨多目录的改动（409 · 423 · 456 这类）—— 要统一设计，子会话各改各的必分叉
  ② 改冻结公开面（契约声明/src/契约声明/*形状.rs）—— 要连登记一起改，一致性要求高
  ③ 改门禁判据本身 —— 改判据等于改「对错的尺子」，要主会话统管
  ④ 三个待裁项（§二十）—— 是「裁决」，不是「活」，派不出去
```

### 22.4 建议的并行方式：按「文件域」分批，不按主题

```text
第 0 批（主会话 · 串行）
  三个待裁项落成决策记录
  —— 不裁，后面全白做

第 1 批（可 3~4 路并行 · 零冲突）
  取「文件独占」条目 + 同目录内互不重叠的，各派一腿
  例：321（代码地图查询）· 365/366（迁移试点）· 403（密钥引用）· 415（进程退出）
  每腿独立工作树 · 独立认领 · 独立验收

第 2 批（可 2~3 路并行 · 需错开）
  热点目录按「同一文件只给一腿」切
  跨语言适配 与 对外接口面 各一路；契约声明 单列一路（它被最多人依赖）

第 3 批（主会话 · 串行）
  跨多目录的条目（409 · 423 · 456 …）—— 统一设计后再改

★ 铁律：同一份文件，同一时刻只给一条腿。
   平台的文件租约能兜住撞车，但「撞了再退」不如「一开始就不撞」。
```

### 22.5 并行时的验收口径（照平台既有口径，不另立）

```text
每腿收尾 = 在本腿工作树里跑全量 v1_gate，退出码 0 才算完
合并     = 由主会话做（子会话只提交本地，不推远端）
冲突     = 撞冻结公开面要停下报告，不许擅自解
```

### 22.6 「做一项划掉一项」怎么落

```text
本件是调研件，不承担派工状态。建议：

① 派工时，用台账号登记开工（平台自有机制，登记即认领）
② 每完成一条，按平台口径**从台账删掉那一行**（做完即删，不留划线原文）
③ 本件 §22.2 的「文件独占 16 条」只作**派活参考**，不作为状态源 ——
   状态永远只在台账里，避免本件变成第二套账
```

**一句话**：**并行能做，但按「文件」切，不按「主题」切**；
能派的活是「落点单一 + 文件独占」那一类，跨目录和改冻结面的必须留在主会话。

### 22.7 ★ 派活前置核实（实测纠正，重要）

按 §22.2 的「文件独占 16 条」准备派活时，**逐条核了性质**，发现一条必须先说清的事：

```text
「文件独占」只说明「不会与别人撞车」，**不说明「能独立修好」**。
```

实测这 16 条的性质分布：

| 条目 | 性质 | 为什么不能直接派修 |
|---|---|---|
| 321 | 要裁决 | 属被暂停的裁决类 |
| 365 · 366 | 要新增能力 | 大工程，非单件修复 |
| 403 · 415 · 431 · 447 · 450 · 454 · 497 · 515 | 要新增能力 | 都是「加一套新机制」，不是修 bug |
| 437 · 463 | 属验收 | 要跑 cargo / 真制品，子会话跑不了 |
| 443 · 465 | 与待裁项强耦合 | 待裁项未定前做不了 |
| 517 | 排查不确定的红 | 可能假红，要先复现分析 |

⇒ **结论：这 16 条里没有一条是「根因已定位 + 单件 + 能独立修好」的干净活。**

**由此得出一条派活纪律**：

```text
派活前必须先分两问，不能只问「会不会撞车」：
  第一问：会不会与别人撞车？      —— 按文件独占性判（§22.2）
  第二问：这条活本身能不能独立闭环？—— 按「是否要裁决 / 是否要新增能力 /
                                       是否要跑 cargo / 是否属验收」判（本节）

两问都过，才是可派子会话的活。
只过第一问的，派出去也做不完 —— 会卡在裁决或工具链上。
```

**顺带核到的一条**：台账里那条「文档面 305 条」的代表现象**大部分已过时** ——
实测「index.html 写编译还没实现」「AGENTS.md 数字过期」「两套台账并存」都已不存在或已改。
⇒ 印证 §十五 的方法论教训：**本仓结论有保质期，跨轮引用必须重取读数。**
### 22.8 实际怎么派（后台会话 · 不是子代理）

★ 华哥纠正过一次：**要的是「后台会话」，不是「子代理」**。
两者不是一回事，做法与可见性都不同：

```text
子代理（delegate_task）        一次性、无交互、回执回主会话；界面里不独立成会话
后台会话（tmux + hermes --in） 独立会话 · 桌面端可见 · 能中途 send-keys 纠偏
```

**项目实际用的是后台会话**（与《派活前置》口径一致：一条信 = 一个独立 worker）。

起法（照 hermes-background-tasks 技能，已验证）：

```sh
export PATH="/opt/homebrew/bin:$HOME/.local/bin:$PATH"
TM=/opt/homebrew/bin/tmux
R=/Users/hekunhua/Documents/Agent/PHP/系统工程平台V1
$TM new-session -d -s <会话名> -x 200 -y 50 -c "$R" "hermes --in \"$R\""
# 等 REPL 就绪（出现 Welcome to Hermes Agent）再发提示词，发早会被吞回车
$TM send-keys -t <会话名> '读 <派活信绝对路径> ，按它的口径做。' Enter
```

三条要点：

```text
① 会话名一律 ASCII（bash 标识符只认 ASCII）
② 必须给 hermes --in <仓根> —— 只给 -c 会把会话 cwd 落成启动器目录，
   桌面端会把它归到「Hermes 源码」项目而不是 V1
③ 提示词要点名**派活信的绝对路径**，让 worker 自行读信 —— 信是接口，别在提示词里复述
```

**派活信落点**：`<运行数据根>/临时件/派活_<名>.md`（照模板写，见《派活前置》§七）。
**回执落点**：`<运行数据根>/临时件/回执_<名>.md`。
**可判定的回传信号**：回执文件落盘（不靠盯屏猜）+ 后台哨兵轮询。

**收尾纪律**：会话做完**不会自行退出**（停在最后一条注入消息上等人回话）；
活已交就 `tmux kill-session` 清掉，别留小尾巴。
