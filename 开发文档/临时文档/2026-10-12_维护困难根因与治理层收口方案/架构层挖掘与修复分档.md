## 十二 架构层继续挖掘（本轮新增）

本节只收**架构级**问题：分层 / 边界 / 接缝 / 单腿 / 稳定判据。
取证方式全部是只读（读码 · 读契约 · 读台账 · 读 Cargo 依赖图）。

### 12.1 分层与依赖：底座本体这一层是干净的

实测各 crate 依赖指向，方向自下而上、无反向、无跳层：

```text
契约声明            （无依赖 · 被全体依赖）
  ↑ 运行内核/各 crate   只依赖 契约声明（+ 同层互依，已裁为不算违规）
  ↑ 跨语言适配/适配器实现   契约 + 装载 + 注册表 + 调度 + 通知 + 留痕 + 运行数据根
  ↑ 跨语言适配/资源网关口   契约 + 留痕 + 调度 + 适配器
  ↑ 对外接口面/调用接口面   适配器
  ↑ 测试验证/案例/跑案例    适配器 + 契约 + 装载 + 编译器
```

⇒ **底座本体（对象层）的分层是健康的。** 这条要保住，不要因为治理层乱就以为底座也乱。

### 12.2 一个仓里住了三套「各自完整」的系统

```text
① 底座本体（对象层）
   契约 · 内核 · 适配 · 接口面 · 扩展装载 · 测试验证
   对外命令：闸0 / 一键验证 / 案例

② 开发治理平台（元层）
   开发工具/MCP服务（171 个 .py）· 开工账本 · 工作树与租约 · 合主干 · 反馈系统 · 清理
   对外命令：MCP 13 工具

③ 人工界面（表现层）
   前端呈现/网页应用（26 个 js/css）· 命令行界面 · 桌面应用壳
   对外命令：网页 / CLI
```

三套各有自身的入口、状态、命令与验证方式，却共用同一个仓、同一套行数与命名判据、同一个台账。

⇒ 这是根因一在**目录结构**上的表现：**不是分层错了，是"层"的定义被撑成了三种东西。**

### 12.3 方案与现状必须分开承载（机制教训）

```text
一份「待审议方案」同时承载「现状判断 + 建议 + 待办清单」时，新会话必然误读。
正确形状：方案只写建议；现状由读数回答；待办由台账回答（见 §5.4）。
```

### 12.4 宿主仍直接 dlopen 未知扩展（B03 · 未达成）

```text
对外接口面/调用接口面/src/执行装配/扫扩展根.rs::取扩展声明
    let 句柄 = unsafe { dlopen(路径串, RTLD_NOW) }
    dlsym(句柄, "GetPlatformInfo")
    件头注释：「dlopen 之后不 dlclose：库一旦载入不再卸载」

⇒ 两条一起看：
   ① 未知扩展的初始化代码跑在宿主进程里（方案 §33.1 定为「可信进程内」，不是隔离）
   ② 逻辑卸载 ≠ 物理释放 —— 动态库句柄活到进程结束
```

台账对应条目（dlopen 相关）仍为**未达成**。
