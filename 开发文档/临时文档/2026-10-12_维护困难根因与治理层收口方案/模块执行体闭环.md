## 十七 模块执行体闭环：卡点定位（本轮深挖）

上一节说「模块闭环未通」是最大瓶颈。本轮把它**逐段拆开实测**，找到了具体卡在哪一步。

### 17.1 结论先说

```text
闭环没有断在「编译器不会生成执行体」—— 那一步已经通了。
它断在「生成的执行体装不进模块制品」这一步，根因是一处**形态冲突**：
    底座模块容器规定：能力码段 17 = WebAssembly（原字节）
    编译器实际产出：本机 Rust 源码（文本）
    ⇒ 两者对不上，所以模块制品的能力码段至今是**空**的
```

### 17.2 实测：链条逐段状态

```text
① 程序文本 → 执行源码（真生成）        ★ 已通
   扩展根目录/原子支持库/编译器支持库/src/执行函数面/本机生成/
     · 生成形状.rs   —— 请求/产物形状（含 执行源码: String）
     · 生成实现.rs::生成本机源码 —— 真产出 Rust 源码文本
     · 表达式生成.rs
     · 样本/常量初版.程序文本  返回 (40 ＋ 2)
     · 样本/常量改版.程序文本  返回 (40 ＋ 3)
     · 验证样本.rs —— 真跑：写 .rs → 调 rustc 编译 → 跑可执行 → 断言返回 42 / 43
   ⇒ 这是**真本机执行**，不是模拟：改源码，真实返回值跟着变（40＋2=42、40＋3=43）

② 程序文本 + 接口说明 → .模块制品      ★ 已通（但能力码段空）
   扩展根目录/原子支持库/编译器支持库/examples/出模块制品.rs
     走真 1106 链：词法 → 语法 → 语义 → 装包（调的就是 1106 内部那一个函数）
     件头如实写：「本仓没有『程序文本 → WebAssembly』的代码生成器 ⇒ 能力码段传空字节集」
   ⇒ 链路通，但制品里**没有可执行的东西**

③ 底座装载模块                        ✗ 只解析，不执行
   对外接口面/调用接口面/src/执行装配/模块制品.rs::取模块接口说明
     件头明写：「本模块的制品不同：它的能力码段是 WebAssembly，底座**不**装载它」
   ⇒ 底座对模块只做「读接口说明 + 登记」，不取执行体
```

### 17.3 根因：一处形态冲突（三方口径不一致）

```text
契约声明/src/契约声明/容器封装/容器.rs       段类型_能力码 = 17（常量在位）
扩展装载/后缀表.json                模块三段 = [接口说明段 16, 能力码段 17（WebAssembly · 1106 编译产出）, 指纹段 18]
编译器实际产出                      本机 Rust 源码（文本）
底座装载器                          按「17 = wasm32 原字节」预期，且**不装载模块**
实际制品                            能力码段 = 空
```

★ 最后一条的证据（**本轮审计补强**，先前只测了「不是 wasm」，证据不足）：

```text
直接证据：扩展根目录/原子支持库/编译器支持库/examples/出模块制品.rs
    let 包件字节 = 能力包件::装包(&说明, &[])   ← 第二个实参传的是空切片
  件头自述：「本仓没有『程序文本 → WebAssembly』的代码生成器 ⇒ 能力码段传空字节集」
旁证：制品里搜不到 wasm 魔数（00 61 73 6d）
```

⇒ 三个地方对「模块的能力码段里装什么」有**三种不同说法**：
「WebAssembly 字节」（后缀表）「本机源码文本」（编译器实际产出）「空」（实际制品）。

**这就是根因三（当前态表达不一致）在代码层的实例** ——
同一件事，契约写一套、生成器做一套、制品里是第三套。

### 17.4 为什么没批「格式变更」

```text
开发文档/实际架构.md（原文）：
  「模块本机执行体的制品承载位置尚未批准，相关公开格式变更暂停；
    保留旧模块段 17 的 WASM 含义。」

⇒ 项目**有意暂停**了这件事：不敢擅自改 17 段的含义（那是已冻结的公开面），
  而承载位置（执行体放哪个段）又没批准 ⇒ 整条链停在这里。
  这是**正确的克制**，不是疏漏。
```

### 17.5 打通它需要先裁的三个问题

```text
问题一：执行体放哪
  候选 A：复用能力码段 17，改含义为「本机执行体」
          —— 违反「不许改旧字段含义」，且破坏旧模块制品
  候选 B：新增一个段类型号（如 20）承载本机执行体
          —— 走「新增段类型号」这条合法演进路，但需登记进 冻结登记.json
  候选 C：不改容器，把「执行体来源」放在制品外的旁路文件
          —— 最省事，但会让「制品不自包含」，与「一份制品装下全部」相冲

问题二：谁编译
  现在 本机生成 产出的是 Rust 源码，还要再经 rustc 编译成机器码。
  这一步放在：构建侧（出制品时编好）还是 运行侧（装载时现编）？
  —— 构建侧更稳（不依赖运行机有 rustc），运行侧更灵活。需裁。

问题三：平台身份
  本机执行体是「这台机器 + 这个 rustc」的产物。
  换平台（macOS → Linux、arm64 → x86）就必须重编。
  制品里要不要带「平台身份」字段、不匹配时怎么拒？需裁。
```

### 17.6 对加速顺序的修正

上一节的「第一步：打通一个模块的真闭环」**具体化**为：

```text
第一步（修正后）
  ① 先裁「执行体放哪」（三选一，见 17.5）
  ② 再补「谁编译」与「平台身份」两个判定
  ③ 然后改一处：让 出模块制品.rs 把真执行体装进去（而不是传空）
  ④ 验收：求和模块真被调用，返回的不是 0，而是两个入参的和
     —— 注意现状：程序文本写的是 返回 (0)，能力声明写的是「两数相加」
        这两处本身就对不上，要一起修正
```

### 17.7 附带发现：样本自身的声明与行为不符

```text
扩展根目录/组合模块库/数值统计模块/调用流程/求和.程序文本
    .子程序 求和
        返回 (0)                      ← 行为：恒返回 0

扩展根目录/组合模块库/数值统计模块/能力声明/7950.json
    名称：求和
    说明：「把两个整数相加，返回它们的和」   ← 声明：两数相加
```

⇒ 声明与本体**不一致**。而 出模块制品.rs 的接口说明六字段是**字面写死的**
（件头自述：映射未裁、字面写死），所以制品里的接口说明也来自这份声明、与程序文本无关。

**这正是「模块源码改行为变」这条考题至今未过的直接原因**：
程序文本改不改，都返回 0；声明说加、本体说 0。要过 T02，得先把样本改对。

**为什么这个顺序**：批量翻译的成本是线性的，但**闭环不通时收益是零**。
先把「1 个跑通」做扎实，再放大，比先翻译 1000 个再回头修闭环便宜得多。

## 十九 建议怎么做（本轮结论）

前面各节是「现状与根因」。这一节回答一个问题：**接下来该怎么办。**

### 19.1 一句话建议

```text
不要重写，不要批量迁老项目，不要先做体验优化。
按「四步」走，每步都能独立验收；走完这四步，这个项目就稳了。
```

### 19.2 四步（顺序不能换）

```text
第一步  把「模块执行体放哪」裁下来（一次会议的事，零代码）  ✅ 已裁（2026-10-12）
  为什么排第一：它是当前唯一「卡住一切」的点。
              不裁，模块库就永远只能声明、不能执行；
              裁了，后面三步都是顺着做的活。
  裁到哪：项目文档/决策记录/2026-10-12_模块执行体承载与编译裁决.md
          （段 20「本机执行体段」· 构建侧编译 · 制品带平台身份不匹配即拒）

第二步  打通「一个模块」的真闭环（改一处代码 + 修一个样本）  ✅ 已闭（生成侧 + 装载侧）
  做什么：把真执行体装进模块制品 → 底座能取到 → 真调用返回正确结果
  验收：求和模块被调用时，返回两个入参的和（而不是恒 0）
  顺带修：样本的声明与本体不一致（程序文本写 返回(0)，声明写"两数相加"）
  现状：两侧都已闭并实测（生成侧见 §24 · 装载侧见 §25）；
        「底座能取到 + 真调用」已在适配器那条腿成立（求和(2,3)=5），
        只剩对外接口面（HTTP 面）还没把这条装载链接上去。

第三步  打通「三类类型」的翻译闭环（老项目里最常见的三类）
  列表型参数 · 结果型结构 · 文本默认值 —— 各跑一遍真消费者读回
  验收：翻译一份带这三类的老模块，生成、装载、调用、结果都对

第四步  才谈批量迁移
  用前三步的成果，先迁 3~5 个真老能力，再放大
```

### 19.3 每步的「做完」判据（避免又变成做不完）

```text
第一步做完 = 有一个写下来的裁决（执行体放哪个段 / 谁编译 / 平台身份怎么判）
第二步做完 = 一条命令跑完，求和模块返回「两数之和」，且改源码行为跟着变  ✅（§24 + §25）
第三步做完 = 三类类型各有一条真实读回证据
第四步做完 = 5 个老能力端到端跑通，且**没有改底座一行**
```

### 19.4 与「维护困难」的关系

```text
项目感觉维护困难，根子在两件事：
  ① 元层（治理工具）与对象层（底座本体）挤在一起 —— 见 §三 根因一
  ② 「当前态」有五种表达，读的人分不清在途 / 已实现 —— 见 §三 根因三

这两件**不阻塞**上面的四步，但会一直增加维护成本。
建议：四步走的同时，顺手做两件零代码的事 ——
  · 把《派腿前置》排进 AGENTS.md 的读取顺序（§八 断点一）
  · 会漂的数字改成取证命令（§八 断点三）
```

### 19.5 明确不做的（防止摊子铺太大）

## 二十 待裁项清单（供一次拍定）

§17.5 提到的三个问题，整理成一张表，供项目组一次裁决。

| 项 | 问题 | 选项 | 建议 |
|---|---|---|---|
| 裁一 | 模块执行体放哪个段 | A 复用能力码段 17（改旧含义）· B 新增段类型号承载本机执行体 · C 制品外旁路文件 | **B** —— 走「新增段类型号」这条合法演进路，不动旧含义、不破坏旧制品；只需登记进冻结登记 |
| 裁二 | 谁把执行源码编译成机器码 | A 构建侧（出制品时编好）· B 运行侧（装载时现编） | **A** —— 不依赖运行机有 rustc，制品自包含；代价是构建侧要带工具链 |
| 裁三 | 平台身份怎么处理 | A 制品带平台身份字段，不匹配即拒 · B 不带，运行侧自负其责 | **A** —— 本机执行体绑定「机器 + 工具链」，不带身份就会出现「装上了但跑不动」 |

**裁决口径建议**：三条一起裁，不要分开 ——
它们互相咬合（放哪决定谁编译，谁编译决定要不要平台身份），分开裁必然返工。

**裁完之后的最小动作**（一次做透）：

```text
① 在 冻结登记.json 加一条登记（新增段类型号）
② 让 出模块制品.rs 把真执行体装进去（不再传空字节集）
③ 修 数值统计模块 的样本：程序文本与能力声明对齐
④ 跑一次：装载 → 调用 → 返回两数之和
⑤ 补一条反向样本：改程序文本的常量，返回值跟着变
```
