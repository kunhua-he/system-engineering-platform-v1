## 零 一句话结论

项目**不是架构选错**，而是**元层（治理工具）与对象层（底座本体）挤在同一个仓、同一套门禁、同一个台账里**，
导致「维护底座」这件事被「维护维护系统」压住了。

修的方向不是重写，也不是继续加能力，而是**先把元层独立出来并给它自身的纪律**，
再让对象层去补核心接缝。

## 三 根因（六条，从底层）

### 根因一 元层与对象层没有分家（最底层的一条）

一个仓里同时住着两件性质完全不同的东西：

```text
对象层（底座本体）  契约声明 · 运行内核 · 跨语言适配 · 对外接口面 · 扩展
元层（治理工具）    MCP服务 · 门禁 · 信息核心 · 开工账本 · 合并工具 · 反馈系统 · 清理
```

它们**共用**同一套行数判据、同一套命名判据、同一个未完成台账、同一条闸0。

后果：**元层要修自身，得先过对象层的门禁；而门禁又住在元层里**。

实测已发作（性能改造腿自报）：

```text
循环导入 ⇒ 一键验证包 import 失败
       ⇒ 写前校验不可用
       ⇒ 只能直写文件
       ⇒ 又致指纹漂移
```

这不是一个 bug，是**结构性的循环依赖**：验证者与被验证者是同一团代码。

### 根因二 写入口不止一个，保护层可被绕过

设计上，改源码只有一条路：

```text
v1_edit ─ 四道闸：开工进行中 · 路径已认领 · 指纹对得上 · 旧内容唯一定位
```

★ **本轮复核：这两处旁路已经修掉了**（实测现码，不再是缺口）：

```text
① 无开工ID 的 v1_shell 写主干
   已修 —— 新件 开发工具/MCP服务/主干写盘兜底.py：
   无开工ID 时跑前/跑后各取一次主干快照，已跟踪件被改/删 ⇒ 当场还原并点明；
   新增未跟踪件如实报出（不擅自删）；带开工ID 不介入

② 自检 / 样本遥测写生产账本
   已修 —— 工具流水.py 加「记账域」：域内落进程私有临时库，
   同一份实现只换落点；出域一律 reset ⇒ 不泄漏到并发生产请求
```

⇒ 根因二**本轮收窄为**：写入口旁路已封；但「生成器 / 建库直接写盘」这一路
的记账与指纹链完整性，仍属**待核**（未实测）。

### 根因四 门禁测形状，不测行为；「全绿」与「核心稳固」脱钩

```text

```

后果：

```text
门禁全绿  ≠  子进程隔离成立
          ≠  模块程序文本能变真实行为
          ≠  技能能按号取文
          ≠  发布/回退/恢复成立
```

项目已把这条写进《判据的可信性》，但**放行口径尚未强制绑定行为考题**。

```text
           ⇒  永远感觉做不完
```

## 五 防重犯机制

这一节回答华哥的原问题：**「避免以后还会重犯」。**

### 5.1 已修缺陷 → 抽判据进闸（项目已有此裁决，但只覆盖了一半）

现有纪律「重复错误就抽节点」是对的，但**只抽到对象层**。
本件补齐**元层也要抽**：

```text
对象层缺陷  ⇒  抽对象层判据（命名 / 行数 / 依赖 / 契约形状）
元层缺陷    ⇒  抽元层判据（写入口封闭 / 遥测隔离 / 账本一致 / 回执一致）
```

落点：元层判据单独成组，进闸0 的**实现侧**或独立一组，与对象层判据分开报。

### 5.2 每条新判据必须带反向样本

依据：《判据的可信性》（最高判据 · 假绿六源 / 假红四源 / 反向样本）。

```text
正样本：合规件判绿
反样本：人为植入缺陷，判据必须判红
退回：  撤掉植入缺陷，判据必须恢复判绿
```

★ 反样本要打在**真实件**上，不能用临时夹具自证（临时夹具测不到生效点 = 假绿）。

### 5.3 规则 / 文档空间设上限，防止再膨胀

```text
① 新增规则前先查「能否并入既有」—— 同主题默认合并成一条
② 给规则空间设硬上限，达到上限必须先合并出空位
③ 被取代的条款整条删，不留划线原文、不写废止声明（历史交 git）
④ 编号不复用；删条款留一行空号说明
⑤ 每份 md 必须在 文档账本.json 定档（判据 ㊶ 已卡）
```

### 5.4 「当前态」只允许一种表达

```text
已实现  ⇒  代码 + 行为考题证据
在途    ⇒  唯一台账（一条一个行为切片）
待议    ⇒  临时文档（一次性，批准后入库即删正文）
已定    ⇒  信息核心.db 条款 / 决策记录
```

禁止：方案正文里混写「现状判断 + 建议 + 待办清单」。
方案只写建议；现状由读数回答；待办由台账回答。

### 5.5 文档口径随工具面自动对齐

本次已实测出文档落后：

```text
AGENTS.md / README.md 写「五个工具」  实际 13 个（tools/list 实测）
```

⇒ 工具清单、操作目录、判据条数这类会漂的数字，**文档只写取证命令，不写具体值**。

## 十七 模块执行体闭环：卡点定位（本轮深挖）

上一节说「模块闭环未通」是最大瓶颈。本轮把它**逐段拆开实测**，找到了具体卡在哪一步。

### 17.1 结论先说

```text
闭环没有断在「编译器不会生成执行体」—— 那一步已经通了。

    编译器实际产出：本机 Rust 源码（文本）
    ⇒ 两者对不上，所以模块制品的能力码段至今是**空**的
```

### 17.2 实测：链条逐段状态

```text
① 程序文本 → 执行源码（真生成）        ★ 已通
   扩展根目录/原子支持库/编译器支持库/src/执行函数面/本机生成/
```

### 17.3 根因：一处形态冲突（三方口径不一致）

```text

编译器实际产出                      本机 Rust 源码（文本）
底座装载器                          按「17 = wasm32 原字节」预期，且**不装载模块**
实际制品                            能力码段 = 空
```

★ 最后一条的证据（**本轮审计补强**，先前只测了「不是 wasm」，证据不足）：

```text
直接证据：扩展根目录/原子支持库/编译器支持库/examples/出模块制品.rs
    let 包件字节 = 能力包件::装包(&说明, &[])   ← 第二个实参传的是空切片
  件头自述：「本仓没有『程序文本 → WebAssembly』的代码生成器 ⇒ 能力码段传空字节集」
```

⇒ 三个地方对「模块的能力码段里装什么」有**三种不同说法**：
「WebAssembly 字节」（后缀表）「本机源码文本」（编译器实际产出）「空」（实际制品）。

**这就是根因三（当前态表达不一致）在代码层的实例** ——

```text
    说明：「把两个整数相加，返回它们的和」   ← 声明：两数相加
```

⇒ 声明与本体**不一致**。而 出模块制品.rs 的接口说明六字段是**字面写死的**
（件头自述：映射未裁、字面写死），所以制品里的接口说明也来自这份声明、与程序文本无关。

**这正是「模块源码改行为变」这条考题至今未过的直接原因**：
程序文本改不改，都返回 0；声明说加、本体说 0。要过 T02，得先把样本改对。

**为什么这个顺序**：批量翻译的成本是线性的，但**闭环不通时收益是零**。
先把「1 个跑通」做扎实，再放大，比先翻译 1000 个再回头修闭环便宜得多。

### 22.8 实际怎么派（后台会话 · 不是子代理）

★ 华哥纠正过一次：**要的是「后台会话」，不是「子代理」**。
两者不是一回事，做法与可见性都不同：

```text
子代理（delegate_task）        一次性、无交互、回执回主会话；界面里不独立成会话
后台会话（tmux + hermes --in） 独立会话 · 桌面端可见 · 能中途 send-keys 纠偏
```

**项目实际用的是后台会话**（与《派活前置》口径一致：一条信 = 一个独立 worker）。

起法（照 hermes-background-tasks 技能，已验证）：

```sh
export PATH="/opt/homebrew/bin:$HOME/.local/bin:$PATH"
TM=/opt/homebrew/bin/tmux
R=/Users/hekunhua/Documents/Agent/PHP/系统工程平台V1
$TM new-session -d -s <会话名> -x 200 -y 50 -c "$R" "hermes --in \"$R\""
# 等 REPL 就绪（出现 Welcome to Hermes Agent）再发提示词，发早会被吞回车
$TM send-keys -t <会话名> '读 <派活信绝对路径> ，按它的口径做。' Enter
```

三条要点：

```text
① 会话名一律 ASCII（bash 标识符只认 ASCII）
② 必须给 hermes --in <仓根> —— 只给 -c 会把会话 cwd 落成启动器目录，
   桌面端会把它归到「Hermes 源码」项目而不是 V1
③ 提示词要点名**派活信的绝对路径**，让 worker 自行读信 —— 信是接口，别在提示词里复述
```

**派活信落点**：`<运行数据根>/临时件/派活_<名>.md`（照模板写，见《派活前置》§七）。
**回执落点**：`<运行数据根>/临时件/回执_<名>.md`。
**可判定的回传信号**：回执文件落盘（不靠盯屏猜）+ 后台哨兵轮询。

**收尾纪律**：会话做完**不会自行退出**（停在最后一条注入消息上等人回话）；
活已交就 `tmux kill-session` 清掉，别留小尾巴。
